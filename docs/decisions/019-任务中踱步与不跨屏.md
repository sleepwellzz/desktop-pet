# 019 · 任务进行中的踱步；以及"不跨屏"作为锁定范围

- **状态**：已接受
- **日期**：2026-09-18
- **决策人**：用户（范围、距离上限、频率、跨屏）
- **影响**：`src/kernel/behavior.ts`、`desktop-pet.json`（`behavior.busyPace`、`behavior.edgePolicyScope`、
  `behavior.note`）、`src/main/index.ts`（启动日志一行）、`tools/status-arbiter.test.mjs`、
  `spikes/m3-behavior/`（临时包加 `busyPace`、④ 用例重写）
- **修订**：**取代 ADR 018 决策 1 的前半句**（"`status !== 'idle'` 就整体让位、一步不动"）。
  018 的其余内容（纯函数分层、缩放归一化、夹进工作区、抑制条件）全部继续有效。

## 背景

ADR 018 刻意留了一个没拍的产品决定（018 负面结论 1）：**"任务进行中，宠物能不能离开原位？"**
当时把"运行中看起来像在忙"记成待兑现的承诺，但没做，理由是不能由实现方顺手替产品拍板。

2026-09-18 用户给了答复，分两段：

1. 关于"忙碌动作"这个词：**他不记得这条是怎么记下来的，因此那条待办作废** ——
   不再追求"让宠物看起来在忙"这个动机。本文不再使用那个名字。
2. 关于位置问题，他给了明确要求：**可以离开原位，但不超过几百像素（约 300–400px）**；
   往屏幕内侧走几步就行，不用走太远；**频率不能高，只能作为点缀与解闷的场景**。
   关于多屏：**暂时不考虑多屏** —— 只在主屏活动，或者"我把宠物拖到哪块屏，它就一直在这块屏活动"。

所以本轮做的是一个**更小、更明确**的行为：任务进行中的低频短距离踱步。

## 决策

### 1. 新增"踱步模式"（`busyPace`），与空闲模式并列

`kernel/behavior.ts` 里 `tickBehavior` 的规则 0 拆成两条：

- `status === 'idle'` → 空闲模式（漫游 / 微动作 / 打盹），沿用 ADR 018 的全部规则；
- `status !== 'idle'` → **踱步模式**（`tickBusy`）：不漫游、不微动作、不打盹，只在中低频上走一小步。

新增 `BehaviorPhase = 'pacing'`，以及三个状态字段：`busySinceAt`（进入踱步模式的时刻）、
`anchorX`（踱步锚点）、`nextPaceAt`（下一次踱步的到点时刻）。

### 2. **目标由锚点算，不由当前位置算**（这是本决策最重要的一条）

每次踱步的目标 = `anchorX ± distancePx`，其中 `anchorX` 只在**进入任务状态时**与
**每次抑制结束后**重记。

如果按"当前位置 ± 距离"累加（漫游就是这么做的），踱十次就飘出几百像素 ——
用户要的"不超过几百像素"会在几分钟后**悄悄失效**，而且屏幕上只表现为"它怎么跑那么远"，
没有任何报错可循。锚点约束让这条要求变成**结构性成立**，而不是"大概率成立"。

### 3. 方向朝**工作区中心那一侧**，而不是固定朝左

用户的原话是"往左走几步"，但那是在他常见的摆放位置（工作区右下角）说的。
固定朝左会在宠物贴着屏幕左边时**永久失效**（每次都够不到，`pickPaceTarget` 返回 null）。
朝中心在右下角时**恰好就是朝左**，观感与用户描述一致，且任何位置都不会失效。

### 4. 距离上限 **300px**，频率 **60–180 秒**

用户说"大概三四百个像素"。取 300 是留出余量：这个数值同时就是"最多离开锚点多远"，
取值贴着他的上限会让"不超过几百像素"变成"正好等于几百像素"。频率取 60–180 秒，
刻意比空闲漫游（25–90 秒）更稀疏 —— 它是点缀，不该成为主要活动方式。

### 5. 踱步速度**沿用漫游的速度基线**（默认 96px/s @ 默认缩放）

位移速度是照着位移行的步频校过的（ADR 018 决策 3）。给踱步另设一个速度会有一处**滑步**
（脚在原地打滑或拖地）。sidecar 里留了 `busyPace.speedPxPerSec` 可以调，但注释写明了这个约束。

### 6. **不跨屏** —— 锁定为范围，不是"暂时不做"

用户明确表示暂不考虑多屏。落地方式零代码改动：`workArea` 每 tick 用
`getDisplayNearestPoint(宠物中心)` 取，宠物在哪块屏就用哪块屏的工作区，目标点夹进去；
而锚点在**每次抑制结束后重记**（拖动属于抑制）—— 于是"把宠物拖到哪块屏，它就在哪块屏活动"
是这个机制的**自然结果**，不需要任何额外的显示器逻辑。

`desktop-pet.json` 的 `edgePolicyScope` 从"【本轮范围】…留到后续"改成"【锁定范围，ADR 019】不跨屏"。

### 7. 有任务时**不计打盹**

踱步模式下 `idleSinceAt` 恒为 `null`。打盹是"没人理它"的表现，正在干活不该趴下；
而且用户要的是"多一点生活感"，睡了就没有了。

### 8. 抑制条件与"减少动态效果"与空闲模式一致

拖动中 / 宠物被隐藏 / 全屏让位 / 控制条打开 → 一步不动，并**清掉锚点**（恢复后在新位置重新锚定）。
「减少动态效果」下不踱步（只是不位移，动画覆盖照常交回业务状态）。

## 实测（2026-09-18）

**离线单测**（`tools/status-arbiter.test.mjs` ⑭ 段，虚拟时钟 + 固定随机种子）：
**191 → 219 项断言**。新增 ⑥b（踱步）与 ⑥c（不跨屏）两组，其中三条是这次的核心判据：

- 踱几十次之后仍在锚点 200px 以内 ⇒ **无累积漂移**；
- 默认节奏（60–180 秒）下 10 秒内一次都不踱 ⇒ **频率确实是点缀级**；
- `workArea` 换成"另一块屏"时，目标点夹在新工作区内、锚点留在新屏上 ⇒ **不跨屏**。

同时改写了 ⑥：`running` 期间不再是"一步不动"，而是"交回业务动画 + 锚在当前 x + 踱步未到点所以不动"。

**真实窗口探针**（`spikes/m3-behavior`，临时宠物包把节奏压到 3–5 秒 / 60–160px）：

```
④ running 期间踱步：在动=true｜锚点=1249（观测期内 1 个锚点）｜离锚点最远 111px（上限 160px）
  ｜相=idle｜画面行号=[7,2,1]（7=running 业务态，1/2=位移行）｜越界采样=0
④b 清空会话后恢复自由漫游=true
```

判定 **PASS**（7 条全过）。另外 ①②③⑤ 与之前一致：只沿地平线走 / 抓住 3 秒一步不动 /
控制条开着不动 / 打盹画第 5 行且单击能醒。

## 负面结论

1. **踱步期间画的是位移行（第 1/2 行），不是业务状态那行**。这是本轮唯一需要用户看画面才能确认的取舍：
   另一条路是"业务动画不动、只是窗口在挪"，画面上会变成生日姿态在地面上平移 —— 明显更怪。
   用户原话"动画可以照常播放"两种读法都通，所以记在这里，**验收时看一眼**；改的话是一行。
2. **锚点是"进入任务状态时的位置"，不是"用户放置的位置"**。所以如果宠物在空闲时漫游到了
   某处再被任务打断，踱步就锚在那里。这与"拖到哪块屏就在哪块屏活动"一致（拖动会重新锚定），
   但意味着**长期跑任务的宠物会停在任务开始那一刻所在的位置附近**，而不是回到用户最初放它的地方。
3. **`busySinceAt` 兼作两件事**（"在踱步模式"与"需要重新锚定"）。复用省了一个字段，
   代价是它的名字只说了前一半 —— 读代码时要记得抑制期间被清成 null 是**故意的**。
4. **"不跨屏"是范围而不是能力**：将来要做跨屏，先要定义两件事 ——
   "窗口矩形横跨两块屏时算哪一屏"与"多屏工作区并集"。这两条没定清楚之前，
   把目标点放进虚拟桌面范围只会得到"宠物卡在两屏缝隙里"这种更难查的 bug。
5. **优先级仍是"业务状态 > 自主行为"**，但表达方式从"完全不动"变成了"动，但动得很小、
   且不离开锚点"。这条分界线以后每次加自主行为都要重新问一遍：**它会不会干扰业务状态的表达？**
