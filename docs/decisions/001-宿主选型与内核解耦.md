# 001 · 宿主选 Electron，内核与宿主解耦

- **状态**：已接受
- **日期**：2026-09-15
- **决策人**：用户 + agent（依据方案文档 §5）

## 背景

桌面宠物的选型瓶颈不是业务逻辑，而是窗口层三项原生能力（透明置顶、逐像素点击穿透、不夺焦点）能否实现，以及常驻内存能否接受。

候选：Electron（≈250 MB / 200–400 MB）、Tauri 2（≈10 MB / 80–160 MB）、WPF/WinUI 3、PySide6（仅原型）、原生 C++/Rust + Direct2D。

## 决策

1. **M1–M2 用 Electron 作为宿主。**
2. **宠物内核（状态机 + 仲裁器 + 精灵播放器）写成纯 TypeScript，不 import 任何 Electron API。**
3. 宿主适配层收窄为四个接口：`createOverlayWindow()`、`setClickThrough(mask)`、`registerHotkey()`、`tray()`。其余能力（自启、持久化）走标准 Node/Rust 各写一份。
4. 状态源接入走本地 HTTP 或 stdio IPC，不依赖 Electron 的 IPC 对象。
5. M2 之后按需评估平移 Tauri 2。
6. 排除 Unity / Godot：其窗口层为游戏全屏设计，透明无边框 + 穿透 + 不抢焦点都要靠引擎外补丁。

## 理由

ChatGPT 桌面端本身是 Electron 应用，同栈意味着"复刻行为"的试错成本最低。M1–M2 的目标是把交互、状态机、锚点这些真正难的东西做对，而不是优化体积。

守住第 2、3、4 条，迁移成本就是重写一个几百行的适配层，而不是重写整个应用。**反之，一旦图省事到处直调 Electron API，就永久失去这个选项。**

## 后果

- 常驻内存偏高（200–400 MB），是已知代价，接受。
- 内核代码必须接受"不 import Electron API"的约束，需要代码审查把关。
- 若未来自研渲染改用 Canvas/WebGL，内核不受影响。
