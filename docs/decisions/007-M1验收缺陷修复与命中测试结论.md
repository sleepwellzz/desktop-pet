M1 人工验收（PLAN §4 六项判据）结果：

两项缺陷的排查结论如下。

## 缺陷 1：全屏让位完全失效（已修复）

### 现象

任何全屏应用都不会让宠物消失。用户实测：B 站视频全屏播放，宠物仍在。

### 根因

`detectFullscreen()` 里 `GetWindowRect` 把结构体写进 **JS 对象**：

```ts
const rect: Record<string, number> = {};
if (!w.GetWindowRect(fg, rect)) return status;
```

koffi 对结构体**不回写 JS 对象**（与本工程 M0 阶段踩的嵌套结构体坑同源，见 ADR 004）。
函数返回 `true`，但对象上读不到字段，`rect.right` 等全为 `undefined`：

```
修复前探针输出： fgRect = "undefined,undefined,undefined,undefined"
                monitorRect = "0,0,1707,1067"
```

于是 `(rect.right ?? 0) >= m.right` 恒为 `0 >= 1707` → false，
`coversMonitor` **永远为 false，且不报任何错**。表现就是"宠物永不让位"。

### 修复

1. `GetWindowRect` 改为传 `Buffer` 手工解码（与 `GetMonitorInfoW` 一致）。
2. `MonitorFromWindow` 的标志从 `1`（MONITOR_DEFAULTTOPRIMARY）改为 `2`（MONITOR_DEFAULTTONEAREST）：
   原值会**永远返回主显示器**，多显示器下会把副屏全屏误判为"没覆盖"。
3. 补上规格里早已设计、却没接入的辅助判据：
   `SHQueryUserNotificationState === 'RUNNING_D3D_FULL_SCREEN'` 也算全屏
   （部分独占全屏游戏的窗口矩形与显示器不完全重合）。
4. 轮询首帧：若**启动瞬间就已在全屏**，立即让位（原来要等全屏状态变化才响应，
   会先显示再隐藏，闪一下）。

### 验证

```
修复后探针输出： fgRect = "0,1027,1707,1067"  monitorRect = "0,0,1707,1067"  coversMonitor = false
```

`fgRect` 取到真实值（该矩形是 40px 高的任务栏），判据恢复正常。

## 缺陷 2：命中区域不精细（部分修复，待复验）

### 已确认的事实（全部来自实测）

1. **规格里写好了阈值命中，实现里从未接线。**
   `desktop-pet.json` 声明 `render.hitTest = "alpha-threshold"`、`hitTestAlphaThreshold = 16`，
   但全工程只有类型定义引用了它，没有任何代码读取 —— 实际生效的是系统的
   "alpha > 0 即命中"，比规格宽松。
2. **精灵图空白区确实干净**：全图 69.3% 的像素 alpha 严格为 0；alpha 1–15 的"看不见但非零"
   像素只有 7907 个（0.3%）。
3. **窗口表面的低 alpha 像素全部紧贴轮廓**，不是散落在空白区的噪点：

   | 距可见主体 | 修复前 | 修复后 |
   |---|---|---|
   | > 2px | 25 个 | 18 个 |
   | > 4px | **0 个** | **0 个** |

4. **半透明（alpha 16–127）像素同样全部落在边缘 2px 内**（>2px 为 0 个）。
   即它们是**抗锯齿 + 1.5x 缩放插值**的产物，不是需要保留的美术细节。

   （测量方法：以 `alpha ≥ 128` 为主体做形态学膨胀，统计外围像素到主体的距离分布。）

### 已实施的修复

在渲染层落实规格阈值：精灵图加载后把 `alpha < 16` 的像素连同 RGB 一起清零，
再交给绘制。系统侧命中测试于是退化为"与人眼所见一致"，且不需要引入
`setIgnoreMouseEvents` 那种运行时开关（会有延迟与闪烁）。

实测生效：清理 **2,000,388** 个像素，恰为 `alpha==0 (1,992,481) + alpha 1–15 (7,907)`，
两处独立测量互相印证。自检截图确认动画仍在播。

### 尚未解释、需复验的一点

修复后窗口表面仍有 410 个低 alpha 像素（纯插值产物），但**全部在轮廓 2px 内**。
按此数据，用户在"远离身体的空白区"点击**不应该**触发宠物交互。

因此存在两种可能，需要用一次精确复验区分：

- **A（边缘误差）**：用户点的其实是贴近轮廓 1–2px 的位置 → 属像素级命中测试的固有精度，可接受。
- **B（穿透失效）**：用户点在明显远离轮廓的空白区（窗口左右各有约 46px 纯透明带）也会触发
  → 说明分层窗口的 alpha 穿透在实机上并未生效，需要重新设计穿透方案。

复验动作：在宠物**左侧约 30 像素**的空白处单击一次，观察是否触发挥手。

### 若判定为 A，可用的收紧手段（本次未启用）

- 提高 `hitTestAlphaThreshold` 到 128：边缘变硬边，命中区再收缩约 1px；
  已用上述距离分布证明**不会破坏美术细节**（半透明像素全在边缘 2px 内），代价是边缘失去抗锯齿。
- 本次**刻意没有顺手改它**：一次只动一个变量，先修确凿的 bug，把调参留给有复验数据之后。

## 负面结论：WindowFromPoint 不能用来验证 alpha 穿透

本次为确证缺陷 2，专门搭了原生命中测试探针（`WindowFromPoint` 网格采样 +
与精灵 alpha 逐点比对）。**方法不成立，探针已删除。**

实测证据（宠物窗口，物理矩形 2237,1193~2530,1510）：

```
共采样 23373 点，全部命中
foreignWindows: [{ hwnd: 0x3938530, className: "Chrome_RenderWidgetHostHWND", count: 23373 }]
```

即：**包括纯透明处，WindowFromPoint 一律返回宠物窗口自己的渲染子窗口**。

原因有二：

1. Chromium 的窗口是分层的，顶层 `Chrome_WidgetWin_1` 里套着铺满客户区的
   `Chrome_RenderWidgetHostHWND`，`WindowFromPoint` 返回最深的子窗口 —— 因此
   **不能拿它和 `BrowserWindow.getNativeWindowHandle()` 直接比相等**，
   要先用 `GetAncestor(hwnd, GA_ROOT)` 提升到顶层。
2. 更关键：`WindowFromPoint` 反映的是"客户区覆盖"，**不体现分层窗口的 alpha 穿透**。
   它无法回答"这个点最终归谁"。

**要验证穿透，唯一可靠的路子是 M0 用过的办法**：`SendInput` 真实点击 + 观察谁收到事件
（M0 用另一个进程的靶窗口；本项目内可以改成让渲染层上报 `pointerdown`）。
下次需要时按此实施，不要再走 `WindowFromPoint`。

## 经验教训（跨会话复用）

- **koffi 传结构体，一律传 Buffer 手工解码。** 传 JS 对象会"返回 true 但字段全 undefined"，
  静默失败、无异常、极难发现。本工程已在嵌套结构体（M0）与顶层结构体（本次）各栽一次。
- **规格里的参数如果没人读，等于没写。** 本次的 `hitTestAlphaThreshold` 就是这样潜伏在
  `desktop-pet.json` 里的。今后新增规格字段时，应同时确认有代码读取它。
- **验证手段本身要先被验证。** 探针第一次跑出"10388 点全部穿透"这种全 0/全 1 的结果时，
  就该先怀疑工具，而不是先怀疑被测对象。
