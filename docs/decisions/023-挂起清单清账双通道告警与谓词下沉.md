## 决定一：双通道互斥第一次在代码里有落点（运行期**告警**）

**ADR 020 的"一个 agent 只由一条通道负责"此前只是一句文档约束。**
同一个 agent 被 hook 与被动文件源同时盯着时，状态在两条通道之间来回跳，
**没有任何报错** —— 用户只能看到"点了宠物它又举手"，排查成本全花在猜上。

落地三条（"约 10 行"的那条告警 + 两条让它真正能触发的配套）：

1. **`StatusEvent.origin` 现在能区分写侧**：通道 A 的 hook 客户端写状态时带 `origin: 'hook'`；
   状态文件适配器读条目里的 `origin` 并透传，没有的按 `'file'`。
   （取值按投毒点的同一套纪律校验：`[A-Za-z0-9_-]{1,32}`，不认识的丢弃而不是透传。）
2. **`ingest()` 检测冲突**：同一会话在 **10 秒**内被两个不同 `origin` 上报 ⇒ 打一条 `⚠️ 双通道冲突` 日志，
   同一对冲突**冷却 60 秒**（不冷却的话这条告警会把真正的状态变化从日志里淹没 —— 恰好是它自己要诊断的东西）。
3. **只告警，不逐出**：该信谁属于产品决策（"被动源是降级来源"是 ADR 020 的话），
   机制级互斥仍**未实现**，见 ADR 022 挂起清单 #3 的①③。

**为什么"隔 10 秒"这个窗口是判据的一部分**：隔几分钟才换 `origin` 是"换了一次挂载方式"
（例如卸载 hook 后改用被动源），正常，不该告警；只有"两条通道同时在写"才是冲突。
两个**不同**会话各走一条通道也不告警 —— 多 agent 并存是设计内的形状。

判据：`tools/status-arbiter.test.mjs` 新增 ⑮ / ⑮b 两段共 10 项（含四条边界与冷却）。

## 决定二：`isAckable` 下沉内核，两处共用一份判据

`ack()` 的 `want()` 与控制条渲染层的 `needsAck` 在回答同一个问题，各写一份 ⇒ **已经失配过一次**
（`ready` 在面板上连「确认」按钮都没有，ADR 022 成因一）。

- 内核导出 `isAckable({ status, acknowledged?, expired? })`；
- `ack()` 的 `want()` 改调它，并**带上 `acknowledged`**（已确认的会话不该被重复确认：
  否则每次单击都重复记账、重复打日志，还会把状态变化限流的窗格重置掉）；
- 渲染层 `import { isAckable } from '../kernel/status'`，本地那份判据删除。

判据：⑯ 段 —— **20 组真值表**（五种状态 × 已确认 × 已过期，状态集合从内核 `PET_STATUSES` 取，
加状态会自动进表）+ **与 `ack()` 的行为对齐**（谓词说能消解的，`ack()` 必须真的消解，反之亦然）
+ **结构性断言**（渲染层不许再自带一份判据：源码里不得出现 `s.status === 'needs-input'`）。
只测纯函数是不够的 —— 两边各改一处仍然对不上，对齐那条才是防失配的关键。

## 决定三：`ready` / `stale` 的时间边界由探针钉住（**推翻交接文档的一处推测**）

新增 `spikes/m3-ready-ack/probe-ready-stale-boundary.mjs`（离线、秒级、**18/18**）。实测结论：

| 场景 | 主状态 | 面板 |
|---|---|---|
| `ready` 后 59 秒 | `ready` | 不标"已过期" |
| `ready` 后 61 秒 | `idle` ✅ | 标"已过期"（原始状态仍 `ready`） |
| **`ready` 心跳持续 16 分钟（每 15 秒重报）** | `idle` ✅ | **仍有 1 行，且标「已过期」** |
| `ready` 后停止上报，15 分钟后 | `idle` | **一行不剩** |
| `running` 静默 14 分 59 秒 → 15 分 01 秒 | `running` → `idle` | 1 行 → 0 行 |

**⚠️ 推翻的一条推测**：交接文档写的是"16 分钟心跳后 `viewSessions()` 应为空"。
**实测不为空** —— 心跳刷新的是 `SessionRecord.ts`，而静默兜底看的正是 `ts` ⇒
只要上游还在报，这条会话永远不会过期。

**由此产生一个新事实（未改代码，属产品取舍，留给你拍板）**：
**「（已过期）」不是死分支，而且在生产的重报节奏下会长期驻留** —— 宠物早已回待机，
面板却一直挂着一行"已过期"。可选处置：① 保持现状（如实但不美观）；
② 面板隐藏已过期的行；③ `ready` 到期即视为会话结束（改的是内核语义，影响面更大）。

## 决定四：preload 的诱饵产物不再生成

`tsconfig.json` 排除三个 preload 源码（它们由 esbuild 打包）。
`dist/main/preload-bar.js` / `preload-bubble.js` **全仓无任何引用、永不被加载**，
却会随源码同步更新 —— 制造"只跑 `tsc` 也已生效"的假象（真实加载的是 `bar-preload.js` / `bubble-preload.js`）。

排除不等于放弃类型检查：新增 `tsconfig.preload.json`（`noEmit`，只收这三个文件），
`npm run typecheck` 会连它一起跑。**踩到一个 TS 细节**：`exclude` 会被 `extends` 继承，
不清空就会出现"include 与 exclude 互相抵消 ⇒ TS18003 找不到输入"。

## 决定五：宠物隐藏时停掉两个高频定时器（33ms 行为层 + 16ms 光标轮询）

隐藏期间既没有光标要跟随、也没有动作要走，这两个定时器却照常每 16/33 毫秒醒来一次
（挂机时宠物常常一藏就是几小时）。

- 启停挂在**窗口的 `show`/`hide` 事件**上，不在各条隐藏路径手动配对 ——
  `hide()` 有三条路径（托盘 / 宠物右键 / 全屏让位），手动配对迟早漏一条，
  而漏掉的那条只表现为"恢复之后宠物不动了"，没有任何报错。
  （也不用 `isVisible()` 判断要不要启停 —— `show()` 之后同一 tick 内它可能仍返回 false，ADR 014 负面结论 1。）
- **250ms 那条刻意不停**：它推进仲裁器的粘滞超时与静默兜底，也是气泡到期与托盘状态行的时间来源 ——
  藏起来的宠物不再画东西，但托盘那行"需要输入"仍然必须如实变化。
- 顺带修掉退出时的一行噪音：先停定时器再拆窗口（否则拆完到进程退出之间还有一两次 tick
  落在已销毁的窗口上，`Object has been destroyed`）。

判据：新增 `spikes/m3-hidden-timers/` 真实窗口探针 —— 可见时 800ms 内 tick 增量 ≈17；
隐藏后 **1000ms 内增量 = 0** 且 `timersRunning=false`；恢复后重新起来（**PASS**）。
