# ADR 048：入库探针证据的归属与卫生 —— 证据是决策链的一部分，不能靠删除来"整理"

- 日期：2026-09-28
- 状态：已采纳
- 相关：ADR 047（判据必须能自证新鲜）、ADR 035（退出崩溃与定时器生命周期）、
  ADR 008 / 014 / 023 / 038 / 039（**均直接引用了具体探针证据文件**）、
  `docs/reviews/2026-09-28-全面代码复核.md`（P0-1）、
  `docs/constraints/build-probe.md`

## 背景

用户看这个仓库的第一印象是"根目录与文件排布杂乱、缺乏结构感"。第二点里有一项是
**`spikes/` 下 118 个入库文件**，看起来像"跑测试留下的垃圾"。

动手前的核实结论与直觉相反。分三类：

| 类别 | 数量 | 是否被引用 | 结论 |
|---|---|---|---|
| 探针源码（`*.js` / `*.mjs` / `README.md`） | 66 | 是 | 判据本体，必留 |
| 组件截图（`*.png`，`bubble-shot` / `control-shot` / `bubble-hotkey` 等） | 8 | 是 | 人工验收依据，必留 |
| **判据产物**（`*.json` / `*.out` / `*.log` / `*.jsonl`） | 42 | **是** | 见下 |

逐个查了 42 份产物被谁引用（排除"被 run.mjs 写"这种自引用），结果是
**ADR 008 / 014 / 023 / 035 / 038 / 039 逐一点名了具体文件**作为论证依据，
`docs/constraints/window.md` 也直接读 `m2-hittest/fs-verify.json`。

**所以"把可重跑产物出库"是错的**：那不是清理，是**切断决策链**。
`fs-verify.json` 一删，ADR 023 的"实测过了"就变成一句没人能复核的话。

## 决定

### 一、证据入库是**职责**，不是脏数据

**判据产物必须与其判据源码一起入库**，因为 ADR 用它们作论证依据。
清理"看起来重复"的证据，等于删掉别人（和未来的自己）复核结论的唯一途径。

**明确不做的**：不把 `spikes/**/*.json` / `*.out` / `*.log` 加进 `.gitignore`。
已经躺在 `.gitignore` 里的仍然保留：整屏截图（会拍进桌面、账号名、对话标题 ——
曾误提交并在公开仓库挂了 12 天，commit `8f682f5`）与可重跑的原始 payload 时序。

### 二、真正的噪声源是 `.out`，而它是**手工重定向**留下的

9 份 `*.out` 里**没有任何脚本写它们**（逐个查过 `spikes/*/*.mjs` 的写操作）——
它们是 `node xxx.mjs > run.out` 这种手工重定向的产物。
这带来两个具体问题：

1. **diff 噪音**：跑一次探针就可能整份变化，淹没真实改动。
2. **更严重的**：重定向出来的 `run.out` 会把探针 stdout 与 stderr 混在一起，
   于是 `[uncaught] TypeError` 之后紧跟一句 `全部探针 PASS`——
   **一份自相矛盾的证据**，而它就此入库并被 ADR 引用（P0-1）。

⇒ 处置：`tools/stamp-build.mjs` 已在 `m2-hotkey/run.mjs` 上落地
"**确认拿到新报告才 rename 覆盖**"（ADR 047）。其余 11 个 `run*.mjs`
仍是"先 `rmSync` 再跑"的旧写法 ⇒ **列入挂起清单，不在本轮动**。

### 三、证据卫生做**静态检查**，且**刻意不阻断**

新增 `tools/check-evidence.mjs`：静态扫描入库证据，找
"**内含未捕获异常却声称通过**"这类自相矛盾。接进 `tools/status-arbiter.test.mjs` ⓪c 节。

**当前扫出 3 份 error**（全部是 `Object has been destroyed` 之后仍报 PASS ——
正是 ADR 035 修掉的那个崩溃）：

- `spikes/m2-control/run.out`
- `spikes/m2-menu/run-tray.out`
- `spikes/m3-ready-exit/ready-exit.log`

⚠️ **本节明确不阻断、不计入失败**，这是有意的取舍：

这 3 份只能靠**重跑探针**修好，而重跑要启动 Electron（弹窗、抢焦点、改写产物），
本轮用户已决定**不跑 GUI 探针**。若把它做成硬失败，主测试就会**长期亮红** ——
而长期亮红的判据会被习惯性忽略。PLAN §4 #16 记的正是"偶发失败如何被磨成待观察、
最后不再当作已通过"这个过程。**长期亮红 ⇒ 判据被忽略 ⇒ 判据彻底失效，
这比少一条检查更坏。**

⇒ 判别标准写进纪律：**能立即修的才做成阻断闸门（⓪ 与 ⓪b），
历史遗留的只做成提醒（⓪c）。** 前者防"此刻正在发生的错误判断"，
后者防"已入库的历史污染"，性质不同。

## 后果

- `tools/status-arbiter.test.mjs` 现为 **452 项**（446 原有 + ⓪ 的 2 + ⓪b 的 2 + ⓪c 的 2）。
- **P0-1 未结项**：3 份污染证据已定位、已列清单、已建常态检查，
  但**要真正修好必须重跑探针**。
- `spikes/` 的文件数**不减少**——这是结论，不是遗漏。
  下一个 agent 若再看到"118 个文件"而想清理，**先读这份 ADR**。
