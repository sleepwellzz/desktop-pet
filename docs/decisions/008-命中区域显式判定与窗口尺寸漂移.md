# ADR 008：命中区域改由渲染层显式判定；窗口尺寸漂移修复

- 日期：2026-09-15
- 状态：已实施并实测验证
- 取代：ADR 004 中"用 `WS_EX_LAYERED` 原生命中测试实现逐像素穿透"的方案

## 1. 触发这次调查的用户反馈

人工复验（M1）报告三条：

1. **穿透区域不稳定**：左侧约 100px 处可点到后面的文件、上侧很准，但右侧要约 400px、下侧要约 700px；
   且**不停拖动之后，"点不动的区域"会发生很大变化，趋势是越变越大**，每次启动数值都不同。
2. **触发挥手的判定左右偏宽**：上下很精细（要贴很近），左右能隔几十像素仍然触发。
3. **宠物占地偏大**，希望缩到现在的 0.5~0.7 倍面积。

## 2. 实测方法与结论（spikes/m2-hittest）

方法：探针脚本 `require` **真实** `dist/main/index.js`（同一份主进程/preload/渲染层），
自己再开一个铺满显示器、opacity 0.10 的实心靶窗，然后用 `mouse_event` 注入**真实 OS 点击**，
逐点记录两个信号：宠物渲染层是否收到 `pointerdown`、靶窗是否收到。共 169 个采样点。

**结论 A：生效命中区域 = 整个窗口矩形，与精灵 alpha 无关。**

| 修复前实测 | 数值 |
|---|---|
| 窗口物理矩形 | 2237,1193 ~ 2530,1510（293×317 px） |
| 窗口矩形**内**采样点被宠物吃掉 | **90 / 90 = 100%** |
| 窗口矩形**外**采样点穿透 | 79 / 79 = 100% |
| 与"精灵 alpha≥16 应当命中"比对 | 应穿透却被吃 **43**，应命中却穿透 **0** |

也就是说：窗口里精灵轮廓左右各 46 DIP 的纯透明带，**全部**在吃点击。
M0 的"逐像素穿透是原生行为"这个结论**不成立**——M0 只验证了**窗口外**的点击能穿透，
没有验证**窗口内透明像素**的穿透，把"窗口外的穿透"错当成了"窗口内的逐像素穿透"。

**结论 B：窗口每移动一次就长 1 DIP（这就是"拖动后死区越来越大"的机制）。**

`setPosition` 在 150% 缩放下每次都要对"内容尺寸 ↔ 窗口尺寸"做一次 DIP/物理像素取整，误差逐次累积：

```
初始        DIP 148x160  物理 221x239
第1次移动    DIP 149x161  物理 222x240
第2次移动    DIP 150x162  物理 224x242
...
第6次移动    DIP 154x166  物理 230x248
```

修复前"死区 = 整个窗口矩形"，所以**拖得越多、死区越大**，且每次启动的初始尺寸略有不同
（DIP/物理取整在不同时刻落点不同）——完全对应用户描述的"数值每次都不同、趋势越变越大"。

## 3. 决策

1. **命中判定改由渲染层显式给出，窗口常态整窗穿透。**
   主进程起步就 `setIgnoreMouseEvents(true, { forward: true })`；渲染层按**当前帧**精灵 alpha
   判定光标是否落在实体像素上，命中才通过 `CH.interactive` 切回可交互，离开立即释放。
   命中区域从此完全由我们定义，与窗口尺寸、系统分层窗口行为都无关。
2. **判定驱动源 = 主进程 16ms 光标轮询**（只在光标位置真的变化时才发 `CH.pointerHint`）。
   原因：实测 `setIgnoreMouseEvents(true, { forward: true })` 下**鼠标移动不会转发到渲染层**
   （注入拖动期间渲染层收到 **0** 次 `pointermove`）。曾用 300ms 兜底轮询，结果出现
   20~37 个采样点"应命中却穿透"（点击落在宠物身上却穿了过去）。
3. **命中掩码只查单点，不做邻域膨胀。** 曾为对齐"浏览器双线性插值后看得见的那一圈"取 3×3 邻域，
   实测：误吃 0 → 4，而漏吃一点没降 → 回退。
4. **拖动改用 `setContentBounds`**（每次显式复位内容尺寸），消除尺寸漂移。
5. **`useContentSize: true`**：让 `width/height` 指内容区，画布正好铺满内容区。
6. **`render.defaultScale` 1.0 → 0.75**（面积比 0.75² = 0.5625，落在用户要求的 0.5~0.7 区间中部；
   与 sidecar 里 `scaleStep: 0.25` 一致）。实测宠物由 134×194 DIP 变为 **100×146 DIP**。

## 4. 复测结果（同一探针，冻结动画 + 逐点刷新基准帧）

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 窗口矩形内被吃掉 | 90 / 90（100%） | 34 个采样点，**全部落在精灵轮廓内** |
| **应穿透却被吃（误吃）** | **43** | **0** |
| 应命中却穿透（漏吃） | 0 | 2（轮廓最外一行，约 1px 边界效应） |
| 拖动后的命中图 | 不稳定 | 与拖动前**逐点一致** |
| 拖动后的窗口尺寸 | 每移动一次 +1 DIP | 稳定（拖动后物理 216×234 = 画布精确尺寸） |

缩放端到端验证：`--screenshot` 自检截图实测宠物覆盖 **151×218 物理像素 = 100×146 DIP**，
与"精灵表 idle 行并集包围盒 134×194 × 0.75 × DPR 1.5"完全吻合；两帧差异非空（动画在播）。

## 5. 已知限制与未解项

- **漏吃 2 点**位于轮廓最外一行，属 `floor` 取整与 1px 边界效应，肉眼不可辨；若要再收紧可加大
  `hitTestAlphaThreshold`。
- **切换有最长 16ms 延迟**：极快的"甩动鼠标 + 立刻点击"理论上仍可能穿透一次。实测 169 点未出现。
- **用户报告的"右侧 400px / 下侧 700px 死区"未能复现**：窗口物理矩形只有 293×317，
  物理上不可能吃掉 700px 之外的点击。判断为测量方法导致的假象（点桌面空白没有任何可见反馈，
  只能靠"最近的文件图标"间接判断，而图标位置与死区无关）。已向用户说明并给出更可靠的复验方法。
- 启动瞬间窗口物理矩形比画布大 5px（221×239 vs 216×234，150% 缩放下的取整），
  第一次拖动会被 `setContentBounds` 归一化。不影响命中判定。

## 6. 负面结论（避免重复交学费）

- **`WindowFromPoint` 不能用来验证分层窗口的 alpha 穿透**：窗口内任何位置都返回宠物自己的
  `Chrome_RenderWidgetHostHWND` 子窗口（M1 实测），本次甚至返回 null。它反映的是"客户区覆盖"，
  不是"点击最终归谁"。判定穿透只能用真实点击 + 观察谁收到事件。
- **`SetCursorPos` 不产生 `WM_MOUSEMOVE`**：用它注入"拖动"时渲染层收到 0 次 `pointermove`，
  窗口纹丝不动。注入移动必须用 `mouse_event(MOUSEEVENTF_MOVE | MOUSEEVENTF_ABSOLUTE, nx, ny, 0, 0)`
  （nx/ny 按虚拟屏 0..65535 归一化）。
- **探针的"应当命中"基准必须与被测帧同帧**。宠物在动时拿启动时抓的单帧快照做基准，
  会把漏吃率放大 3 倍（6 vs 2）；本探针最终采用「冻结动画 + 逐点刷新快照」。
- **`console.log` 在 Electron GUI 子系统进程里拿不到**：前后台启动都会被静默脱离，
  探针的一切输出必须落盘，由外层驱动脚本轮询文件。

## 7. 复现方法

```
node spikes/m2-hittest/run.mjs probe.js                # 命中区域逐点实测
node spikes/m2-hittest/run.mjs probe-grow.js grow.json # 窗口尺寸漂移
```

前者会短暂出现一个 10% 不透明度的黑色靶窗，并自动移动/点击鼠标约 40 秒，结束后光标归位。
