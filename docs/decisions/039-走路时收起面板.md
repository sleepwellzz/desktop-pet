# 039 · 走路时收起面板、走完还回来（手动把玩的位移类动作）

- **状态**：已接受
- **日期**：2026-09-22
- **决策人**：用户（产品判断：面板不该跟着飘走）
- **影响**：
  - `src/kernel/bar-policy.ts`（`BarState.restoreAfterWalk` + 两条新事件 `walk-hide` / `walk-restore`）
  - `src/main/index.ts`（`startManualPlay` / `endManualPlay` 各接一句）
  - `tools/status-arbiter.test.mjs`（第 ⑪b 节 + 结构性断言）
  - `spikes/m2-control/probe-control.js`（新增用例 ⑫c：**真实鼠标点击** + 走路收起/恢复）
- **修订**：**ADR 038 负面结论第 2 条**（"手动走路时面板会跟着移动 —— 未取得用户观感数据"）。
  现在数据取得了：**用户不接受**，改为"先收起、走完还回来"。

## 背景

ADR 038 交付后用户实测，提出：

> 「我想要在点击左走右走时，悬浮窗先消失再出现；也就是说，其他动作点击时，悬浮条保持不消失，
> 但在左走右走时，悬浮条会在移动过程中消失，等移动结束后再重新出现。」

这正是 ADR 038 负面结论里列出的三种改法之一（"走路时先收面板"）。

## 决策

### 1. 判据是"**这一下真的会移动窗口**"，不是"这个动作是不是位移姿态"

`beginManualPlay` 在两种情况下会把位移动作**降级成原地演**（贴着屏幕边缘 / 工作区比宠物还窄），
那时宠物一步都不动 ⇒ **没有任何理由收走面板**。所以收起的条件是
`res.play.targetX !== null`（= 真的会移动窗口），而不是 `action.facing !== null`。

### 2. 这份"待恢复"是**状态机里的一个状态位**，不是主进程里的一个布尔

它决定"面板要不要自己冒出来" —— 而"面板自己冒出来"正是 ADR 016 花过学费要根除的体验。
这类判断必须能单测，所以它和其他显示规则一起住在 `kernel/bar-policy.ts`（纯函数）。

**与悬停唤出的根本区别（别拿 ADR 016 来反对这一条）**：

| | 悬停唤出（ADR 016 删除） | 走路后恢复（本条） |
|---|---|---|
| 触发源 | 光标顺便掠过 = **无人触发** | **用户刚点了「左走」** = 显式动作的延续 |
| 体验 | "我没叫它它自己冒出来" | "我把面板收起来走两步，它回来接着给我用" |

### 3. 三条不变量（缺一条就有真实缺陷）

- **① 只有 `walk-hide` 能置位**，且**面板当时必须可见**。
  面板本来就不可见时不产生欠账 —— 否则走完会**凭空冒出一个面板**。
- **② 面板一旦可见，欠账即作废。** 用户自己把它叫回来了（右键宠物 / 托盘菜单），
  走完就不许再自作主张开一次。
- **③ 用户/环境明确要求它关着时，欠账也作废**（`pet-hidden` / Esc / ×）。

> **② 与 ③ 都是单测真抓到的，不是想出来的**：
> - 少了 ③：**走路期间宠物被隐藏**（托盘 / 全屏让位）⇒ 走完 `walk-restore` 会把面板
>   **开到半空**（宠物已经不在了）。单测报 `宠物被隐藏 ⇒ 欠账作废：期望 false，实际 true`。
> - 少了 ③ 的另一半：走路期间按 Esc / 点 × ⇒ 他刚关掉、走完又自动开一次 = "它自己冒出来"。
>
> ② 是先写下的规则（"可见即结清"），③ 是被单测逼出来的（"不可见时也要能作废"）。
> 这两条合起来才覆盖完整 —— 只写 ② 会漏掉"作废时面板恰好不可见"的那一半。

### 4. 顺带补上一个**从未验证过的面**：真实鼠标点击这个面板

新增用例 ⑫c 之前，探针点面板一律用 `b.click()`（**DOM 合成事件**），它**绕过 Windows 的输入路由**。
而 ADR 009 那条"`hide()` 之后系统不再把**真实鼠标按钮事件**路由到该窗口"，
在控制条上只被**键盘**路径验证过（ADR 016 实测的是 `keyDelta`）——
控制条恰好是"会接收按钮事件"的窗口，所以那一面一直是空的。
新需求让面板**自己 hide 再 show**，正好把它推进 ADR 009 描述的情形里 ⇒ 必须实测。

用例顺序刻意这样排：**先证明正常情况下真实点击有效（基线）→ 再走一次路（hide→show）→ 再真实点击一次**。
基线通过而复查失败 ⇒ 就是 ADR 009 在控制条上复现了。（结果：见 §实测。）

### 5. 焦点：恢复时**照旧抢焦点**

`syncBar()` 只有一条显示路径（`focus: true`），本项目"唤出一律抢焦点"（ADR 016 决策 2）
也就继续成立。理由：**走路前焦点就在面板上**（用户刚点了面板上的按钮），
走完还回来的正是"他原本在的位置"。代价是走路那 2–3 秒内如果他切去别的窗口打字，
面板回来会抢一次焦点 —— 概率低、打扰轻，如实记录。

（刻意不引入 `showInactive` 的恢复路径：那会新开一条未验证的显示分支，
而"面板显示时不带焦点会不会被 `focus(false)` 规则立刻收掉"在本项目没验证过。）

### 6. 走路期间**仍然可以**右键唤出面板

用户显式动作优先：面板会显示出来（欠账按不变量②作废），并且会继续跟着宠物走完那一小段。
没有为此加"打断走路"的规则 —— 重叠窗口只有 2–3 秒，不值得多一条规则。
（如实记为已知观感项。）

## 实测

- **单测**：361 → **391 项**全绿。第 ⑪b 节 30 项覆盖三条不变量的每个分支，
  含"走路期间 tick 不会让它冒出来"、"走路期间的失焦不丢欠账"、
  "面板本来就不可见 ⇒ 不产生欠账"。
- **真机探针** `spikes/m2-control` 用例 ⑫c：见本轮 journal 与 `control.json`。
  关键读数：走路中面板确实收起 → 宠物真的左移 → 走完面板自己回来且**重新居中** →
  **隐藏→显示之后真实鼠标点击仍然有效**（ADR 009 未在控制条上复现）。
- 结构性断言：`walk-hide` 只在 `targetX !== null` 时触发；`walk-restore` 在结束时触发；
  **宠物窗口标题必须保持 `desktop-pet`**（所有探针靠 `getTitle()` 找窗口，改了会让整套回归静默失效）。

## 负面结论

1. **恢复时抢焦点**是明确的代价（见决策 5），未做"不抢焦点"的版本。
2. **走路期间右键唤出面板会看到它跟着飘**（决策 6）—— 与 ADR 038 那条被取代的观感是同一个，
   只是现在只在"用户主动在 2–3 秒窗口里叫出面板"时短暂出现。
3. **状态机多了一个状态位与两条事件**。这是本轮唯一没有更省做法的部分：
   主进程里放一个布尔确实更少代码，但那样"面板会不会自己冒出来"就不可单测了，
   而它正是本项目最敏感的一条体验（ADR 016）。
4. **`restoreAfterWalk` 只在 `bar-policy` 内可见**，主进程不做二次判断
   （"有没有欠账"由状态机答）。这是刻意的：两处各判一次必然会漂移。
