# ADR 045：版本号什么时候跳 —— 「一次交付一个版本号」，Agent 主动定

- 日期：2026-09-23
- 状态：已采纳
- 相关：ADR 041（版本号定为 `1.0.0` + 唯一真源 = `package.json`）、ADR 043（减少动态效果冻结动画）、
  `AGENTS.md` 收工协议、`docs/changelog.md`

## 背景

用户问了三件事，问得很准：

> 那为什么这个版本不叫 1.0.1 呀？或者是更新一个版本号？从现在开始，之后每做一个事情，
> 应该是都要更新版本的？还是说我也需要手动说更新版本呢？因为我感觉这确实是一个 bug，你觉得是吗？

**先把账认下来**：上一轮（ADR 043 修"减少动态效果冻结动画"）**确实该跳 `1.0.1`，我漏了**。
理由是硬事实：`1.0.0` 那个 zip **用户已经分发给朋友了** —— 它已经"发布"了。
在这个版本上修掉一个用户可见的缺陷之后再产出构建，如果还叫 `1.0.0`，就会得到
**两个内容不同、却共用同一个版本号的文件**（朋友手上那个有 bug，你手上这个没有）——
而"同名不同物"正是版本号存在的意义所要消灭的东西。**这比版本号跳错更糟。**

所以本轮做两件事：把这一版改成 `1.0.1`，并把"什么时候跳"定成规则。

## 决定

### 一、跳号的判断标准：**对"发布过的版本"做了什么**

`1.x` 阶段（`MAJOR.MINOR.PATCH`）：

| 做了什么 | 跳哪一段 | 例 |
|---|---|---|
| **修 bug**（行为本来就是错的，现在对了；承诺范围不变） | **PATCH** | `1.0.0 → 1.0.1` |
| **加一个用户能看见的新东西**（新按钮/新动作/新配置项） | **MINOR** | `1.0.1 → 1.1.0` |
| **弄坏了 ADR 041 承诺范围内的兼容性**（`prefs.json` / 自启项 / sidecar 字段 / 分发结构 / 图集规格） | **MAJOR** | `1.1.0 → 2.0.0` |
| 文档 / 注释 / 单测 / 探针 / 内部重构 / 打包工具 | **不跳** | 用户看不到，也不影响任何承诺 |

**范围收窄还是放宽，本身就是信息**：比如上一轮把「减少动态效果」的作用域从"冻结一切动画"收窄成
"只停自主行为"，虽然改的是行为，但那是**修一个错的实现**（用户的显式操作本来就不该被那个开关吞掉），
所以是 PATCH；如果哪天是"我们决定新增一种全新的动画开关让用户选"，那才是 MINOR。

### 二、跳号的节奏：**一次「交付」一个版本号**，不是一次 commit 一个

- **触发点是"打包交付"**（= 用户会拿到新构建），不是 git commit。
  一次交付里攒了多件事就**按其中最高的那类跳一次**，不是每件事跳一次。
- 这也与既定交付纪律对上：**"凡是用户能看见的改动，做完就直接打包"** ⇒ 打包即发布 ⇒ 打包即定版本号。
- **没有交付就不跳**。中间那些零碎提交（改文档、补单测）不产生版本号。

### 三、谁来定：**Agent 主动定并说明理由**，用户不需要记

用户原话担心的是"是不是我也需要手动说更新版本"。**不需要。**

- 每次打包时，Agent **主动**判断该跳哪一段、把 `package.json` 改掉，并在交付说明里
  **用一句话给出理由**（"这次是修 bug ⇒ PATCH ⇒ 1.0.1"）。
- 用户只需要在**不同意**时推翻 —— 默认不需要做任何事。
- 判断有异议时以用户为准：**版本号是给人看的沟通工具，不是技术事实**。

### 四、发布要留痕：给发布提交打 tag

以前只改了 `package.json`，没有 tag ⇒ 事后想问"`1.0.0` 到底是哪一份源码"只能靠翻日志猜。
现在规则：**每次交付时，给当前 HEAD 打一个 `v<版本号>` 的轻量 tag 并推上去**。

- tag 名**不带斜杠**（`v1.0.1`，不是 `release/1.0.1`）—— 本机对"新建目录下的 ref"
  有过静默失败的历史（见 `PLAN.md` §3b 的 GitHub 段），不带斜杠最稳。
- 补记 `v1.0.0`：指向 `8c43505`（= `package.json` 首次写为 `1.0.0` 的那个提交）。
  ⚠️ 它是**追溯**打的，只能保证"版本号规则一致"，不保证与当时分发出去的那个 zip 逐字节相同。

## 判据

- `package.json` 的 `version` 是唯一手写处（ADR 041 已钉住），本轮改为 `1.0.1` 后，
  exe 版本资源 / 日志横幅 / 托盘菜单那行小字 / zip 名与 README **四处派生值全部跟着变**：
  实测 exe 报 `1.0.1`、横幅报 `启动 v1.0.1`、zip 名 `desktop-pet-1.0.1-win-x64.zip`。
- `git tag -l` 能看到 `v1.0.0` 与 `v1.0.1`；`git describe --tags` 在 HEAD 上给出 `v1.0.1`。
- 新增的这条规则写进 `AGENTS.md` 收工协议（第 6 条），否则下一个会话不会知道要跳号。

## 负面结论 / 边界

- **不采用"每次提交自动跳 0.0.x 流水号"**。那样版本号里就**不再包含"变了多少"的信息**，
  用户会看到一串无意义的号，也无法从版本号判断"我这版该不该升级"。流水号解决的是
  "唯一标识"问题，而这里需要的是"沟通"问题。
- **不采用日期版（CalVer）**。桌宠不是"固定周期发版、用户不关心兼容性差异"的东西（ADR 041 已述）。
- **`1.0.0` 已经出去了，不能收回**。它现在明确代表"**含『减少动态效果会冻结动画』缺陷的那一版**"，
  这是它唯一有意义的用途：**如果朋友回来说有问题，先问版本号** —— `1.0.0` = 旧缺陷，`1.0.1` = 已修。
- **这条规则不解决"该不该发"**。什么时候打包仍然由交付纪律决定（有用户可见改动就打），
  这里只回答"打出来的包该叫什么号"。
