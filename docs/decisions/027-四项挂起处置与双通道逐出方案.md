## 3. #4 `boot()` 949 行 → **改成"可导航"，不强行拆函数**

审查报告建议"拆三个装配函数，不改执行顺序"。**我没有照做**，理由（已写进 `index.ts` 的函数头注释）：

这些段落共享同一批对象（`overlay` / `arbiter` / `bubble` / `bar` / `prefs`…），且有**严格先后**
（快捷键必须早于托盘菜单注册，否则 `petMenuView` 读 `activeHotkey` 会踩 TDZ）。
拆成模块级函数就得把这批对象打包成一个 ctx 传来传去 —— 隐式耦合变成显式但更啰嗦，
而**启动路径的任何改动都要跑五套真实窗口回归**（全屏/托盘/控制条/行为层/状态）。

**实际做了什么**：
1. `boot()` 顶部加**装配索引**（①–⑪ 的职责与执行顺序），949 行从此可导航；
2. 分节标记统一为可搜索的 `═══` 格式；
3. 顺手修掉一处真实的小缺陷：`// —— 拖动 ——` 那行注释被前一段行尾"吞掉"了（两行注释粘连）。

**代价与收益**：行数几乎没变，但**定位成本从"滚 950 行"降到"看索引跳段"**。
真出现"某一段要被复用"的需求时再拆 —— 那时拆分有明确边界，不是为拆而拆。

判据：`npm run typecheck` 0 错、`npm run build` 0 错、`spikes/m3-latency/run.mjs` **PASS**
（启动路径探针：6/6 带 recvAt，延迟 100–114ms，与改动前一致）。

## 4. #2 双通道逐出 → **方案已定，下一轮实施**

用户："逐出的语义我不太明白，你可以自行决策和构思，只要符合我们的使用场景和习惯即可。"

### 决策：**按通道优先级仲裁，不按到达顺序**

| 选项 | 结论 |
|---|---|
| 后到者胜（现状的实质） | ❌ 这正是"来回刷"的机制，也是 ADR 022 那个缺陷的根因 |
| 先到者锁定 | ❌ 桌宠启动时往往先读到**快照**（被动源），会把它永久锁死，hook 永远进不来 —— 与意图相反 |
| **事件驱动 hook 优先于被动源** | ✅ 与 ADR 020 已定的"被动源是**降级来源**，是切换不是叠加"完全一致 |

### 规则

1. 每个 `sessionId` 记一个**主导通道** `dominantOrigin` + 最近上报时刻。
2. 事件到达时：
   - 没有主导通道 ⇒ 它成为主导通道，正常入仲裁器；
   - 同一通道 ⇒ 正常入；
   - **不同通道** ⇒ 比较优先级：hook（事件驱动）> 被动源（file / proma）。
     高者**接管**（成为主导 + 入仲裁器），低者**丢弃**（不入仲裁器，打一条日志）。
3. **锁会过期**：主导通道超过 `dominanceHoldMs`（默认挂钩 10 分钟）不再上报 ⇒ 释放，
   低优先级通道恢复生效。**这条是安全的底线** —— hook 挂了不会让宠物永久失明。
4. 参数放 `desktop-pet.json → statusSources.dominance`，可整体关闭（回到"只告警不处置"）。

### 为什么这样符合"我们的使用场景"

你的实际使用是 **WorkBuddy 走 hook、Proma（已冻结）走被动源** —— 这是**两个不同 agent**，
天然不冲突；会打架的是"同一个 agent 被两条通道同时盯"，而那种情况里
**hook 的信息一定比被动源准**（被动源只能给存在性，ADR 020 实测）。所以"hook 优先"就是正确答案。

### 判据（实施时写）

- 单测：hook 接管后被被动源上报不生效；被动源单独存在时正常；锁过期后被动源恢复；
  不同 sessionId 互不影响；关闭开关后回到只告警。
- 回归：`probe-ack-revival`（13→14/14）、`probe-ready-stale-boundary`（27/27）、
  `probe-stale-sessions`、`m2-status` 端到端。
