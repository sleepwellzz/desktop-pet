# ADR 043：系统「减少动态效果」只管自主行为，**不冻结动画**

- 日期：2026-09-23
- 触发：分发给朋友后回报的**跨机器行为差异**

## 症状（用户原话）

> 他的动作不管是在悬浮条里你点击哪个动作，都是一种静态图片的展示，并没有动起来。
> 左走右走也都是简单的图像平移。然后炒菜呢，就是一个站立不动的图，图片，贴图。
> 但是我给另一个朋友发他那边就是正常的，是可以运动的。

同一份代码、同一个 zip，两台机器两种表现。

## 排查：不是依赖问题

**先回答"是不是要什么系统环境或库"：不是。**

动画是纯 Canvas 2D + `requestAnimationFrame`，不依赖任何编解码库、不需要 GPU 特性、
不需要运行时安装任何东西。精灵图是 WebP，由 Chromium 自己解码 —— 图片**显示得出来**，
说明解码没问题（症状是"不换帧"，不是"画不出来"）。

真正的原因在 `src/renderer/renderer.ts`：

```ts
const reducedMotion = window.matchMedia?.('(prefers-reduced-motion: reduce)').matches ?? false;
...
if (player && !reducedMotion) player.update(dt);     // ← 帧推进被关掉
```

`prefers-reduced-motion: reduce` 读的是**操作系统设置**
（Windows：设置 → 辅助功能 → 视觉效果 → 动画效果）。那台机器把它关了，于是：

- `tick()` 不再调 `player.update(dt)` ⇒ `frameIndex` 永远停在 0；
- `setState()` **照样切行**（所以"炒菜"确实切到了炒菜那一格）—— 但只画第 0 帧
  ⇒ 用户看到的就是"一张站着不动的贴图"；
- 左走右走的**窗口位移**由主进程 33ms tick 驱动、与渲染无关 ⇒ 照样平移
  ⇒ 用户看到"平移但腿不动"。

三条症状全部吻合。

## 实测复现（本机，不用朋友的机器）

Chromium 有 `--force-prefers-reduced-motion` 开关，可以在本机精确模拟那台机器。
新写的判据 `spikes/motion/run.mjs` 直接采 **canvas 像素**做指纹（不是内部帧索引 ——
帧索引推进了但没重绘的话，用户看到的仍是静止，那是典型的"代理指标"陷阱）。

| | `matchMedia` | idle 循环（24 次采样） | 手动动作（running-left） |
|---|---|---|---|
| 修复前 · 正常 | false | 8 种画面 / 12 次变化 | 8 种 / 23 次变化 |
| **修复前 · 强制减少动画** | **true** | **2 种 / 1 次变化（`AABBBB…` 冻结）** | **1 种 / 0 次变化（`AAAA…` 完全不动）** |
| 修复后 · 强制减少动画 | true | **8 种 / 12 次变化** | **8 种 / 23 次变化** |

**并把缺陷打回去确认判据不是真空的**：把 sidecar 的 `strategy` 改回 `freeze-frame`
再跑一次，两轮都红、且序列精确重现 `AABBB…` / `AAA…`。

## 决策：把「尊重」的边界收窄

| 谁 | 要不要尊重「减少动态效果」 | 理由 |
|---|---|---|
| **行为层**（自动漫游 / 微动作 / 踱步位移） | **继续尊重**（ADR 018，本次不动） | 那是**它自作主张的运动**，用户没要求看，停下来是对的 |
| **动画播放**（业务状态 / 手动把玩 / 单击致意） | **默认不尊重** | 用户主动打开一个桌宠、还点了"炒菜"，却看到一张不会动的图 —— 这叫产品坏了 |

一句话：**「减少动态效果」的本意是减少它自作主张的运动，不是让它变成一块石头。**

配套三点：

1. 新增纯函数模块 `src/kernel/motion-policy.ts`：解析策略 + 持有判据 `shouldAdvanceFrames()`。
   **判据下沉到策略自己身上** —— 调用点会新增（`tick` / 状态迁移 / 单击致意），策略只有一个。
2. 兑现 sidecar 里那个**一直没被实现的** `reducedMotion.strategy`（以前注释假装读了它，
   代码里根本没读 —— 又一处"注释骗人"）。取值：
   - `animate`（**默认**）：动画照常；
   - `freeze-frame`：连状态动画与手动把玩一起冻住，只画 `frameIndex` 那一帧。
3. **启动日志必须打出这一行**，否则下次还是只能靠两台机器对照猜：
   ```
   [pet] 减少动态效果：系统开关=true｜策略=animate（动画照常（只停自主漫游/微动作））
   ```

## 反面意见（摆出来，不要只写对自己有利的）

`prefers-reduced-motion` 是无障碍规范，**确实有用户需要它**（前庭功能障碍等）。
把它从渲染层摘掉，等于这些用户少了一道保护。

为什么仍然这么做、并且保留 `freeze-frame`：

- 桌宠是**用户主动运行、以动画为核心**的应用 —— 不属于规范要抑制的"装饰性 UI 动画"。
- 但规范关心的那部分我们**没丢**：自主动画（漫游/微动作/踱步）继续尊重（ADR 018）。
- 确实想完全静止的人，**主动**在 sidecar 里写 `freeze-frame` 即可 ——
  门槛从"系统顺手一开就把产品弄坏"变成"明确选择"，这更合理。

## 附带发现：构建链在本环境的一个限制

`tools/run-build.cjs` 用 `spawnSync(node.exe, …)`，本环境下会间歇性报 **EBUSY**
（不是编译错误，是子进程起不来，表现为全步骤 1~4ms 就"失败"）。
本次用**进程内直接调 tsc / esbuild 的 JS API** 绕过（脚本在 `.workbuddy/build-inproc.cjs`，
步骤与正式脚本逐条对齐）。正式脚本不改 —— 那是环境限制，不是它的问题。
**下次遇到 BUILD FAILED 且耗时都是个位数毫秒，先怀疑这个，不要去改代码。**
