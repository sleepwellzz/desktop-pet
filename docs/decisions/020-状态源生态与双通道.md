# ADR 020 · 状态源生态：双通道架构、通道互斥与命名空间

- 日期：2026-09-18
- 状态：**已采纳**（实施中；判据 1/2/3/6/9 待真实回合验证）
- 相关：ADR 008（命中/穿透）、ADR 010（状态源抽象与仲裁器）、ADR 017（快照时间语义）
- 设计稿：`docs/design/m3-status-ecosystem.md`

## 背景

M2 打通了 `状态源 → 仲裁器 → 动画`，但只验证了**链路**，从未接过真实 agent
（PLAN §8 风险表里唯一还写着"仍待验证"的一条）。本轮把"链路通"升级为"真能用"。

用户在此过程中的两条关键输入改变了方案：

1. **目标 agent 不是 Codex，而是 WorkBuddy（主力）+ Proma（第二主力，Pi agent 架构）**。
2. **质疑"两个软件同时跑会不会冲突/叠加"**，并要求状态变化**延迟不能高**。

## 决策

### 1. 选 ⑦-b（状态源生态），不选 ⑦-c（宠物包工具链产品化）

⑦-c 的前置（素材导入流程 + 规格标准）绑定在 ADR 015 的重启条件②上，而该产品线用户尚未拍板；
⑦-b 直接对着风险表里唯一"仍待验证"的一条。**按风险排，不按功能好看程度排**（PLAN §4 的既有纪律）。

### 2. 架构是**两条通道**，不是"每个 agent 一套适配器"

| 通道 | 形态 | 覆盖 |
|---|---|---|
| **A · 事件驱动 hook** | agent 在生命周期事件上 spawn 我们的客户端，客户端读 stdin JSON 回写状态文件 | **WorkBuddy**（主）、Codex、将来的 Claude Code —— **三者是同一套事件名与 stdin 契约** |
| **B · 被动会话源** | 只读 agent 写在磁盘上的会话/心跳文件并归一化 | **Proma**（主） |

关键洞察：WorkBuddy 内嵌的 agent CLI 就是 **Claude 系的 hook 引擎**（同一份 14 事件表、同一个
`hook_event_name` 字段）。所以"将来支持 Claude Code"= 把同一份配置写到 `~/.claude/settings.json`，
**映射层零改动**。这让"多 agent 覆盖"从 N 份适配器退化成 1 份映射 + N 个配置路径。

### 3. **一个 agent 只由一条通道负责，两条通道互斥**（本轮新增的硬规则）

两个**不同**的 agent 各占一个 `sessionId`，天然不冲突；仲裁器本来就是多会话形状
（`pickPrimary` 按「优先级 → 非 idle → 事件最新者胜」，`badgeCount` 即气泡 `+N`）。

**真正会打架的是同一个 agent 被两条通道同时盯**：hook 说 `running`、被动源说 `idle`，
两边来回刷，且**没有任何报错**（2.3 节那条"症状不可解释"的典型）。
⇒ 被动源的角色是"该 agent 没配 hook 时的唯一来源"**或**"hook 失效时的降级来源"，
**是切换，不是并行兜底**。

### 4. `sessionId` 必须带来源前缀（`wb:<pid>` / `proma:<uuid>`），标题必须带来源名

不带前缀时，两个 app 的 UUID 万一相撞会互相覆盖 —— 概率低、后果是状态乱跳且难查。
标题带来源（`WorkBuddy · desktop-pet`）是因为气泡与控制条只显示一个标题，
两个 agent 同时在跑时分不清谁是谁。

**副产品**：用户"只想连某一个 agent"因此变成**一次按前缀过滤**，不是新机制 ——
可以做成 `desktop-pet.json → statusSources.{...}.enabled`，或控制条上的筛选项。

### 5. hook 配置只写**工程级**，且默认只写 `settings.local.json`

- **只写工程级**：用户级（`~/.codebuddy/`、`~/.workbuddy/`）会作用于用户**所有**会话，
  包括他正在跟我对话的那一个；工程级影响面可控、可 git 回滚。
  实测证实工程级**确实生效**（见下），所以这不是保守猜测而是有证据的选择。
- **`settings.local.json` 而不是 `settings.json`**：命令里含**本机绝对路径**（node 可执行文件），
  天然因人而异；PROJECT_LOCAL 就是为这个准备的，且已进 `.gitignore`。
  要入库的共享版留给 `--shared`，但先要确认命令能做成路径无关的。
- 安装器**默认 dry-run**，打印 diff 与影响面；`--uninstall` 只摘掉命令含 `pet-hook-cb.mjs` 的条目。

### 6. 客户端**退出码恒 0**

Claude 系 hook 的约定是 `2 = 阻断`。我们的客户端**只做观测，不该有能力拦住 agent 的任何动作**；
任何异常都吞掉并写 stderr。另有 10s 超时上限与 stdin 超时兜底。

### 7. `Interrupt` → `idle`，**不是** `blocked`

`blocked` 的动画是趴卧（"已受阻"）。中断是**用户自己按的停**，用它表达是在对用户撒谎。

## 实测结论（本机 2026-09-18；均为真跑，非推断）

1. **闸门：WorkBuddy 桌面确实会读工程级 hook 配置 ⇒ YES**。进程树显示
   `WorkBuddy.exe → daemon-app-server-entry.js → sidecar-entry.js → cli/bin/codebuddy --serve --session-id <uuid>`，
   且该 uuid 与 `~/.workbuddy/sessions/<pid>.json` 的 `sessionId` **完全一致**。
2. **设置作用域**：CLI 里 `DEFAULT_SCOPES = [USER, PROJECT, PROJECT_LOCAL]`，
   跑 agent 的进程**没带** `--setting-sources` ⇒ 工程级会被读。
3. **node 冷启动 ≈ 377ms**（5 次：359/384/369/396/376）⇒ 每次 hook 触发 = 一次进程启动，
   因此**工具级事件（`PreToolUse`/`PostToolUse`）默认不挂**。

## 负面结论（**这些比上面的正面结论更值钱**）

1. **"心跳秒级新鲜"是我的错误判断，已更正。** 我最初只看了一次文件的**当前年龄**（"它现在很新"），
   就写下"秒级"。151 秒 @1Hz 采样实测：心跳**只刷新 5 次 ⇒ 粒度约 30 秒**，且刷新与"在不在干活"无关。
   **教训：能推出"刚刚有人写过"，推不出"它一直在写"——判断一个信号的时间分辨率要看更新频率，
   不是看当前年龄。**
2. **`curl` 当 hook 客户端不更快，反而更慢**：冷启动 706ms（node 377ms），
   连本机未监听端口要 **2341ms** —— 正常路径更慢、失败路径慢 6 倍。这条推翻了"用原生二进制省时间"的直觉。
3. **WorkBuddy 的被动源只能给"存在性"，给不了"活动性"。** 逐项实测：
   `tasks/*/N.json` 窗口内 **0 次变更**（它是待办清单，不是活动指示器）；
   `file-history/`、`changes-index/`、`plans/` **0 次**；`projects/` 4 次、`artifact-index/` 2 次（太少）；
   `logs/` 有 105 次写入但内容是 `vendor-extract.log`、`weixinpay/*.xlog` 这类**应用级日志** ⇒ 噪声。
   **后果**：把它当 running 判据会制造**假阳性**（看起来像在工作其实没有），
   而假阳性恰恰是最不能接受的失败模式 ⇒ **通道 A 成为 WorkBuddy 的主路径，B 降为可选**。
   这条也**推翻了设计稿初版的执行顺序**（初稿把 B 排在 A 前面当"零风险的先赢"）。
4. **`--permission-mode fullAccess` 下不会弹审批** ⇒ 判据 3（`needs-input` 端到端）
   在本机当前配置下**验证不了**。届时如实记"未验证"，不用模拟顶替。

## 真实回合验证（2026-09-18，**判据 1 通过**）

配置落盘后，用用户真实的一条消息触发，hook 侧留下 5 条实测记录（`spikes/m3-status-sources/hook-payloads.jsonl`）：

| 时刻 | 事件 | 关键字段 |
|---|---|---|
| 09:48:10.490 | `PermissionRequest` | `tool_name: "Read"`、`permission_mode: "default"` |
| 09:48:10.979 | `PermissionRequest` | 同上（同一事件被派发两次，间隔 489ms） |
| 09:50:02.368 | `Stop` | 带 `last_assistant_message` / `background_tasks` / `session_crons` |
| 09:51:02.385 | `Notification` | **`notification_type: "idle_prompt"`**、`message: "CodeBuddy is waiting for your input"` |
| 09:52:48.966 | `UserPromptSubmit` | 带 `prompt`（用户原话） |

**结论 1 · 判据 1 通过**：hook 真的被派发；payload 完整；**含空格路径正常**
（命令里的两个绝对路径都没被 shell 截断 —— 这条本项目栽过一次，现在专门验了）。

**结论 2 · 三处证据交叉吻合**：payload 里的 `session_id` = 进程树里的 `--session-id` =
`~/.workbuddy/sessions/203516.json` 的 `sessionId`，**同一个值**。这三条独立来源一致，
说明"会话心跳文件 ↔ 真实 agent 进程 ↔ hook"是同一个会话。

**结论 3 · payload 比文档写的更丰富（实测优于文档的又一例）**：多了 `permission_suggestions`、
`permission_mode`、`client`（实测值 `"WorkBuddy"`）、`version`、`generation_id`、`model`、
`agent_type`、`background_tasks`、`session_crons`。
其中 **`client` 字段可以直接当来源标识用**，比我们硬编码 `--label=WorkBuddy` 更准。

**结论 4 · 我的一条预测被推翻**：我此前根据进程树里的 `--permission-mode fullAccess`
预测"不会弹审批，所以判据 3 验不了"。**实际 `permission_mode` 是 `"default"`，权限请求弹了两次。**
⇒ **判据 3（`needs-input` 端到端）是可以做的**，而且信号已经在手。

**结论 5 · 真实回合暴露了一个我自己的缺陷（已修）**：
`Notification` 我原本一律映射为 `needs-input`，而实测拿到的 `notification_type` 是 **`idle_prompt`**
（"干完了、在等你说话"）—— 它在 `Stop` 之后约一分钟必然出现。两条一起作用的结果是
**每次干完活宠物都会举手要你确认**，`needs-input` 这个最宝贵的状态会被**贬值**（用户开始习惯性忽略）。
修法：加一份**良性类型白名单**（目前只有 `idle_prompt`），命中的 `Notification` **不写状态**；
未知类型仍按"要你注意"处理（`PermissionRequest` 才是精确通道，`Notification` 是冗余通道，
宁可对未知保守也不漏真求助）。**这条只有跑真实回合才能发现** —— 单测写不出来，因为我当时
不知道有 `idle_prompt` 这个取值。

**结论 6 · 状态文件侧的结果正确**：

```json
"wb:ab2f75f8-9494-401f-b73e-01ad3286ae79": { "status": "running", "title": "WorkBuddy · desktop-pet" }
```

命名空间前缀与"标题带来源"都生效。同文件里还留着一条 8 月人工验收的 `default` 残留
（带 `ts`，会正常落进静默兜底，不影响）。

**尚未验证**：判据 2（状态序列对账）、判据 6（性能预算）、判据 9（会不会拖慢正常的活）——
**原因：验证时桌宠没有运行**（`tasklist` 里没有 electron 进程），宠物侧 `events.jsonl`
最后一条停在 2026-09-17T23:29，没有可对账的时间线。这三条必须**开着桌宠**再跑一次。

## 影响与后续

- **`pet-hook.mjs` 刻意未改**：它是人工验收入口（`喂状态.bat` 与多个探针依赖），
  搬走它的着力点会让一批回归失去意义。两个客户端写同一份快照与同一个 schema。
- 下一步（按修订后的顺序）：判据 1/2/6/9 的真实回合验证 → Proma 的采样探针 → Proma 适配器。
- 若判据 9（拖慢用户正常的活）不过，**砍事件集或整个弃用通道 A**，本轮以
  "映射层 + 客户端 + 一条明确的负面结论"收尾，不硬凑。
