# ADR 022 · 启动耗时归因与 `ready` 消解的双成因

- 日期：2026-09-18
- 状态：**已采纳**（启动优化方案待用户拍板；其余已落地）
- 相关：ADR 017（状态快照时间语义）、ADR 020（状态源生态与双通道）、ADR 021（状态↔动作复核）

## 背景

用户报告两件事：

1. **启动耗时明显增长，已达到数秒**；
2. **agent 任务完成后 `ready` 的炒菜动画始终保持，点击或确认后都不回待机**；
   并且悬浮条里仍显示"就绪但结果待确认"，希望**加一个「已确认」按钮**消除这种状态。

用户同时要求做一次工程级代码审查。

## 决定一：启动耗时归因 —— 瓶颈不在应用代码

**实测分段（`spikes/m3-startup/`，三次取样一致）**：

| 阶段 | 耗时 | 占比 |
|---|---|---|
| `npm run build`（无条件全量） | **29,941 ms** | **93%** |
| `npm start` 的 npm 引导 | 1,232 ms | 4% |
| Electron → 窗口可见 | 871 ms | 3% |
| **合计** | **≈ 32 s** | 100% |

`boot()` 内部时间线：283ms（app ready）→ 322ms（boot 进入）→ 605ms（boot 返回）→ 871ms（窗口可见）。
**应用代码合计只占 322ms**。

拆开构建链（`tools/run-build.cjs`）：tsc 3.3s + 6×esbuild ≈1.4s + copy-assets 0.6s ≈ **5.3s 有效构建**。
⇒ **29.9 秒里有约 24.6 秒是 npm 自身的解析/加载开销**（每次 `npm run` 都要重新解析 `package.json`
并加载 npm 的整个模块图）。

**为什么之前没发现**：启动耗时是**加总效应**，"每次启动都全量构建"这一条在 `.bat` 里是一行
看起来无害的 `call npm.cmd run build`；而每一处单独看都"几十毫秒，不像问题"。
为此新增 `--trace-boot` 接缝（生产路径零开销 —— 不开开关时 `bootMark` 是空函数），让每一处自己报数。

**暂不实施优化**：`启动桌宠.bat` 无条件构建虽慢，但换来"改完代码双击即生效"。
改为按需构建是**取舍**而非纯改进，需用户拍板。方案（三步，可分别验证）：
① 构建改按需（比对 `src/**` 最新 mtime 与 `dist/.build-stamp`）；
② 去掉 `npm start` 引导（直接 `node_modules\.bin\electron.cmd dist\main\index.js`）；
③ 开头打一行 `echo 正在启动…` 避免"双击后毫无反应"的错觉。
预计稳态启动 **32s → 2s 以内**。

## 决定二：`ready` 消不掉是**两个独立成因**，不是同一个

这是本轮最重要的一条 —— 两个成因的症状在屏幕上完全一样（"状态挂着消不掉"），
但机制、层次、修法全都不同。只修任何一条都不够。

### 成因一：面板谓词漏了 `ready`（渲染层）

`renderer/control-bar.ts` 的 `needsAck` 旧版只认 `needs-input`：

```ts
// 修复前
const needsAck = s.status === 'needs-input' && !s.acknowledged;
```

而内核 `ack()` 的 `want()`（`kernel/status.ts:316`）**早已同时覆盖两者**：

```ts
const want = (s: SessionRecord): boolean => s.status === 'needs-input' || s.status === 'ready';
```

⇒ `ready` 在面板上**既没有「确认」按钮、行也不可点**。用户看到状态一直挂着，却没有任何手段清掉它。
这是"同一判断在两处各写一份"的典型失配：**内核已经知道 `ready` 可确认，面板不知道**。

修法：谓词改为与内核 `want()` 一致，并加注释钉住这个一致性要求。

### 成因二：双通道交替反复撤销用户的确认位（内核）

`ingest()` 原判据按「状态字符串」记账：

```ts
if (e.status === 'needs-input' && prev?.status !== 'needs-input') this.acknowledged.delete(...);
```

看起来足够保守（"状态真的迁移了才清"），实测却会被 **ADR 020 明令互斥、但生产里确实发生过的**
双通道组合击穿：hook 通道写 `running`、被动文件源每 15–60 秒重报 `needs-input`
（`source/status-file.ts:202` 把"`ts` 变了"翻译成一条新事件）——
状态在两者之间来回跳，**每一次跳回 `needs-input` 都清一次确认位**。

生产证据：`~/.desktop-pet/events.jsonl` 357 条中绝大多数是同一会话的 `needs-input`、
`origin: "file"`、间隔 15–60 秒、持续数小时。

修法：把"确认"锚定在**求助的实例**上，而不是状态字符串上。新增 `reAskMinIntervalMs`
（默认 60s，`desktop-pet.json → statusTimeouts.reAskMinIntervalMs` 可配）：
迟滞窗口内的重报视为**同一次求助的续报**，不动确认位；只有间隔足够久的"重新举手"才再打扰用户。

**关键细节（不许动）**：**离开 `needs-input` 刻意不清除 `needsInputSince`**。
双通道交替正是靠"保留上一次求助时刻"才被挡住 —— 清掉它，每次切回 `running` 再切回来
就都算一次新求助，机制立刻失效。

## 决定三：控制条加「已确认」按钮（用户要求的功能）

动作排新增 `ack-all` 命令（`shared/ipc.ts` 的 `BarCommandId` 加成员 → 主进程
`barCommandHandlers` 查表执行 → 渲染层按钮）。多条待确认时文案为「全部已确认（N）」。

**语义与"单击宠物"完全一致**：都调 `arbiter.ack()` **不带参**。因此不引入新机制，
也不会在两处各写一份"什么算待确认"。行内「确认」按钮同时对 `ready` 出现。

## 负面结论 / 教训

1. **"状态没变"不等于"确认位安全"**。只要还有第二条通道能把它变走，就得按"求助实例"
   而不是"状态字符串"记账。原判据的推理（"没迁移就不清"）在单通道世界里是对的，
   错在默认了"状态字符串能代表一次求助"。

2. **探针的两次输入之间必须显式推进时钟**。情形 2b 首版在同一次钟值上连发两条 `ingest`，
   结果量到的是 500ms **限流窗格**而不是被测的**迟滞窗口** —— 与 M2 ④ 第一版探针
   "没先把宠物挪离右下角就测贴边"是**同一类判据不纯**。已写入审查报告作为探针通则。

3. **本次修复是症状级，不是机制级**。迟滞窗口把误报压到 60 秒一次，但**双通道本身仍然并存**。
   若上游重报节奏变化（例如某 agent 改成每 90 秒刷新），误报会以 90 秒周期回来。
   **ADR 020 的"一个 agent 只由一条通道负责"目前只有文档约束，代码里没有任何检查** ——
   这是当前最可能以"无报错、只是行为不对"形式复发的架构缺口。
   建议补：① 文件源侧按 `origin` 逐出已由 hook 负责的会话；② `ingest()` 检测同会话
   10 秒内来自两个不同 `origin` 时告警一次；③ 补一条双通道探针。

4. **本轮审查未发现 Critical 与安全漏洞**。总评 7.5/10。三条 Major（启动全量构建、
   双通道互斥无强制、谓词两处失配）与三条 Minor 见 `docs/reviews/2026-09-18-工程级审查.md`。
   受影响范围明确：`ready` 的两条成因**不影响 `needs-input`**（那条路径的面板谓词一直是对的），
   所以此前 M3 第三块的验收结论仍然成立。
