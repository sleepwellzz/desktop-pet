# ADR 013：气泡文字裁切与居中修正（兼"怎么量渲染结果"的方法结论）

- 日期：2026-09-16
- 状态：已采纳
- 关联：ADR 012（气泡层与全局快捷键）、`spikes/m2-hotkey/README.md`

## 背景

M2 ③ 的人工验收里，用户报了两条气泡的观感问题：

1. **文字下缘被切**（"每个字的最下方可能会被遮挡，未显示完整"）；
2. **文字没有居中**。

两条都是"看起来不对"，无法用逻辑断言直接判对错，所以先要解决的是**怎么量**。

## 决定

### 1. 文字下缘被裁：`line-height: 1` 是根因

原 CSS 是 `font-size: 13px; line-height: 1`，于是 `#text` 的行盒只有 **13px**；
而字体（雅黑 13px）自身的 ascent+descent ≈ **17px**。字形盒比行盒高约 4px，
上下各溢出约 2px，而 `#text` 与 `#bubble` 上都有 `overflow: hidden`
（**省略号 `text-overflow: ellipsis` 必需，不能去掉**），于是溢出的那部分被切掉。

改为 **`line-height: 20px`**：留出余量后裁切归零。实测见下表。

### 2. 文字没居中：flex 默认左对齐

`#bubble` 是 `display: flex`，默认 `justify-content: flex-start`；而气泡宽度是主进程
`estimateBubbleWidth()` **估算**出来的（中日韩按 14px/字），估算偏大产生的余量**全部落在右侧**。
实测左余量 0.00px / 右余量 3.39px —— 肉眼看就是"文字偏左"。

改为 **`justify-content: center`**，并给 `#text` 加 `min-width: 0`
（否则文本撑开盒子、省略号失效）。

### 3. 判据：量**渲染本身**，不要量字体公式

第一版判据用 canvas 的 `measureText()`：拿 `fontBoundingBoxAscent/Descent` 当字体度量、
按"半行距 + ascent"反推基线位置，再与 `actualBoundingBox*` 比出溢出量。
**它算出裁切 = 0.00px —— 与真实渲染不符（假阴性）。**

## 理由

- `line-height` 小于字体行高时，行盒与字形盒的关系是**排版引擎内部行为**，
  而"字体度量"在 canvas 与 Chromium 布局之间**并不一致**（hhea / OS/2 / usWin 的取值可能不同，
  再加上 hinting 与 DIP 取整）。用 A 引擎的度量去预测 B 引擎的像素，本身就是错的。
- 改为**差分取证**：同一帧给气泡窗口截两次图 ——
  ① 真实渲染（保留 `overflow:hidden`）；
  ② 注入一段 CSS 把 `overflow` 改成 `visible`。
  两次都用 `capturePage().toBitmap()` 取原始 BGRA，在 `#text` 的列带里找"亮像素"（近白 = 正文文字）
  的首次/末次行号，**差值就是被裁掉的物理像素数**，容差为 0。
  这个判据只依赖渲染结果本身，与字体、引擎、DPR 都无关。
- 只扫 `#text` 的列带，是为了避开右侧角标的白色 "+1" 干扰。
- 另加一条兜底断言：墨迹高度若小于字号的 0.7 倍，视为大面积裁切 ——
  防止有一天差分判据本身失效（两次截屏都没拍到字）导致"静默通过"。

## 实测证据（`spikes/m2-hotkey/`，DPR 1.5，文本「需要输入」+ 角标 +1）

| 指标 | 修改前 | 修改后 | 判据 |
|---|---|---|---|
| `line-height` | 13px（= font-size） | 20px | — |
| 墨迹行范围 | 19..37 | 20..39 | — |
| 关掉 `overflow` 后 | 19..**38** | 20..39 | — |
| **被裁（上/下）** | 0 / **1 物理像素** | **0 / 0** | 必须为 0 |
| **左右余量** | 0.00 / 3.39px | **1.69 / 1.70px** | 差 ≤ 2px |
| 探针判定 | FAIL | **PASS** | — |

同一轮其余项（快捷键真实击键触发、气泡 2 秒收起、needs-input 常驻、拖动跟随、
气泡工作期间宠物仍可点）保持通过。

## 负面结论（留给后续）

1. **不要用 canvas 的字体度量去推断 Chromium 的排版结果。** 两者不是同一套度量。
   要判断"有没有被裁 / 有没有对齐"，请量渲染结果本身（截屏差分），或量 DOM 的盒子几何。
2. **`overflow: hidden` 与 `line-height` 是一对陷阱**：省略号需要前者，
   而后者一旦小于字体行高，前者就会吃掉字形的上下缘。改字号时**必须同步检查 `line-height`**。
3. 平台/引擎的未文档化行为清单再加一条。本项目现有四条：
   隐藏→显示切断按钮事件路由（ADR 009）、`setPosition` 在 150% 缩放下逐次长 1 DIP（ADR 008）、
   探针读到上一次运行的残留日志（ADR 010）、**canvas 字体度量 ≠ Chromium 排版度量**（本 ADR）。

## 未做的事（有意）

- **不美化配色**（用户明确说本轮不处理：深灰底"可能有点丑"，以后再改）。本轮只修"错误"，
  不修"审美"。
- **不收紧 `estimateBubbleWidth()` 的估算**（CJK 按 14px/字略大于实际的 13px）。
  居中之后多出的余量左右平分、不再刺眼；真要紧再连同配色一起做。
