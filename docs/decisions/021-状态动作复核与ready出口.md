# ADR 021 · 状态↔动作全盘复核：映射不变更，改 ready 的出口与气泡定位

- 日期：2026-09-18
- 状态：**已采纳并实施完成**（设计经用户两轮确认，实施后全回归通过）
- 相关：ADR 002（资产契约与锚点）、ADR 010（状态源抽象与仲裁器）、ADR 013（气泡裁切与居中）、
  ADR 018 / 019（行为层）、ADR 020（状态源生态与双通道）
- 设计稿：`docs/design/m3-state-animation-audit.md`
- 取代关系：**本 ADR 取代任务书初稿 §1 的"`running` 改挂第 8 行"**；
  并**确认 2026-09-16 那条"`running` 保持映射到第 7 行"的决定继续有效**（该决定从未被真正推翻）
- 新增探针：`spikes/m3-ready-exit/`（真实窗口，验 `ready` 的通报时效真的让渲染层换帧）

## 背景

用户 2026-09-18 报告：*"我感觉现在宠物状态有点乱……在我打字的这个过程之中，
并没有任何 agent 在跑，但是它依然是小厨师在炒菜的这个动画状态。"*
要求先做一次「所有宠物状态的触发条件与对应关系」的全盘复核。

任务书初稿（`docs/design/m3-state-animation-audit.md` 的第一版）把用户另一句原话
*"我认为可以让小厨师的姿态一直保持为 Agent 在 running 的状态"*
解读为 **"`running` 应当改挂第 8 行小厨师"**，并据此准备了"取代 2026-09-16 旧决定"的说明。

## 决策

### 1. **不做这次映射变更。** 任务书初稿的解读前提是错的

用户在看到"如果你现在这个小厨师状态是 ready 的话，那你需要去看看 Running 有没有对应的动画"
这个追问后，自己更正了：

> *"是不是 Running 是那个过生日的动画呀？如果是的话，那就表明，Running 和 Ready 应该是分开了的。
> **是我自己记混了。**"*

**核实（实测，`docs/row-7-vs-8.png`，逐帧渲染对照）**：用户猜对了。

| 业务状态 | 动画 | 行 | 画面 |
|---|---|---|---|
| `running` | `running` | 第 7 行 | 派对帽 + 蛋糕（过生日） |
| `ready` | `waving` → `review` | 第 3 → 8 行 | 挥手 → 围裙 + 平底锅（小厨师） |

**两者本来就是分开的。** 用户最终要求是 *"只要你确保 running 和 ready 不一样就行"* ——
**现行映射已满足**。

⇒ 若按初稿实施，会把一个**正确的**映射改坏，且理由是错的。
**2026-09-16 的决定（`running` 保持第 7 行）继续有效**，从未被真正推翻 —— 归档留痕，不再讨论。

**一条方法论教训**（与既有纪律同源）：**用户对画面的描述必须用画面本身核实，不能用状态名反推。**
本次是"用户记混了 + 我据一句孤立原话起草了变更"，两边都没做那一步核对。
`docs/status-reference.png` 与新增的 `docs/row-7-vs-8.png` 就是为此存在的 —— 动映射前先看图。

### 2. 真缺陷是 **`ready` 没有出口** —— 一次 `Stop` 事件让它把姿态举到 15 分钟兜底为止

> **⚠️ 实施阶段的一处自我更正，比原判断更准确。**
> 本 ADR 的初稿（与任务书初稿）写的是"**落点被反复重走**"：每次 `ready` 都重播 `waving` →
> 落回 `review`，于是宠物周期性地重新挥手、再回小厨师。
> **实施前用真实仲裁器复跑，这个机制不成立**（见下方"实测更正"）。
> 保留这段是因为**错误判断的形状本身有价值** —— 它说明了"事件流证据"的陷阱。

#### 2.1 机制实况（实测更正）

用真实 `StatusArbiter`（虚拟时钟）跑三组场景，结论如下：

| 场景 | 观察 | 结论 |
|---|---|---|
| 一条会话报 `ready` 后静置 40 秒（每 250ms tick） | `rev` **一次都没变**，`animation` 恒为 `{waving, then:review}` | 仲裁器**不会**反复提交 |
| 别的会话报 `running` 再转 `idle` | 输出**不变**，仍是 `ready` | 其它会话也**不**扰动它 |
| `PetPlayer` 播完 `waving` 后每帧跑 `reconcileStatus` | 收敛到 `review` **并停住** | 渲染层**不会**反复重走 |

⇒ **`rev` 稳定、渲染层收敛稳定**。"落点被反复重走"在**稳定输入**下不成立。

#### 2.2 那为什么还会看到"一直在炒菜"？—— 真实成因有两个

1. **`ready` 没有出口（主因，本 ADR 的修复对象）。**
   一次 `Stop` 事件把会话置为 `ready` 后，**没有任何机制让它离开** ——
   要等 15 分钟静默兜底（`sessionStaleMs`）才轮到它。
   在这 15 分钟里宠物就一直摆着小厨师姿态、气泡写着"就绪（未读）"，
   **而用户手上确实没有任何 agent 在跑**。这正是用户报告的那句话。

2. **会话真的在 `ready ↔ running` 之间来回（次因，不是缺陷）。**
   `events.jsonl` 里 `wb:ab2f75f8-…` 就是这种形状：`ready →(345s)→ running → needs-input
   →(137s)→ ready →(570s)→ running → needs-input →(69s)→ ready → needs-input`。
   每次真正回到 `ready` 都重播一次 `waving → review` —— **这是正确行为**：
   状态真的变了，动画就该重播。把它当缺陷去"修"会改坏一个正确的机制。

#### 2.3 初稿的"事件流证据"错在哪（负面结论，值得记）

初稿引用的证据是：`wb:de8d4bad-…` **243 秒内 55 条事件、平均 4.5 秒一条、最长连续重复 40 次**。
重新按会话拆解后发现，那 55 条里 **50 条是 `needs-input`（78/82）**，`ready` 只有 **1 条**。
真实形状不是"`ready` 被反复重走"，而是"**`needs-input` 在密集重报**"（另一种现象）。

⇒ 纪律：**"某会话事件很密"推不出"某状态被反复重入"**。按会话、按状态拆开数清楚再下结论 ——
这次是"聚合后的直觉"替掉了"逐条核对"。

#### 2.4 修法：给 `ready` 一条到点退场的规则

`ready` 与 `needs-input` 的**形状不同**，所以不能用同一套：

| | `needs-input` | `ready` |
|---|---|---|
| 语义 | "它挡着路，非你不可"（**求助**） | "干完了，结果给你看"（**通报**） |
| 已有机制 | 粘滞 + `stickyTimeoutMs`（5 分钟）安全阀 | **无** ← 缺陷 |
| 应有出口 | 用户确认 / 超时 | 用户确认 / **时效到期** |

实现（`src/kernel/status.ts`）：

- `ArbiterOptions.readyTimeoutMs`（默认 **60 秒**），从宠物包 `statusTimeouts.readyMs` 读；
- **只在状态真正变成 `ready` 的那一次**记时（`readySince`）——
  用 `SessionRecord.ts` 算会踩坑：`ts` 每次心跳都刷新，拿它计时会让"上游每分钟重报一次 ready"
  变成永久驻留，**也就是这条机制在自己要防的场景下恰好失效**；
- `effectiveStatus(rec, now)` 里把超时的 `ready` 视为 `idle`（与已确认的 `needs-input` 同一条路）；
- **`ack()` 也消解 `ready`**：单击宠物在两种状态下都是"我看到了"的意思。
  实现是"把计时推到已超时"而不是删掉 —— 删掉会让判定退回 `rec.ts`，而它可能刚被心跳刷新，
  于是"确认"在下一秒被撤销（症状：点完宠物，姿态过一会儿又回来）；
- `SessionView` 加 `expired` 字段（与 `acknowledged` 同一套路：**原始 `status` 不改**，
  另给标记让面板决定怎么显示）。

**取 60 秒的理由**：足够用户切回窗口时看见"它刚才干完了"（气泡 6 秒是**逐字阅读**用的，
姿态是**余温**，可以长得多），又不会久到变成噪音。

#### 2.5 一条旁证（初稿已写，仍成立）

气泡对 `ready` 只显示 6 秒（`bubble.holdMsByStatus.ready = 6000`）就收起，
宠物却停在那一格 —— 同一状态两种表达不一致。**通报时效把两者重新对齐**：
气泡先收（文字看完了），姿态随后收（余温散了）。

### 3. 第 5 行趴卧的语义挤压：气泡改常驻（用户拍板）

用户答复：*"我觉得打盹也可以放作是宠物在日常休闲之中的一个动画之一。
但是它和 Block 的区别是在于 Block 的时候呢，宠物在打盹的样子上面应该出现文字提示。"*

⇒ **这就是"靠文字提示区分"的原则，已按它实施**：把 `blocked` 从定时气泡改到
**常驻**（与 `needs-input` 同规格）。

**为什么必须常驻**：此前 `blocked` 的气泡 4 秒后收起，**收起之后两种含义在画面上重新变得
不可分** —— 用户看到的就是"它趴下了，但不知道是累了还是出事了"。
打盹仍然无气泡，那才是"没事"的默认样子。

配置改动（`desktop-pet.json`）：

```diff
- "stickyStatuses": ["needs-input"],
- "holdMsByStatus": { "idle": 0, "running": 2000, "blocked": 4000, "ready": 6000 },
+ "stickyStatuses": ["needs-input", "blocked"],
+ "holdMsByStatus": { "idle": 0, "running": 2000, "ready": 6000 },
```

**顺带澄清一处任务书漏掉的事实**：`blocked` **不是**"权限审批"。
权限审批是 `needs-input`（第 6 行 `waiting`，来自 `PermissionRequest`）；
`blocked` = "已受阻/失败"（趴卧 8 帧，来自失败类信号）。
**触发条件列已补进设计稿 §2 的表** —— 此前那张表缺这一列，是"是否对应"看不出来的原因之一。

### 4. 气泡定位缺陷：已修 —— 根因是"把未知当成已知"

`src/host/bubble-layer.ts` 的 `if (!lastPetBounds) lastPetBounds = win.getContentBounds()`
**把气泡窗口自己的矩形当成了宠物矩形**；而 `main/index.ts` 调 `bubble.show(text, badge)`
时**根本没传宠物位置** ⇒ 启动后第一次推气泡必然走这条兜底。

**与 ADR 017 那条"没有 `ts` 不等于刚刚"是同一类错误**：兜底值取了一个**看起来像但不等于**的东西。

**修法（已实施）**：宠物矩形**显式传进** `show(text, badge, petBounds)`；
宠物窗口已销毁时**选择"不显示"，而不是"显示在错的地方"**。

**先例可直接引用**：`src/host/control-bar.ts` 的 `place()` 里同样面对"宠物矩形未知"，
写的是 `if (!pet) return;` —— **它选择的是不显示，所以它没有这个 bug**。
两个窗口面对同一个问题、一个写对一个写错，正好互为例证。

**实测取证（`spikes/m2-hotkey`，同一探针改前 / 改后各跑一次）**：

| | 气泡首次显示位置 | 说明 |
|---|---|---|
| 改前 | `798,446` | 屏幕正中偏左 —— 与宠物（`1549,857`）**毫无关系** |
| 改后 | `1561,809` | 正贴在宠物正上方（宠物 `1549,857`，气泡高 38 + 间距 10） |

改前那个 `798,446` 只在第一次拖动宠物后才被 `followPet` 纠正到正确位置 ——
即**"启动后到第一次拖动之间，气泡一直在错的地方"**。

## 实测结论（本机 2026-09-18，均为真跑）

1. **九行素材占用已逐行核实**（含行为层引用）：
   第 1、2 行是"位移姿态"（`role` 推导）；**第 5 行被 `blocked` 与打盹共用**；
   第 7 行由 `running` 使用；第 8 行是 `ready` 的落点。第 0、3、4、6 行各自独占。
2. **"落点被反复重走"经复跑被推翻**（见 §2.1）：
   稳定输入下仲裁器 `rev` 不动、渲染层收敛不动。真缺陷是"`ready` 没有出口"（§2.4）。
   ⇒ **初稿的事件流证据是聚合后的误读**（§2.3）。
3. **`ready` 的通报时效在真实窗口上已验证**（`spikes/m3-ready-exit`，PASS）：
   `0.1–0.5s` 画第 3 行（挥手）→ `0.6–4.2s` 画第 8 行（小厨师）→ `4.3s` 起画第 0 行（idle）。
4. **气泡定位改前 / 改后各跑一次同一探针**（`spikes/m2-hotkey`）：
   改前首次显示在 `798,446`（屏幕正中），改后在 `1561,809`（贴着宠物正上方）。
5. **快照里有 3 条 `needs-input` 历史会话**（`wb:ab2f75f8` / `wb:default` / `wb:de8d4bad`）
   会争主状态（`needs-input` 优先级最高）⇒ **做行号观察前必须先「清空状态会话」**，
   否则量到的是别人的状态。这是"判据必须只让被测的那条规则生效"的又一例。
6. **`wb:default` 已核实为"历史人工验收残留"，不是缺陷**：
   该桶 114 条事件的 `origin` 全是 `file`、`title` 全是 `manual-acceptance`，
   跨度 39 小时（`--clear` 之前的所有 `喂状态.bat` 记录都落在这个共享桶里）。
   ⇒ 初稿"疑似缺 `session_id` 落共享桶"的猜测**不成立**（至少当前证据不支持）。

## 负面结论（比正面结论更值钱）

1. **"用户对画面的描述"必须先核对画面再动手。** 本次用户记混了 running 与 ready 的动画，
   而我据一句孤立原话起草了一次**会改坏正确映射**的变更。两边都跳过了"看图"这一步。
   ⇒ 纪律：**动 `statusMap` 之前，先把 `docs/status-reference.png` 与
   `docs/row-7-vs-8.png` 打开对照**，不要凭状态名或凭一句原话推断外观。
2. **"事件流很密"推不出"某状态被反复重入"。** 初稿看 `wb:de8d4bad` 243 秒 55 条就断定
   "`ready` 落点被反复重走"；按会话按状态拆开后，那 55 条里 50 条是 `needs-input`、
   `ready` 只有 1 条。**聚合后的直觉替掉了逐条核对**，差点照着一个不存在的机制去改代码。
   ⇒ 纪律：**判断某机制的形状前，先按它自己的维度把数据拆开数清楚。**
3. **同一份兜底逻辑，两个窗口写对了一个**：气泡层与控制条都面对"宠物矩形未知"，
   控制条 `if (!pet) return;` 写对了，气泡层拿自己的矩形顶上。⇒
   **排查同类缺陷时，先去兄弟模块找"同一个问题的正确写法"**，比从零推理更快。
4. **`loop: true` 本身不是 bug。** 它是表属性（循环态不会自己退出），
   真正的伤害来自"上游是否反复把它重走一遍"（行为属性）。
   两者混为一谈会得出"把所有循环态都加出口"这种会改坏 `idle` 的结论。
5. **只跑 `tsc` 不足以跑真实窗口探针。** `tsc` 只产出未打包的 `preload.js`，
   而 preload 是 esbuild 打包的 —— 漏掉 `npm run build:preload` 会得到
   `Unable to load preload script: module not found`、"0 个采样点"，
   **看起来像探针逻辑坏了，其实是构建不完整**。（已写进 `spikes/m3-ready-exit/README.md`。）

## 影响与后续

- **`statusMap` 本轮未改**（§1、§2 的修法都不在映射行上）——设计稿 §4 判据 5 预判的
  "会打破的断言"**实际只打破了 1 条**（气泡策略里 `blocked` 的 4 秒定时），已同一轮改掉。
  `ready.then = review` 与 `running → running` 两条**都没动**，相关断言原样通过。
- 本轮改动落在四处：
  ① **`ready` 的出口**（`kernel/status.ts` 的 `readyTimeoutMs` + `readySince` + `ack` 扩展）；
  ② **`blocked` 气泡常驻**（`desktop-pet.json` 的 `bubble.stickyStatuses`）；
  ③ **气泡定位**（`host/bubble-layer.ts` 签名加参数 + 兜底改为不显示）；
  ④ **探针接缝 `--ready-ms`**（`main/index.ts`，与 `--no-behavior` 同一套路）。
- `tools/make-row-compare.py` 与 `docs/row-7-vs-8.png` 是本轮新增的**常备资料**：
  换宠物包后需与 `docs/status-reference.png` 一起重新生成。
- **待单独处理**：`spikes/m2-hotkey` 的快捷键判定（既有环境问题，见"回归结果"）。
