# ADR 035：退出必须清掉所有定时器，且这件事要由机器守住

- 日期：2026-09-22
- 触发：用户在便携版点「退出宠物」，弹出 `A JavaScript error occurred in the main process / Uncaught Exception: TypeError: Object has been destroyed`
- 结论：定位到两条**从未登记句柄**的定时器；修复后加了静态检查，让它不可能再复发

---

## 1. 症状与人话版本

用户点了「退出宠物」，宠物确实退了，但**中途崩了一下并被 Electron 抓到弹了框**。

Electron 报 `Object has been destroyed`，意思是：有代码拿着一个**已经被销毁的窗口对象**还在用它。

**这个值多少钱**：宠物确实退了，功能不受影响，但每次退出都弹一个技术性错误框 —— 对一个天天驻留的小工具来说，这是很差的观感，而且它会让人怀疑"这软件是不是坏了"。

## 2. 这个 bug 其实早就被抓到过，然后被我们放过了

```text
spikes/m2-menu/run-tray.out:
  [probe] 调 actions.quit()
  [pet] 用户从菜单退出
  [uncaught] TypeError: Object has been destroyed        ← 就是这个
  ✅ 退出用例通过：pid=202748 已消失                      ← 判它通过了
```

探针**记录了这个异常**，但仍判"通过"。当时的处置写在 `quit()` 的注释里：

> 探针日志里那行噪音就是它

⇒ **把用户可见的崩溃降级成了"日志噪音"**，于是它一路走到了用户面前。

这是本项目「判据不纯」的第六次、也是代价最直接的一次。

## 3. 根因：两条定时器的生命周期越过了窗口

`boot()` 里有两组定时器，语义完全不同：

| 定时器 | 周期 | 归谁管 | 隐藏时要停吗 |
|---|---|---|---|
| 33ms 行为层 / 16ms 光标轮询 | 高频 | `timers` 对象 + `startTimers/stopTimers` | **要**（省 CPU） |
| **仲裁推进** | 250ms | **谁都不管**（裸 `setInterval`，句柄当场丢弃） | 不要（藏起来也要推进粘滞超时） |
| **全屏监听** | 600ms | **谁都不管**（`startFullscreenWatch` 返回的 dispose 没人接） | 不要（藏起来也要让位） |

`stopTimers()` 只清得掉第一组。**第二组从头到尾没有句柄，谁也停不了它。**

退出时的时序因此变成：

```
stopTimers() → tray/bubble/bar.destroy() → app.quit()
              → 窗口关闭销毁
              → 250ms / 600ms 的下一次 tick                    ← 还活着
              → overlay.browserWindow.webContents.send(...)    ← 作用在已销毁的对象上
              → TypeError: Object has been destroyed
```

**最确定的崩点是全屏回调里的那次 send**：它没有 `isDestroyed()` 守卫。
（`pushStatus()` 早在 296 行就有守卫 —— 有守卫的没崩，没守卫的崩了，这条对比很能说明问题。）

**一句话教训**：**定时器的生命周期必须和它要碰的对象的生命周期对齐。**
否则就是"对象已经死了、定时器还在撞它"，而且只在退出这种一次性路径上暴露。

## 4. 修复：机制级，不是症状级

1. 新增 `processTimerDisposers`（登记"进程级"定时器）+ `stopProcessTimers()`，两条都进去；
2. `quit()` **和** `will-quit` 都要调它 —— 后者是给"自检截图那个 quit 分支"和 `window-all-closed` 兜底，
   它们不经过菜单动作；
3. 全屏回调加 `isDestroyed()` 守卫 —— 最后一道防线，因为崩溃让用户看见最糟；
4. 渲染层控制条那条 1s 的相对时间刷新，也接住句柄并在 `beforeunload` 清理。
   **说清楚它并不是这次的崩溃源**（渲染层的定时器随页面销毁，而主进程的那两条不会），
   只是它会被新规则判出来，与其加白名单，不如补上。

## 5. 让它不可能再复发：`tools/check-timers.mjs`

这个缺陷是**竞态**的 —— 退出到进程真正结束还剩 0~N 毫秒，残留定时器能否抢到一次 tick 全看运气。
本轮尝试了三种确定性复现手段，**全都失败了**：

| 手段 | 为什么不行 |
|---|---|
| 在 `will-quit` 里同步忙等 1.5s | **忙等会把事件循环锁死**，定时器一次都不会执行 —— 适得其反 |
| `process._getActiveHandles()` 数残留 interval | Electron 主进程里这组句柄不可靠，before/after 都是 0，没有区分度 |
| 覆盖 `app.quit` 留出异步观察窗 | 进程会被 Electron 卡在半死状态，`process.on('exit')` 都来不及落报告 |

（另外两个附带踩到的小坑：Electron 必须带着同级 `resources/` 才能启动，单独拷一个 exe 会
"什么都跑不起来且毫无报错"；`electron <app>` 只吃**一个**参数，给多了脚本会被当 argv 忽略。）

**但它一定得被拦住。** 所以在代码层面它是一眼可见的 —— 定时器的句柄没被接收。那就把它变成机器判据：

> 规则一：裸语句的 `setInterval(...)` 直接失败（必须赋给变量或登记）。
> 规则二：`startXxxWatch(...)` 这类返回 dispose 的调用，返回值必须被接住。

- 只扫 `src/`（产品代码）；`spikes/` 是可丢的探索脚本，让它们遵守产品规范只会让人不敢做实验。
- 挂在 `tools/status-arbiter.test.mjs` **第 ⑳ 节**，跟 313 项断言一起每次必跑。
- 也提供 `npm run check:timers` 单跑。

## 6. 顺手修掉的判据

`run-tray.mjs` 的退出用例原来只核对 **PID 是否消失**。进程崩了也一样会消失 —— 这正是 §2 那次漏判的原因。
现在它会同时扫描日志里的 `[uncaught]`：

```
❌ 退出用例失败：进程是退了，但**退出途中崩了 N 次**
```

**这条原则要记住：结果指标（进程没了）不能替代过程指标（怎么没的）。**

## 7. 判据与诚实的边界

- 构建 OK｜定时器静态检查 ✅｜单测 **313/313**（新增第 ⑳ 节）｜托盘探针 PASS 且日志零 uncaught。
- **没有做的事**：没能构造出"修复前有、修复后没有"的确定性复现（原因见 §5）。
  所以对这次修复的证据链是：**机制清楚 + 用户亲历 + 历史探针日志佐证**，不是"我复现过"。
  ⇒ **勇敢说出来，别把"测过了"说成"证明过了"。**
- 真正的终局判据仍然在用户手上：双击新版便携版，点几次「退出宠物」，看有没有错误框。
