# ADR 009：全屏让位后"输入通路失效"——隐藏/显示会切断鼠标按钮事件的投递

- 日期：2026-09-15
- 状态：已修复并实测验证
- 影响文件：`src/host/overlay-window.ts`、`src/main/index.ts`、`src/shared/ipc.ts`、`src/renderer/renderer.ts`

## 1. 现象

人工复验：启动后一切正常（宠物可拖动、可单击、死区很小），但**只要触发一次全屏**（视频全屏 / F11），
宠物让位再回来之后**就再也无法拖动**，单击同样无效。可稳定复现，且不复原——直到重启应用。

## 2. 复现

探针 `spikes/m2-hittest/probe-fs-verify.js`：用**独立进程**（`fs-child.js`，另起一个 Electron
开全屏窗口）触发**真实**的全屏让位路径（`detectFullscreen` → `hide()` → 退出后 `show()`），
再用 `mouse_event` 注入真实点击。

**最小复现**（不需要真全屏）：直接 `win.hide()` + `win.showInactive()` 即可 100% 复现。

**症状的精确描述**（这是定位的关键）：隐藏/显示之后，鼠标**移动**事件仍能进入渲染层，
**按钮**事件进不去 —— 注入的 `pointerdown` 计数恒为 0。

## 3. 排查过程（每一步都是实测，不是推断）

| # | 假设 | 实测 | 结论 |
|---|---|---|---|
| 1 | 坐标映射错位 | 把主进程发下的 hint 载荷与"按 `getContentBounds` 推算的期望客户区坐标"逐点比对，偏差 0 / 0.2 px | 排除 |
| 2 | Chromium 认为页面不可见而丢弃输入 | `document.visibilityState` 全程 `visible`，`hidden=false` | 排除 |
| 3 | 窗口几何异常 | 内容区 144×156@(1539,847)、物理 216×234，隐藏前后完全一致 | 排除 |
| 4 | 我们自己的状态机坏了 | 光标移开/移回，`WS_EX_TRANSPARENT` 仍精确随光标切换 | 排除 |
| 5 | 窗口收不到事件 | `SendMessage(hwnd, WM_LBUTTONDOWN)` 直接发给顶层 HWND → 渲染层**能**收到 `pointerdown` | **窗口本身能收，坏的是 Windows 对真实输入的路由** |
| 6 | 某个补救动作能修 | 逐个试：`EnableWindow(false→true)`、`webContents.focus()`、重设 alwaysOnTop、opacity 抖动、`blur()`、`invalidate()`、再 hide/show、再 `showInactive()`、`setBounds(getBounds())` | 全部无效 |
| 7 | 位置/尺寸 nudge 能修 | 某些时机有效（remedy 矩阵里 3 个动作成功），换一次实验又失败 | **不可靠，不能依赖** |
| 8 | 重建渲染层能修 | `webContents.reload()` | **稳定有效** |

第 7、8 条的差别是本轮最关键的发现：**nudge 是否生效取决于时机，而重载渲染层每次都生效。**

### 干净实验的完整记录（`spike/m2-hittest/probe-clean.js`）

全程不直接调用 `setIgnoreMouseEvents`，避免污染应用的内部记账：

```
1 基线（光标在宠物上）        → ✅ 进得去
2 hide + showInactive 之后    → ❌ 进不去
4 光标移开再移回              → T 精确切换（应用逻辑完全正常）
5 一次真实 nudge              → ❌ 无效
6 webContents.reload()        → ✅ 进得去
```

> 教训：探针在应用运行期间直接调 `setIgnoreMouseEvents` 会打乱应用的记账，
> 使后续结论失真。本轮为此重做了一次干净实验才拿到上面的数据。

## 4. 决策

1. **窗口重新显示后重新加载渲染层页面**：`overlay.reload()`（`hide→show` 的恢复分支里调用）。
   页面重载后 `CH.ready` 会再次触发，主进程复用缓存的 init 载荷重新下发。
2. **重载后的 ready 流程做两件事**：`overlay.resetToIgnore()` 把命中状态无条件归零对齐，
   `pushPointerHint(true)` 强制渲染层立刻重报一次命中状态（`PointerHint.force`）。
   为什么必须强制：渲染层"与上次相同就不上报"的缓存会让状态卡在穿透态。
3. **去掉 `setIgnoreMouseEvents(..., { forward: true })` 的 `forward`**：实测转发根本不生效
   （渲染层收到 0 次 forward 来的移动事件），而且它会额外带上 `WS_EX_LAYERED`，少一个变量。
4. **创建后用一次 `setContentBounds` 归一化**：顺带消除了实测到的
   "Chromium view 148×160 vs 窗口内容区 144×156"的 4 DIP 错位（现 `innerWidth` = 144）。
5. 渲染层补 `pointercancel` 处理（拖动过程中被隐藏会让 `dragging` 永久卡住，
   之后所有 hint 都被 `if (!dragging)` 挡掉 —— 同类症状的第二条路径，一并堵掉）。

## 5. 验证（`probe-fs-verify.js`，两轮，外部全屏进程）

| 轮次 | 阶段 | 单击（pointerdown） | 拖动（窗口位移） |
|---|---|---|---|
| 1 | 全屏前 | 1 ✅ | dx=-270, dy=-200 ✅ |
| 1 | 全屏后 | 1 ✅ | dx=-270, dy=-200 ✅ |
| 2 | 全屏前 | 1 ✅ | ✅ |
| 2 | 全屏后 | 1 ✅ | ✅ |

第 2 轮同样全过 → 无累积劣化。日志中可见恢复时渲染层重新取到精灵图。

**回归**：`probe.js` 命中区域 误吃 0 / 漏吃 2（与修复前一致）；自检截图 216×234、
宠物 152×219 物理像素、两帧姿态不同。

## 6. 代价与已知限制

- 每次全屏恢复会重载一次渲染层页面：约 100~300ms 的空白后宠物重新出现。
  用户刚从全屏退出，不构成观感问题。
- 重载会把动画状态重置回 idle 第 0 帧，无副作用。
- **未查明** Chromium / Windows 内部究竟是哪一层缓存了这个窗口的输入路由。
  因此这里用"重建渲染层"这个**可靠动作**绕过，而不是解释它。若将来有更好的办法
  （如 `SetWindowRgn` 或改用非分层方案），应替换本条并回来修订本 ADR。

## 7. 负面结论（避免重复交学费）

- `hide()` → `showInactive()` 会切断**真实鼠标按钮事件**的投递，而 `SendMessage` 不受影响。
  以后遇到"点不动"，先用 `SendMessage(WM_LBUTTONDOWN)` 区分"Windows 路由问题"还是"进程内处理问题"。
- 位置/尺寸 nudge 类补救**不可靠**（不同时机结果不同），不要写进产品代码。
- 判断"点击最终归谁"依然只能靠真实注入点击（`WindowFromPoint` 在分层窗口上返回 null）。
