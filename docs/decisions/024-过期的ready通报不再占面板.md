# ADR 024：过期的 `ready` 通报不再占面板（挂起清单 #14）

- 日期：2026-09-18
- 状态：已实施
- 关联：ADR 021（`ready` 通报时效 / 「要求注意」类状态必须有出口）、ADR 023（挂起清单清账）
- 触发：用户答复"如果你觉得是 bug，就修复"，本 ADR 记录**判定为 bug 的依据**与修法边界

## 0. 结论

**是 bug**，已修。修法：`viewSessions()` 过滤掉"`ready` 且通报时效已过"的会话。
**只过滤视图，不删记录**。

## 1. 现象

上游（状态文件源）持续重报 `ready` 时，60 秒通报时效到点后：

- 主状态**正确**回 `idle`（宠物不再摆"小厨师"姿态，ADR 021 那条修好了）；
- 但控制条面板上**仍留着这一行**，标注「（已过期）」，且**长期不消失**。

## 2. 判定为 bug 的三条依据

1. **ADR 021 的"出口"原则只落地了一半。** 该原则的字面要求是「要求注意类状态必须有出口」；
   实现上只改了仲裁输出（宠物回待机），没改面板视图。一条"已经结束的通报"继续占着面板，
   等于**出口没走到视图**。
2. **这一行没有任何出口，连手动的都没有。** `isAckable()` 对已过期的行返回 false
   （不给「确认」按钮是刻意的、也是对的 —— 宠物都回待机了再给按钮是误导），
   于是用户**唯一**能让它消失的手段是：等上游 15 分钟不心跳（触发静默兜底），或手动「清空状态会话」。
3. **而"等 15 分钟"在生产里永远不会发生。** 生产实测：文件源条目每 15–60 秒重报一次，
   重报刷新 `r.ts`，而静默兜底判的正是 `ts` 的年龄 ⇒ **这一行事实上永久驻留**，
   期间还一直撑高面板（面板高度随行数 72↔128 DIP）。

## 3. 为什么不选另外两个选项

| 选项 | 否决理由 |
|---|---|
| **保持现状** | 见 §2：一个没有出口、还会长期撑高面板的常驻行。 |
| **过期即删记录**（视为会话结束） | 会造成**周期性复活**：记录没了 ⇒ 上游下次重报 `ready` 时 `prev` 不存在 ⇒ `readySince` 被重设 ⇒ 宠物又炒 60 秒菜。比现状更糟。 |
| **让 `isAckable` 对过期行返回 true**（给个按钮让用户点掉） | 用户点"确认"一条已经结束的通报，语义上是撒谎；而且要求用户手动清理本该自动结束的东西。 |

## 4. 修法与边界

```ts
// kernel/status.ts · viewSessions()
.filter((r) => !(r.status === 'ready' && this.effectiveStatus(r, now) !== 'ready'))
```

- **范围窄**：只针对 `ready`。`idle` / `running` / `blocked` / 已确认的 `needs-input`
  一律不受影响（已确认的 `needs-input` 行仍显示并带「已确认」标签 —— 那是用户刚刚做过的动作，
  留个痕迹是合理反馈，与"系统自己判定过期"性质不同）。
- **不删记录**：上游改口 `running` 时这一行必须能回来（已加反向用例，防误杀）。
- **重报不会让它复活**：`ingest()` 里 `readySince` 只在"新进入 ready"时起算
  （`if (prev?.status !== 'ready')`），所以重报不续期。
- **`expired` 字段保留**：过滤之后它在视图里恒为 false，但该字段是 `isAckable` 公开谓词的一部分；
  渲染层的「（已过期）」分支改为兜底分支并加注释（不是死代码，是防御）。

### 副作用核验（逐条）

| 消费方 | 影响 |
|---|---|
| `main/index.ts:547` 控制条 `sessions` | 面板少一行 ⇒ 高度自然回落。已跑 `m2-control` 探针 **PASS**。 |
| `main/index.ts:314` 托盘 `sessionCount` | 计数更准（与面板一致）。 |
| `main/index.ts:638` `ack-session` 白名单 | 过期会话不在视图 ⇒ 单行 ack 会被拒。**可接受**：那行本来就不给按钮；「全部已确认」走不带参的 `ack()`，不受影响。已加注释。 |
| 面板空态 | 本来就存在（「清空状态会话」之后就是空态），`sessionsEl` 清空即可，无需新增处理。 |

## 5. 连带发现：确认 `ready` 现在会让通报当场退场

`ack()` 对 `ready` 的做法是把 `readySince` 拨回 `now - readyTimeoutMs`（即"当作已过 60 秒"）。
修复前它的表现是"行还在、标已读"；修复后是**行直接消失**（确认即已读）。
这是**正确的**行为（用户点了"已确认"，那条通报就该走），
但两处断言的观测方式必须跟着改，已在单测 ⑯ 与 `probe-ack-revival` 情形 3 里同步。

## 7. 教训（与既有纪律同源）

**"修了一半的出口"比"没修"更难发现。** ADR 021 那条 `ready` 出口的验收探针
（`m3-ready-exit`）测的是**渲染层画的行号**，它 PASS 是对的 —— 宠物确实不炒菜了。
面板那一行没人测，于是出口只走了一半而不自知。
⇒ **一条规则跨层生效时，每一层都要有判据**（仲裁输出 / 面板视图 / 托盘文案是三个不同的观测面）。
