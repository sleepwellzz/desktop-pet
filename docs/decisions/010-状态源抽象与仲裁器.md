# 010 · 状态源抽象与仲裁器

- **状态**：已接受
- **日期**：2026-09-16
- **决策人**：用户 + agent
- **影响**：`src/kernel/status.ts`、`src/source/*`、`src/shared/ipc.ts`、`src/main/index.ts`、`src/renderer/renderer.ts`、`tools/pet-hook.mjs`

## 背景

PLAN §8 风险表里最高的一条是"**没有真实状态源，产品会空转**"（致命级）。M1 交付的宠物只会播 idle：
状态机（`kernel/player.ts` + `desktop-pet.json` 的 `statusMap`）早就支持五态映射，缺的是**喂事件的源头**。
M2 第一步就是补上这条链：`状态源 → 仲裁器 → 动画`。

设计文档 §7.6 给出了方向（事件形如 `{sessionId, status, title, ts}`、单向可回放事件流），
并明确要求"不要让原始状态直连动画"，但未定接口细节、未定仲裁器归属、未定第一个 hook 的形态。

## 决策

### 1. 三层分工与仲裁器的归属

| 层 | 位置 | 职责 |
|---|---|---|
| 状态源 | `src/source/`（node 内置模块，不碰 electron） | 把外部世界（文件/端口/hook）归一化成 `StatusEvent` |
| 仲裁器 | `src/kernel/status.ts`（纯 TS） | 事件 → **全应用唯一主状态** + 动画意图 |
| 渲染层 | `src/renderer/` | 只负责把"该演什么"画出来 |

**仲裁器跑在主进程**，不跑渲染层。理由：M2 接下来的托盘提示、控制条、角标文案都在主进程侧，
让每个消费者各算一份比多一次 IPC 更糟；渲染层由此退化成哑渲染层，它唯一的权力是
"当前正在播一次性动作"时可以暂缓切换。

### 2. `StatusSource` 用 `start/stop`，不是设计文档里的 `subscribe(cb)`

源自己持有资源（文件监听句柄、将来的监听端口），只有一个 `subscribe` 无法表达"何时开始、何时释放"。
这是对设计文档 §7.6 模块表的**有意偏离**，记录在此以免后人以为漏实现了。

### 3. 事件是增量，快照的 diff 由适配器负责

`pet.json` 时代的教训（ADR 002）在这里复用：契约定在**最窄**处。仲裁器只见增量事件，
因此它可以保持纯函数、可被回放夹具穷举测试；"读文件、比快照、算差异"这类脏活全压进适配器。

配套一条硬规则：**"写了但读不懂" ≠ "没写"**。前者是未知（保留上一次已知状态），
后者才是消失（补一条 idle 收尾）。混为一谈的后果是"某个字段写错 → 宠物立刻掉回 idle"。
单测先挂在这一条上，已修。

### 4. 三条防抖规则：如实实现，但不假装是两套机制

设计文档 §9.3 要求三条：最短展示 400ms、变化限流 500ms、needs-input 粘滞。

其中前两条都是"距上次输出切换多久"，本质同一个时钟，因此合并为一个窗格
`max(minDisplayMs, throttleMs)`（默认由 500ms 主导）。刻意**不**去编造两套独立机制来"凑满三条" ——
真要它们独立生效，把 `minDisplayMs` 调到大于 `throttleMs` 即可。被窗格挡下的目标不丢弃，
转存 `pending`，由 `tick()` 到期补上。

### 5. 粘滞超时必须是"自动确认"，而不是"解除粘滞"

会话停在 `needs-input` 上时，单解除粘滞会让下一次仲裁立刻把它重新选为主状态、重新建立粘滞 ——
表现为**超时形同虚设**（每 5 分钟重置一次计时器）。所以超时的语义是"自动确认"：
把该会话的 `needs-input` 降级为 idle（**只降级这一种状态**：它之后报 running/blocked 仍正常参与仲裁，
否则用户一确认宠物就"失明"了）。这一条由单测钉住，因为肉眼看宠物完全看不出区别。

粘滞解除的四个条件：用户确认 / 超时自动确认 / 会话静默过期 / **会话自己改口 idle**。
最后一条是对文档措辞的补充：文档说"不被 running 覆盖"（已完整实现），
额外允许 idle 解除，是为了避免"用户已在终端里回答完"时宠物还举着手。

### 6. 静默兜底 = 15 分钟

会话超过 `sessionStaleMs` 无事件 → 按 idle 处理。这是"agent 崩溃后宠物永远停在 running"的唯一兜底：
hook 正常会在结束时写 idle，崩溃/拔电时不会。
取值 15 分钟的理由：它必须**大于一次合法任务中最长的"无 hook 空档"**（例如一次长思考期间没有任何工具调用），
否则会在任务进行中把宠物误判为结束。5 分钟有被误判的风险，不设超时则崩溃后永久卡住。

### 7. 第一个真实 hook 走"状态文件 + 监听"

对比过本地 HTTP 推送，选文件的理由：

- 任意 agent 的 hook 点都能用一条命令写入，不需要额外依赖；
- 不引入监听端口 → 没有端口占用、防火墙弹窗，以及"疑似流氓软件"的观感风险（PLAN §8 同级风险）；
- 进程重启后状态自然还在（快照语义），HTTP 推送要求双方同时在线；
- **手工在终端敲同一条命令就是设计文档里的"手工模拟器"**，链路不依赖任何 agent 就能验证。

路径 `~/.desktop-pet/status.json`（hook 不需要知道工程在哪），`--status-file=` 可覆盖，
`--no-status-source` 用于隔离排查。写入用 `tools/pet-hook.mjs`（临时文件 + rename 原子替换）。
读侧监听**目录**而不是文件（写侧 rename 会让文件句柄失效）+ 1s 轮询兜底（Windows 上 `fs.watch` 会漏）。
事件同时追加到 `~/.desktop-pet/events.jsonl`：链路通没通不看屏幕也能查，顺带把 M3 的"事件回放"埋好。

### 8. 单击宠物 = 用户确认（ack）

"粘滞驻留至用户确认"需要一个"确认"的动作来源。单击是最轻的（不需要打开任何窗口），
同时保留原有的挥手动作。无待确认会话时 ack 是空操作（不刷日志）。

### 9. 重载补推用 `replay` 标记（与 `PointerHint.force` 同一模式）

全屏让位恢复要 `reload()` 渲染层（ADR 009），新页面必须重新拿到当前状态，否则宠物静默回到 idle。
但若无差别重放，`ready`（映射到一次性的 waving）会在每次全屏恢复时再挥一次手。
所以补推带 `replay: true`，渲染层直接落到**静止落点**（`animation.then ?? animation.state`）而不重播一次性动作。
回归探针的日志里能看到这条：`推送 idle → idle rev=0（重载补推，不重播一次性动作）`。

### 10. `then` 落点放进播放器内部

`statusMap.ready = {state: waving, then: review}` 是一条序列。把 `then` 交给
`player.setState(id, { then })`，由播放器在一次性动作播完时优先落到 `then`，
而不是让调用方"播完再 setState" —— 后者会有一帧闪烁（先回落到 fallback 再被切成 then）。

### 11. 本轮不做气泡与角标（只算不画）

`bubble` / `badgeCount` 已在仲裁输出里，但渲染层不画。理由不是省事：气泡必须占用宠物以外的画布区域，
就得改窗口尺寸，而窗口尺寸与命中区域是 ADR 008/009 刚从两轮真实点击实测里救回来的东西。
在"改状态链路"的同一轮里再动命中边界，属于把两个高风险改动叠在一起。留到 M2「悬浮控制条」那一轮一起设计。

## 负面结论（踩过的坑，别再踩）

- **探针驱动会读到上一次运行的残留日志**，把"探针已开始采样"误判成立 —— 实测注入比采样早 3.7 秒，
  前两步状态全部丢失，表现为"头两个窗口没有采样点"。修法：驱动先删日志，并用运行标识
  （`PET_E2E_RUN`）确认就绪行确实出自本次运行。
- **桌宠是 detached 启动的，`child.kill()` 带不走它下面的进程**。收尾必须
  `taskkill /PID <pid> /T /F`。**绝不能按镜像名杀 `electron.exe`** —— WorkBuddy 自身也是 Electron 应用。
  残留实例会继续读写同一个状态文件，污染下一次运行。
- **`pet-hook.mjs --clear` 的参数校验顺序错了**（先要位置参数、后判 `--clear`），
  导致"移除会话"这条路径根本调不通 —— 一跑 E2E 立刻现形（`缺少状态值`）。CLI 的用法与校验必须一起写。
- **`idle` 事件不产生状态切换**（输出本来就是 idle），所以单测的断言必须挂在真实切换上，
  否则测的是"什么都没发生"。（第一版限流测试就是这么假通过的。）

## 实测证据

| 手段 | 结果 |
|---|---|
| `node tools/status-arbiter.test.mjs`（虚拟时钟） | **58 项断言全过**（含粘滞/限流/角标/静默兜底/快照 diff/播放器 then） |
| `node spikes/m2-status/run-status-e2e.mjs`（真实应用 + 真实 hook CLI） | **PASS**：六步全部核对到渲染层**实际绘制的帧行号**（7 / 6 / 0 / 3→8 / 5 / 0） |
| `node spikes/m2-hittest/run.mjs probe-fs-verify.js`（回归） | **两轮全过**：全屏让位恢复后单击与拖动均正常 |

## 后果

- 仲裁器成为状态层唯一真值来源；后续托盘/控制条/角标必须从这里取，不允许各算一份。
- `src/source/` 是新增的一层（不属 ADR 001 的"四个宿主接口"），因为它不碰 electron、只依赖 node 内置模块。
- HTTP 状态源尚未实现，但接口已就位；替换/新增源不需要动仲裁器与渲染层。
- 气泡与角标待 M2 控制条那一轮；`bubble` 字段现在只进日志。
