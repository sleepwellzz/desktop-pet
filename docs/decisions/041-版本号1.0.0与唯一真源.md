# ADR 041：版本号定为 1.0.0，且只有 `package.json` 一个出处

- 日期：2026-09-22
- 触发：用户问「那我们是不是就给这一次做完了的这个版本加一个版本号码？是不是叫 1.0.0？」
  —— 顺带问「一般怎么给软件编版本号」
- 结论：**取 `1.0.0`**；同时确立**唯一真源 + 四处派生**，并把 exe 版本资源里 Electron 的残留一并清掉

---

## 1. 先说查到的现状：不是"没有版本号"，而是"有一个别人的"

用户以为要从零开始加。实际读一遍打包产物的版本资源是这样的：

| 字段 | 改前的值 | 判定 |
|---|---|---|
| `FileVersion` | `44.4.0` | ❌ **Electron 自己的版本** |
| `ProductVersion` | `44.4.0` | ❌ 同上 |
| `ProductName` | `desktop-pet` | ✅ ADR 036 改的（决定自启值名） |
| `FileDescription` | `desktop-pet desktop pet` | ✅ |
| `CompanyName` | `GitHub, Inc.` | ❌ Electron 的 |
| `LegalCopyright` | `Copyright (C) 2015 GitHub, Inc.` | ❌ 同上 |
| `OriginalFilename` | `electron.exe` | ❌ 文件已改名，资源里还写着旧的 |

而 `package.json` 里那个 `version: 0.1.0` **从来没被任何东西读过** —— 它跟着
`resources/app/` 一起进了包，但没人把 `app.getVersion()` 接到任何地方，也没人把它写进 exe。

⇒ 所以这一轮真正的任务不是"添一个版本号"，而是**把一个错的版本号换成对的，并保证它只写一遍**。

## 2. 为什么是 `1.0.0`，以及"窄承诺"

**`1.0.0` 的含义是"从这里开始承诺兼容性"，不是"功能做完了"** —— 用工作量衡量版本号在 SemVer
规范里没有依据。所以门槛应该这样问：*这个软件现在有没有"不能被下一次更新搞坏的东西"？*

有，而且不少：

1. `~/.desktop-pet/prefs.json`（用户改过的缩放偏好等）；
2. 注册表自启项 `electron.app.desktop-pet`；
3. `pet.json` / `desktop-pet.json` 里已被用户调过的字段；
4. 分发结构（目录名 `desktop-pet/` + 入口 `desktop-pet.exe`）；
5. 图集规格 V1/V2 与 `behavior-map.json` 的行语义。

**最有力的证据是"已经为兼容性付过一次真实成本"**：旧自启值名的迁移（ADR 035）、
以及"勾了自启之后不能移动目录"这条约束 —— 会疼的地方已经出现了。

**反面意见（一并记下，因为它成立）**：如果接下来打算大改 sidecar 字段名，`0.x` 更诚实，
因为 `0.x` 的正式含义就是"接口还会动"。但长期挂在 `0.x` 的代价是**没有数字空间去表达
"这一版改坏了兼容性"**，沟通上更吃亏。

⇒ 折中：**取 `1.0.0`，但把承诺范围收窄并写下来**。

**承诺不破坏**（上面那五类）。**不承诺**：内部 IPC 通道名、控制条命令白名单、
kernel 模块划分、日志文案 —— 这些随便改，用户看不见，也不该有人依赖。

## 3. 唯一真源纪律：一个数字，一个出处

```
package.json 的 version  ← 唯一手写处（人改这一个）
  ├─→ exe 版本资源 FileVersion / ProductVersion（打包期 rcedit 写）
  ├─→ app.getVersion()（开发态与打包态读的是同一份 package.json）
  │     ├─→ 启动横幅 pet.log
  │     └─→ 托盘右键菜单里的一行只读小字
  └─→ 分发 zip 名与 README.txt（打包期写入）
```

为什么单拎出来强调：**同一个数字写两遍就会不一致**。本工程已经在"宠物名"上栽过一次
（面板写淘淘、托盘写 desktop-pet，2026-09-22 用户报的）。版本号比名字更容易悄悄漂移 ——
它没人天天看，还要跨四处保持一致。

**接入点：`app.getVersion()`**。打包态它读的是 `resources/app/package.json`，
与开发态是同一份文件，所以两边天然一致，不需要任何"打包时替换"的把戏。

## 4. 实测：Windows 的两套版本号都得写

rcedit 探测（对一份副本 exe 跑，不能用运行中的 exe 作目标 —— 会 `Unable to commit changes`）：

| 参数 | 结果 |
|---|---|
| `--set-file-version 1.0.0` | 接受（exit 0） |
| `--set-file-version 1.0.0.0` | 接受 |
| `--set-product-version 1.0.0` / `1.0.0.0` | 都接受 |
| `--set-version-string OriginalFilename ...` | 接受（任意键都能写） |

**关键读数**：同时写入"4 段数值版"与"3 段字符串版"后，
`(Get-Item exe).VersionInfo.FileVersion` 读出的是 **`1.0.0`** ——
**属性页显示的是字符串版**。

⇒ 所以两套都得写，各有各的读者：

- **四段数值版**（`1.0.0.0`）—— 给系统 / 安装器**比较大小**用。semver 的预发布后缀
  （`1.0.0-beta.1`）在这个字段里没有位置，所以打包脚本里显式剥掉（`windowsVersion()`）。
- **三段字符串版**（`1.0.0`）—— 用户在「属性 → 详细信息」里看到的那一行。

只写数值 ⇒ 属性页显示 `1.0.0.0` 或干脆空着；只写字符串 ⇒ 安装器读不到可比较的数字。

## 5. 用户的三个选择（2026-09-22）

1. **版本号取 `1.0.0`**；
2. **顺手清掉 exe 里 Electron 的痕迹**（CompanyName / LegalCopyright / OriginalFilename）——
   不改的话属性页写着 `GitHub, Inc.` / 2015 年的版权 / `OriginalFilename=electron.exe`，
   看起来就像"Electron 换了个名字"而不是一个自己的软件。
   版权栏刻意只写产品名：**没有的东西（作者、年份）不要编**，留白比编一句假声明诚实。
3. **托盘的悬停提示不要出现版本号**（保持「淘淘 · 空闲」），
   版本号改放在**托盘右键菜单里的一行只读小字**。

第 3 条值得单独记一句：用户要的是"自己开发的时候能知道版本号就可以"——
**这是"用户说不要"的落点**，下一个会话很容易觉得"到处都显示才完整"而顺手加回去。
单测里钉了一条：`tray.ts` 剥掉注释后不得出现 `version` 字样。

## 6. 位置与形态上的几个判断

- **菜单里那行放在最上方**（紧跟只读的状态行），不是最下方。理由：它属于"读一眼就走"的
  信息区，而下面每一项都是**动作**，退出必须留在最后一项（ADR 034 第 1 条已拍板，单测钉住）。
- **原生菜单不支持字号**，`enabled: false` 的置灰效果就是这里最接近"小字"的表达。不为了
  "小字"去自绘菜单 —— 那要扩大窗口，会触碰命中区域（ADR 008/016 的地盘）。
- **宠物右键弹的是同一份菜单**，所以版本号也出现在那里。这是刻意的：一份模板两个入口
  是既有约定，"宠物上右键看不到版本"才是 bug。
- **面板不加版本号**：面板宽只有 260px，身份位后面塞不下。
- **zip 名带版本**（`desktop-pet-1.0.0-win-x64.zip`），**目录名不带** —— 自启注册表里记的是
  绝对路径，目录改名会让老用户的条目失效。
- 与既有 `spriteVersionNumber`（宠物包**图集**版本 V1/V2）刻意区分：软件版本一律只叫 `version`。

## 7. 判据

| 判据 | 命令 | 结果 |
|---|---|---|
| 单测（新增 ⑱ 节 17 项） | `node tools/status-arbiter.test.mjs` | **391 → 408 项全绿** |
| 定时器生命周期 | `npm run check:timers` | 参与单测第 ⑳ 节，通过 |
| exe 版本资源（真机读回） | `(Get-Item exe).VersionInfo` | 见下方"实测" |
| 分发 zip 名 | 打包输出 | `desktop-pet-1.0.0-win-x64.zip` |

⑱ 节里最要紧的一条是**用真实的菜单模板跑一遍**（`require('dist/host/pet-menu.js')` 后调
`buildPetMenuTemplate`）—— 这才是"用户真的会看到它吗"的落点。它**不是真空的**：
改造前用同一段代码打印过一次标签，得到
`["状态：空闲","<separator>","隐藏宠物",…]`，**里面没有版本行**。

其余是结构性断言：主进程与打包脚本里**不得出现任何版本字面量**（已预检：三个源文件
剥掉注释后都没有 `x.y.z` 形态的数字，所以这条断言不会因无关数字误报）。

### 实测（打包后）

- exe 版本资源：`FileVersion = 1.0.0`、`ProductVersion = 1.0.0`、
  `CompanyName = desktop-pet`、`LegalCopyright = desktop-pet`、`OriginalFilename = desktop-pet.exe`；
- `ProductName` 仍是 `desktop-pet`（自启值名不变 —— **这一项不许动**）；
- 便携版走双击路径启动：`isPackaged=true`、`v1.0.0`、手动把玩 9 个动作、窗口/精灵图/托盘/
  控制条就绪、零异常、收尾 0 残留。

## 8. 未做 / 负面结论

- **没有做"关于"对话框**。多一个窗口不值，托盘菜单里一行足够。
- **没有做自动递增版本号**（提交钩子之类）。对一个人维护的软件，手改一个数字比引入
  一套规则更可控；真正需要它的时候是"多人并发发版"。
- **没引入 CalVer**（日期版）。它适合固定周期发版、用户不关心兼容性差异的东西；
  桌宠不是，而且 CalVer 表达不了"这一版破坏了兼容性"。
- **没有改宠物窗口标题**（仍是 `desktop-pet`）。所有探针靠 `getTitle()` 找窗口，
  改了会让整套回归静默失效。单测里有一条专门钉住它。

## 9. 一次操作教训（不是平台问题，是我的）

写这一轮时有**六处 Edit 报告成功但文件没变** —— 根因是我把多个 Edit 并发打到**同一个文件**
上（一次消息里发了 6 个），读-改-写互相覆盖，丢了更新。
症状很有欺骗性：工具回的是 "Successfully edited"，而 `tsc` 报的是一个看起来毫不相干的
类型错误（`Property 'version' does not exist`）—— 因为接口那半边丢了、用它的那半边留下了。

⇒ 纪律：**同一个文件的多处改动必须串行**，且改完 grep 复核。
这与工程里已记的"Edit 偶发报告成功但文件没变"是同一类风险，只是这次成因明确。
