# ADR 034：打包成品用户实测收口 + 开机自启注册表值名复核**不通过**

- 日期：2026-09-22
- 触发：用户双击 `dist-win/desktop-pet/desktop-pet.exe` 实测（挂起 #13 的最后一步）
- 结论：**三分之二通过，三分之一没过** —— 成为新的挂起 #15

---

## 1. 用户实测结果（#13 的"正解"验证）

用户反馈原文：「已经启动了这个 EXE 文件，但它确实不弹窗口，也没有需要关闭的窗口。而且宠物仍然在系统托盘，我已经勾选了开机自启。」

| #13 的待验项 | 结果 | 证据 |
|---|---|---|
| 无控制台 | ✅ **通过** | 用户实测；机理侧再补一刀：`electron.exe` 的 PE 子系统 = 2（GUI），从不自建控制台 —— ADR 028/029 的根因是**继承启动者的控制台**，由 explorer 双击即消失 |
| 关窗存活 | ✅ **通过** | 用户实测"宠物仍在系统托盘" |
| 托盘图标随包分发 | ✅ 通过 | 上一轮已实测从包内 `assets/tray.ico` 读出 |
| **注册表值名** | ❌ **不通过** | 见 §2 |

⇒ **#13 的核心目标（"无控制台 + 关窗存活"）达成。** 剩下的值名拆出来单独跟踪，即 **#15**。

## 2. 失败项：自启写进注册表的值名是 `electron.app.Electron`

用 PowerShell（`Get-ItemProperty HKCU:\Software\Microsoft\Windows\CurrentVersion\Run`）读到：

```
electron.app.Electron : "<工程目录>\dist-win\desktop-pet\desktop-pet.exe"
```

旁边的对照组也一并读到：

```
electron.app.Obsidian : D:\Program\Obsidian\Obsidian.exe
```

**好消息部分是命令形态**：
- `isPackaged=true` ⇒ 走的是 `autostart.ts` 的**无参分支**（`{ path: process.execPath, args: [] }`）—— **正确**。
  带参数会把自己的 exe 当成"要打开的文件"，这条最大的坑没踩到。
- 指向的正是便携版 exe；用户勾选后回读 `true`，`pet.log` 里也留了 `[pet] 开机自启 → 开（回读=true）`。
  ⇒ **自启功能本身是好的，坏的只是"它在注册表里叫什么"。**

**坏消息**：值名仍是开发态那个 `electron.app.Electron`。

## 3. 成因诊断：推翻了 ADR 033 的一句推断

ADR 033 / `autostart.ts` 的注释都写着"值名里的 `Electron` 是未打包时的 app 名，**打包后会变成 productName**"。
**这句是推断，实测不成立** —— 它把"我的应用叫什么"归给了 `app package.json` 的字段，而实测证明这条路走不通：

| 观察 | 值 |
|---|---|
| `resources/app/package.json` 的 `name` | `"desktop-pet"` ✅ **存在且正确** |
| `resources/app/package.json` 的 `productName` | `undefined`（没有这个字段） |
| 实测值名 | `electron.app.Electron` ❌ |

⇒ **`app package.json` 的 `name` 字段不决定这个值名。** 光靠放着一份名字正确的 package.json 是不够的。

对照 Obsidian：electron-builder 打包时会把 productName 同时写到**两个地方** —— app package.json 和 **exe 的版本资源（VersionInfo ProductName）**。所以从 Obsidian 的表象反推不出到底哪个起作用，必须实测。

**已排查掉的副作用面（下一会话可直接用）**：全仓库 `src/` 下**没有任何** `getPath(` / `userData` / `setName` 调用 —— 预存在 `~/.desktop-pet/prefs.json`（`prefs.ts` 用 `homedir()` 手写路径）。
⇒ 即便采用"在 ready 前 `app.setName()`"这条最激进的方案，**也不会把用户已有的偏好文件甩在旧目录里**。这是个意外的好消息，写在这里省得下次重查。

## 4. 修复候选（按"代价从小到大"排，**均未实测**）

| 方案 | 做法 | 风险 / 存疑 |
|---|---|---|
| A. 给 app 的 package.json 加 `productName` | `resources/app/package.json` 里加 `"productName": "desktop-pet"` | 零副作用，改一个 JSON。但 §3 已证明 `name` 不起作用，**`productName` 是否起作用未实测**，先验并不乐观 |
| B. `app.setName('desktop-pet')` | 在 `app.whenReady()` **之前**调用 | 副作用面为零（见 §3）。但 Electron 文档写着 setName「does not affect the name that the OS uses」——**很可能不生效**，而生效与否只能实测 |
| C. 改 exe 的版本资源 ProductName | rcedit / electron-builder 那一套（Obsidian 的做法） | **最有可能是正解**（走的是Obsidian 已验证的那条路）。代价：要引 rcedit（npm 可装），或手写 PE 资源更新 |

**推荐顺序：先试 A（10 秒），不行直接上 C。** B 大概率浪费一轮。

## 5. 判据（下一次会话照此执行，别用推断代替）

1. 改完 ⇒ `node tools/make-portable.mjs` 重新打包；
2. 双击新 exe ⇒ 托盘里**先取消勾选**「开机自启」⇒ **再勾选一次**（让新代码重写注册表）；
3. `Get-ItemProperty HKCU:\Software\Microsoft\Windows\CurrentVersion\Run` ⇒ 值名应为 `desktop-pet`；
4. **必须同时确认旧的 `electron.app.Electron` 条目已被清掉** —— 只改值名不管旧条目，会留一个指向同路径的孤儿，用户在系统启动列表里看到两个看不懂的 `Electron`。

**注意：`reg.exe` 被沙箱策略拦截，读注册表要走 PowerShell（`Get-ItemProperty` + `Out-File` 再读文件）。这条已两次验证可用，不要再在 `reg.exe` 上浪费轮次。**

## 6. 值名的实际危害有多大（决定要不要修）

- **功能：无影响。** 命令正确、自启能跑、关也能关。
- **辨识度：有影响。** 系统设置 / 任务管理器的启动项列表里它叫 `electron.app.Electron`，看不出是桌宠，也和其它 Electron 应用混淆。
- **撞名：低概率但真实。** 机器上任何另一个用便携方式自启的 Electron 应用，会和它争**同一个值名**，后写的覆盖先写的。

⇒ **建议修，但不紧急** —— 可以排在下一轮，不必为它单独开一轮。

## 7. 附带更正

修正 ADR 033 与 `autostart.ts` 注释里那句"打包后会变成 productName"：它是**推断**，实测证明 `app package.json.name` 不起作用。注释保留原句会让下一个会话直接跳到"那就改个 productName 试试"而忽略已有证据 —— 已在 §3 明确标注推翻。
