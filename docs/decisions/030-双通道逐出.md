# ADR 030：双通道**逐出**（把 ADR 020 的约束从文档变成动作）

- 日期：2026-09-21
- 状态：已实施
- 关联：ADR 020（一个 agent 只由一条通道负责）、ADR 023（此前只告警不处置）、ADR 027（方案）
- 触发：用户授权"逐出的语义我不太明白，你可以自行决策和构思"

## 1. 规则：**按通道优先级，不按到达顺序**

1. 每个 `sessionId` 记一个**主导通道**（`dominant`）+ 最近上报时刻。
2. 事件到达时：
   - 没有主导通道 / 主导通道沉默超过 `holdMs` ⇒ 这条**接管**，正常入仲裁器；
   - 与主导相同 ⇒ 续报，刷新时刻，正常入；
   - 不同 ⇒ 比优先级：**事件驱动 hook（`origin: 'hook'`）高于被动源**。
     高者接管 + 入；低者**丢弃**（不入仲裁器，打一条日志）。
3. `holdMs`（默认 **10 分钟**）是安全底线：主导通道消失（hook 卸载 / agent 崩溃）后自动释放，
   被动源接管 —— 否则宠物会永久失明。

**否决的两个选项**（理由与 ADR 027 一致，此处记录实施后的再确认）：
- 后到者胜 = 就是状态来回刷的机制本身（ADR 022 那个缺陷的根因）；
- 先到者锁定 = 桌宠启动时往往**先读到快照**（被动源），会把 hook 永久锁在门外，与该规则的目的相反。

## 2. 三个实施决定（都是实测/推演后定的，不是顺手写的）

### ① 告警必须在逐出**之前**

`ingest()` 里的顺序是：`detectDualChannel()`（诊断）→ `admits()`（处置）→ 记账。

若把告警放在逐出之后，**一旦逐出生效，低优先级事件根本走不到告警逻辑**
⇒ "有两条通道在盯同一个会话"这件事再也不报警了 —— 而那恰恰是用户需要知道的
（它会告诉你"某个 agent 的配置重复了"）。

**实现时真的踩到这一点**：先写成"逐出在最前"，单测 ⑮ 的「冷却过后再次冲突会重新告警」立刻变红
（期望 2、实际 1）。诊断与处置是**两件事**，顺序错了就丢信息。

### ② 没有通道标签的上报**永远放行**，且不改变主导通道

`origin` 为空的来源是"人工用 `pet-hook.mjs` 喂状态"或旧版客户端。
**逐出它会让"我想手动把宠物掰回某个状态"静默失效** —— 那比偶尔漏一次互斥更糟。
它也不接管主导通道：一次手工喂状态不该把 hook 挤下场。

### ③ 丢弃必须发生在**所有记账之前**

被丢弃的上报连 `sessions.set()`（刷新 `ts`）、`readySince`、`needsInputSince` 都不能碰。
否则它会：让静默兜底永不触发（`ts` 被刷新）、撤销用户的确认位（`needsInputSince` 被改写）
—— **等于没逐出，只是把"来回刷"换成了"偷偷改记账"**。
单测 ⑮c ⑦⑧ 专门钉这两条。

## 3. 配置

```json
// desktop-pet.json → statusTimeouts.dominance
{ "enabled": true, "holdMs": 600000 }
```

`enabled: false` 退回 ADR 023 的"只告警不逐出"。放在 `statusTimeouts` 段里
（而不是另开顶级段）：它有一个时间参数，且与那一段其它项同属"状态层的收敛策略"。

## 4. 这条规则如何切断 ADR 022 那个缺陷

原来：hook 写 `running`、被动源每 15–60 秒重报 `needs-input`，状态来回跳，
**每次跳回来都清一次确认位** ⇒ 用户点完宠物十几秒后又举手。

现在：hook 第一次上报就占据了主导权，**被动源的重报被整条丢弃** ——
不只是"不清确认位"（ADR 022 的症状级修法），而是**它压根到不了仲裁器**。

两者并存、各管一层：`reAskMinIntervalMs` 仍然保留（它管的是"同一条通道内的重报节奏"）。

## 6. 遗留风险

- 若某天**被动源比 hook 更准**（例如 hook 客户端出错、被动源是唯一真相），
  这条规则会压住真相。缓解：`holdMs` + 可 `enabled:false` + 丢弃日志可查。
  真到那一步说明"两条通道都开着"本身就是错的，该去修配置而不是改规则。
