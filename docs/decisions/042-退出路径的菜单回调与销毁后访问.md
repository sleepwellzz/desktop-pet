# ADR 042：退出路径上"菜单关闭回调"碰了已销毁的面板；以及"守卫要守对对象"

- 日期：2026-09-22
- 触发：用户报「右键托盘按退出按键时，弹出 `A JavaScript error occurred in the main process /
  Uncaught Exception: TypeError: Object has been destroyed at callback(...\dist\main\index.js...)`」
- 结论：定位到**面板「⋯」菜单的关闭回调**（守卫写错了对象）；修守卫，并把
  "销毁之后不许再碰它"这条判据**下沉到资源自己身上**；同时补上完整堆栈的落盘

---

## 1. 用户给的证据里，最有用的其实只有两个字

用户复制过来的堆栈是**被截断**的（`...\dist\main\in...:55`，行号根本对不上源码 ——
他手上那个 `dist-win` 版本的第 55 行是 `function resolveStatusFile()`，不是回调）。

真正可用的是函数名：**`callback`**。

于是对**整个编译产物**做了一次穷举：**`callback` 只出现一次**：

```
dist/main/index.js:779   callback: () => {
```

⇒ `at callback` 只可能是它：`'popup-menu'()` 里那条 `menu.popup({ window, callback })`。
（面板上的「⋯」按钮弹的就是**同一份**含「退出」的原生菜单 —— 托盘右键与面板「⋯」共用一套模板，
所以用户说"右键托盘"和实际走的面板「⋯」是同一份菜单、同一个 `actions.quit()`。）

## 2. 根因：**写了一个守卫，但守的是错的对象**

```ts
menu.popup({
  window: bar.browserWindow,
  callback: () => {
    barMenuOpen = false;
    if (!bar) return;                                  // ← 守的是"包装对象非空"
    const focused = bar.browserWindow.isFocused();      // ← 窗口销毁后这里抛
    dispatchBar({ kind: 'focus', hasFocus: focused });
  },
});
```

`bar` 是模块级 `let`，**`destroy()` 之后它仍然非空**（`quit()` 也从不把它置回 `null`）——
所以 `if (!bar)` 在真正危险的那个状态下**恒为假**，等于没守卫。

而 `BrowserWindow.isFocused()` 在窗口销毁后抛什么，本轮单独实测过：

| 调用 | 结果 |
|---|---|
| 销毁后 `win.isFocused()` | **抛 `TypeError: Object has been destroyed`** |
| 销毁后 `win.isDestroyed()` | 返回 `true`，不抛 |
| 销毁后 `win.destroy()`（二次） | 不抛（幂等） |

用户看到的那句话，和第三行那个方法，正好对上。

**这条回调什么时候落在"已销毁"状态上**：它由 Electron 在**菜单关闭时**调用，
而「退出」这个菜单项干的正是 `bar?.destroy()` —— 两者谁先谁后由原生菜单的关闭时机决定。

## 3. 说清楚一件事：**我没能稳定复现它**

试了五种方式，全部失败：

| 方式 | 结果 |
|---|---|
| 合成点击「⋯」后调 `quit()` | 不崩（合成点击下菜单没停留） |
| **真实鼠标**注入点击「⋯」后调 `quit()` | 不崩 |
| `tray.popUpContextMenu()` 让托盘菜单真弹出来，再调 `quit()` | 不崩 |
| 拦截 `Menu.prototype.popup` 抓到真实 menu，销毁窗口后 `closePopup()` | 回调在 `destroy()` **途中**就被调用了，那时 `isFocused()` 还没坏 |
| 直接调 `quit()`（托盘/面板两条入口） | 不崩 |

⇒ 它的时序是**竞态**的，与 ADR 035 那个"退出崩溃"属于同一形状（那次三种复现手段也全失败）。

**但没有复现 ≠ 不用修**：机制是实测的（`isFocused()` 在销毁后必抛）、
代码路径是唯一的（全仓只有一个 `callback`）、用户看到的报错就是这一条。
⇒ 照 ADR 035 §7 的规矩：**别把"没复现"说成"不存在"，也别把"测过了"说成"证明过了"。**
修复按"最坏情况"做：**只做在当前状态下一定成立的事**。

## 4. 修复

### 4.1 守卫守对对象

```ts
if (!bar || bar.browserWindow.isDestroyed()) return;
```

### 4.2 判据下沉：谁拥有资源，谁负责它的生命周期

顺手发现**同一类的第二处**，而且它没有守卫：托盘的 `refresh()` 会调
`tray.setContextMenu` / `setToolTip`，而**销毁后的 `Tray` 调用它们会抛**
（本轮实测：`Error: Tray is destroyed`）。而"销毁之后还会有人调 refresh"是**真实存在**的路径 ——
退出时 `quit()` 先 `void statusSource?.stop()`（异步），随后就 `tray.destroy()`；
一次迟到的状态推送仍会经 `refreshMenu()` 打到这里。

⇒ 判据放进 `createTray` 内部（一个 `dead` 标志，`destroy()` 先置位再销毁），
**不放在每个调用点** —— 调用点会新增，资源只有一个。
（注意：这条的报错文案是 `Tray is destroyed`，与用户的 `Object has been destroyed` 不同，
所以它**不是**用户那次崩溃的原因，是顺手堵掉的同类隐患。）

### 4.3 让下次不用再"反推"

加 `setupCrashLog()`：把**未捕获异常的完整堆栈**追加到 `~/.desktop-pet/pet.log`。
理由就在 §1：用户能从 Electron 那个错误框里复制出来的堆栈是**被截断的**，
本轮是靠在编译产物里穷举 `callback` 才定位到 —— 下次不该再这么费劲。
**只记录，不做别的**：不 `process.exit`、不试图恢复状态。
（ADR 035 的教训是"别把用户可见的崩溃降格成日志噪音"；这条日志是**给排查用的补充**，
不是"有日志就算处理过了"的许可证。）

## 5. 判据

### 5.1 真机（`spikes/m2-control` 用例 ⑭）—— 这是主判据

不去赌时序，而是**把真实回调放到最坏的那个状态下调用**：先按真实路径点开「⋯」
（用 `Menu.prototype.popup` 的观测补丁抓住 Electron 真正会调的那个函数），
面板存活时调一次（基线），再 `bar.destroy()` 之后调一次。

```
[probe] 菜单关闭回调：抓到 1 个｜面板存活时 ok=true｜面板已销毁时 ok=true
```

**它不是真空的** —— 把修复从 `dist` 里撤掉再跑一次：

```
[probe] 菜单关闭回调：抓到 1 个｜面板存活时 ok=true｜面板已销毁时 ok=false
        ｜面板已销毁时: TypeError: Object has been destroyed
[probe] 判定：FAIL
```

红的那一条，报的正是用户看到的那句话。

### 5.2 结构钉子（单测 ⑲）

`isDestroyed()` 守卫在位、托盘 `dead` 标志在位且 `destroy` 先置位、
`uncaughtException` 落全量堆栈。**这一节是 lint（防回退）**，
真正的机器判据是 5.1；两者分工写在这里，免得后人把 lint 当成证明。

### 5.3 其余

单测全绿｜`m2-menu/tray` 的退出用例（含 `[uncaught]` 扫描）通过。

## 6. 未做 / 负面结论

- **没有**把"退出时不要弹框"做成吞异常。理由：那会把真正的缺陷藏起来，
  而 ADR 035 已经教过一次"把崩溃降格成噪音"的代价。这次修的是**根因**。
  如果将来还有同类问题，正确做法是继续找那个碰了已销毁对象的地方。
- **没有**把 `bar` / `bubble` 在 `destroy()` 时置回 `null`。它能挡住这一处，
  但挡不住"别人持有的是 `win` 而不是包装对象"的情形；`isDestroyed()` 才是那条通用判据。
  两种都留着只会让下一个人以为"置 null 就够了"。
- **没有**改动 `quit()` 里 destroy 的顺序。那属于 ADR 035 的地盘，
  而这次的问题不在顺序上（顺序换了也挡不住竞态的另一半）。
- **⑫c（hide→show 后真实鼠标点击）在注入缺陷那一轮出过一次偶发失败**，
  重建后两轮均通过。已记入 PLAN §4 作为待观察项 —— **不当作已通过**。
