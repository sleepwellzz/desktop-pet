# ADR 044：打包压 zip 改用工程自带实现，守门不再依赖外部程序

- 日期：2026-09-23
- 状态：已采纳
- 相关：ADR 037（分发 = 整目录 + 一个 zip）、ADR 041（zip 名从 `package.json` 派生）、
  ADR 035（定时器句柄）、`tools/zip-dir.mjs`、`tools/make-portable.mjs`、`tools/check-timers.mjs`

## 背景

本轮是为了交付 ADR 043 的修复（朋友那台机器上"所有动作都是静态贴图"）而打包，结果**打包本身
先炸了**，而且炸得很安静：

```
tar -a -c -f desktop-pet-1.0.0-win-x64.zip desktop-pet
  → exit 0，脚本打印"zip 完成：…（373 MB）"
  实际产物：一个 tar（372.8 MB，头部是 tar 的文件名 "desktop-…"，不是 PK\x03\x04）
```

`-a`（按后缀自动选格式）**没有生效**，而失败没有任何声音。对方拿到的是一个改名为 `.zip` 的 tar，
**双击解不开**；而自动化的"打包成功"日志里完全看不出来 —— 体积那一栏只写了"373 MB"，
恰好和"没压缩"一模一样，也和数据目录的原始体积一样，**看着毫无破绽**。

同一批里还有第二处同形问题：单测第 ⑳ 节用 `spawnSync` 起一个 node 去跑 `check-timers.mjs`，
而本机沙箱会间歇性让 `spawnSync` 返回 `EBUSY` ⇒ **"每一个定时器都能被关闭"这条断言变红了，
而它要测的东西根本没问题**。

两件事的根因是同一个：**把判据/产物的可信度，押在了一个我们控制不了的外部程序上。**

## 决定

### 一、zip 由工程自己的代码压，不再调用系统 `tar`

新增 `tools/zip-dir.mjs`：纯 Node，`zlib.deflateRawSync` + 手写 ZIP 结构
（本地头 / 中央目录 / EOCD）、自带 CRC-32、按扩展名无关的确定性输出。
`tools/make-portable.mjs` 的 `--zip` 段改为 `import { zipDirectory }` 调用它，并且在压完之后
**回读头部魔数**：

```
if (magic !== '504b0304') die(`压缩产物不是 ZIP（头部 ${magic}）—— 别把它发出去`);
```

细节（都有理由）：

- **顶层目录自己也写一条目录条目**（GNU tar / bsdtar 都这么干）⇒ "解压出来是一个
  `desktop-pet/` 目录"不依赖解压器愿不愿意替我们补全父目录。
- **压不动的条目就原样存**（`method 0`），比"压完更大"的单位更诚实，且仍是合法 ZIP。
- **逐条目流式写盘**，不把整个 zip 驻留内存：最大的条目是 235 MB 的 exe，压缩后 ~104 MB，
  同时持有两份也远低于 node 默认 4 GB 堆。
- 实测：236 个文件 / 372.6 MB → **156.8 MB / 10.1 秒**，与历史（ADR 037 记的 153 MB）一致。

### 二、守门函数改成"导出一个纯函数"，单测不起子进程

`tools/check-timers.mjs` 拆成 `export function checkTimers(rootDir)`（**不打印、不退出**，
返回 `{ violations, checked }`）+ 一层 CLI（`basename(process.argv[1]) === 'check-timers.mjs'` 时才跑）。
单测第 ⑳ 节直接 `import { checkTimers }` 调用，**不再 spawn**。

命令行用法不变（`npm run check:timers` 仍然是那个退出码判据）。

## 判据

新增单测第 ㉒ 节（`tools/status-arbiter.test.mjs`），把"它到底是不是 zip"钉死：

| 断言 | 内容 |
|---|---|
| 结构性 | `make-portable.mjs` 不再出现 `spawnSync('tar'` |
| 结构性 | `make-portable.mjs` 压完回读魔数（`!== '504b0304'`） |
| 功能性 | 真压一个小目录 → 头部是 `PK\x03\x04` |
| 功能性 | 找得到 EOCD，条目数一致（顶层目录 + 子目录 + 2 个文件 = 4） |
| 功能性 | **自己解析中央目录 + `inflateRawSync` 把内容读回来**，文本与二进制（含 `0x00`、`>0x7f`）都在 |
| 功能性 | 条目名保留顶层目录（`dp-zip-xxx/`、`…/sub/`） |

另外对**真产物**做过一次独立验收（不只用自家代码看自家产物）：

- 用 Windows 的 `Expand-Archive` 解压 → 236 个文件 / 390749855 字节 / 顶层 `desktop-pet/`；
- 再对源目录与解压结果做 **236/236 个文件的 SHA-256 全量比对，0 处不同**；
- 解出来的 `desktop-pet.exe` 版本资源仍是 `1.0.0`、`CompanyName=desktop-pet`。

单测总数 `433 → 446`（新增第 ㉒ 节 + 第 ⑳ 节不再因环境变红），**全绿**。

## 负面结论 / 边界

- **这不是"tar 不好"**。`tar` 在很多机器上是好的（ADR 037 那次 153 MB 的 zip 就是它压的）。
  问题是**它的行为依赖 PATH 上是哪一个 tar、以及支不支持 `-a`**，而失败不发声。
  自己实现是为了把这份不确定性拿掉，不是为了性能（两者耗时同量级）。
- **没有用 PowerShell 的 `Compress-Archive`**：373 MB 的输入它很慢，而且同样绕不开
  "它到底是哪个实现"的问题。
- **`zlib` 的压缩率比 tar 的 zip 路径略低或略高都不重要** —— 分发体积在 150 MB 量级，
  差异对使用没有影响；确定性更重要。
- **`make-portable.mjs` 仍然 `spawnSync` 调 `rcedit`**（改 exe 版本资源那一步，ADR 036/041）。
  本机沙箱会拒它，所以本轮是分步跑完的。**这一处没有改**：`rcedit` 是原生 exe、没有等价的
  JS 实现，且它**失败时会报错**（不是静默的），风险等级与 tar 那条不同。
- **`.workbuddy/build-inproc.cjs` 是本机沙箱的绕法**（进程内调 tsc / esbuild 的 JS API），
  不进仓库；换台机器不需要它。

## 复用的排查点

1. **"打包成功"必须回读产物本身**。体积、退出码、日志文案都会说谎；
   能被"改个名字冒充"的格式（tar ↔ zip）尤其要**验魔数**。
2. **判据不要押在外部程序上**。断言被 `EBUSY`、缺依赖、PATH 上的同名程序判红，
   会让人开始怀疑断言本身，最后把真问题一起忽略掉。**断言不该被它测以外的东西判红。**
3. **导出纯函数 + 薄 CLI** 是这类"既想当命令行守门、又想被单测直接调用"的工具的标准形状。
