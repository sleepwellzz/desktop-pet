# 038 · 控制条动作排：手动把玩宠物（与 agent 状态无关）

- **状态**：已接受
- **日期**：2026-09-22
- **决策人**：用户（产品判断：要动作面板、走路要真的走、循环动作演多久、按钮常驻）+
  agent（实现与判据）
- **影响**：
  - 新增 `src/kernel/manual-play.ts`（纯函数：清单解析 / 开始 / 推进）
  - `desktop-pet.json`（新增 `actions` 段；`controlBar` 新增 `actionRowHeight` / `actionColumns`）

  - `src/main/index.ts`（手动把玩装配 + 优先级 + tick + 命令白名单）
  - `src/host/control-bar.ts`（面板高度从三段变**四段**）
  - `src/renderer/control-bar.{html,ts}`（动作排渲染）
  - `src/renderer/renderer.ts`（日志前缀 `行为层：` → `动画覆盖：`，这条通道现在有两个来源）
  - `tools/status-arbiter.test.mjs`（新增第 ⑰ 节）、`spikes/m2-control/probe-control.js`（新增 ⑫b）
- **修订**：ADR 016 第 4 条「面板动作排 = 隐藏宠物 / 宠物名 / ⋯」—— 面板上多了一整排**手动把玩**按钮。
  面板的定位也从"状态仪表盘 + 快捷动作"扩成"状态仪表盘 + **玩具架** + 快捷动作"。
- **不复用/不修改**：`src/kernel/behavior.ts` 一行未动（理由见决策 3）。

## 背景

第十三轮打包（ADR 033–037）之后项目进入"加新功能"阶段。用户提出的第一件事（原话要点）：

> 1. "我需要在悬浮条中添加相应的动作按钮……我不管现在的 agent 状态是什么，
>    我可以像逗宠物一样，把玩它的所有状态。"
> 2. "当我右键这个悬浮条时，里面应该有一些小 UI 按钮供我选择并触发它的某些动作。"
> 3. "既能由 agent 自动触发，也能在闲时手动把玩它。"
> 4. "**手动触发时，它上面不会显示文字气泡；只有 agent 触发时，才会显示文字气泡。**"

即：把图集里 9 行姿态全部变成可点的小按钮，**与 agent 状态解耦**，且**手动不产生气泡**。

## 决策

### 1. 动作排常驻面板；按钮是**文字**（2 行 × 5 列），不是缩略图

四个形态方案里用户选了文字按钮：待机 / 左走 / 右走 / 拜一拜 / 跳一下 / 趴下 / 等一等 /
过生日 / 炒菜。取舍：

- **缩略图**更"像一排玩具"且换宠物包自动跟着变（不需要名字），但 260px 宽的面板里每个只有
  ~26px，**生日与炒菜这种细节动作在缩略图上认不出来** —— 认不出来就等于没有这个按钮。
- **文字**需要一份名字表，但名字是**画面语义**，本来就该由人给：`running` 那一行画的是生日、
  `review` 那一行画的是小厨师。写进 sidecar 的 `actions.list[].label`，
  **`pet.json` 一个字段都不动**（原生语义仍是 working / review，见 `extraAssets` 的对照）。

### 2. 手动把玩走**动画覆盖通道**，不经过仲裁器 —— 这是"手动不出气泡"的实现方式

`CH.status`（仲裁器）与 `CH.behavior`（动画覆盖）是本项目既有的两条下行通道。
手动把玩走后者，于是：

| | 手动把玩 | agent 状态 |
|---|---|---|
| 通道 | `CH.behavior` 覆盖 | `CH.status` → 仲裁器 |
| 气泡 | **永远没有**（覆盖通道从不碰 `statusMap[].bubble`） | 有（`statusMap[].bubble`） |
| 面板会话行 / 托盘状态行 | 不动 | 动 |

这条"**手动 = 陪它玩 / agent = 有事告诉你**"的分界线**不是靠判断实现，而是靠通道划分天然成立的** ——
凡是要再写一句 `if (手动) 不显示气泡` 的做法都是错的方向。

### 3. 三级优先级：**手动把玩 > 自主行为层 > 仲裁器状态**

行为层与手动把玩在"面板开着"这件事上**要求正好相反**：行为层必须静止（面板锚在宠物身上），
手动把玩必须生效。所以没有把它们塞进同一份策略，而是三分：

- `behaviorSuppressed()` 加一条 `|| manualPlay !== null` —— 把玩期间行为层停手；
- `applyBehaviorCommand()` 顶部加 `if (manualPlay) return;` —— **行为层的命令一律丢弃**。
  这一条非有不可：面板打开时行为层处于抑制态，它每 tick 都会在边沿下发一次"交回仲裁器"，
  不挡的话手动动作会被**每秒冲掉 30 次**（表现是"点了没反应"）。
- **但行为层仍然每 tick 推进**。这一步同样不能省：抑制态会让它把自己的 `sentPlay` 清成 null，
  省掉的话把玩结束后它仍记着"我在走" ⇒ 窗口移动而腿停在待机姿态（**滑着走**），
  而屏幕上只表现为"它怎么飘着"。**顺序也要对：先推行为层记账，再落手动命令。**

### 4. 位移类动作**真的走**，走不动就**不假装走了**

`running-left` / `running-right` 两行是位移姿态。原地播它们的腿就是滑步 ——
而"位移速度必须与步频匹配"这条本项目已经记录过一次（`desktop-pet.json → behavior.normalization`）。
所以：

- 距离在 `actions.walkDistancePx`（默认 180–300px）内取，**按该行自身的朝向**决定方向
  （不按状态名猜，从 `role: locomotion-*` 推出来）；
- 目标点夹进宠物**所在显示器的工作区** —— 与自主漫游同一条"不跨屏"纪律（ADR 019）；
- 速度用**与自主漫游同一个函数**（`roamSpeedPxPerSec`，按缩放归一化）：两处取不同值必有一处滑步；
- **走不动时（可用空间 < 20px）降级为原地演一遍 `dwellMs`，但仍播位移姿态** ——
  动作本身要看得见，只是不谎称走了。这是"拿不到就别显示在错的地方"（ADR 021）的同一条纪律。

### 5. 演出时长：循环动作 `dwellMs`（6 秒），一次性动作**按自身片长**

- **循环动作**（待机 / 左右走 / 趴下 / 等一等 / 过生日 / 炒菜）：演 `dwellMs` 后自动交回。
  **刻意不做"一直演到再点一次"** —— 一次交互让宠物把那格姿态举着不放到静默兜底，
  正是 ADR 021 花过学费的场景（用户报的"没有 agent 在跑，它还在炒菜"）。
- **一次性动作**（拜一拜 4 帧 @8fps / 跳一下 5 帧 @10fps）：按 `clipMs + 250ms` 收。
  **不能用 `dwellMs` 代替**：`loop:false` 播完不循环，画面会**冻在末帧上摆 6 秒**
  （那正是"看起来卡住了"）。250ms 是让落定姿势（抱拳 / 落回地面）真的被看见的余量。
  —— 这与行为层处理微动作用的是同一个量、同一个理由。
- **位移类**：走到位就结束；另有 `min(12s, 路程×2 + 1.5s)` 兜底（窗口被别的东西卡住时收得住）。

### 6. 手动把玩**有界**，所以 agent 状态变化不打断它

用户明确要求"我不管现在的 agent 状态是什么"。加上上一条的时长保证（最多 6 秒），
"不打断"的代价被压到极小 ⇒ **不需要"高优状态抢占手动把玩"这条额外规则**。
把玩结束的下一 tick 就落到**最新**的 agent 状态（不是开始把玩时的那个）。

### 7. 面板高度算式从**三段**变**四段**，且参数随 `BarView` 下发

```
headerHeight + 会话行数 × rowHeight + 动作排行数 × actionRowHeight + footerHeight
                                 ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^ 新增
动作排行数 = ceil(动作个数 / actionColumns)
```

两个新参数**随视图下发**（`BarView.actionColumns` / `actionRowHeight`），渲染层不写死 ——
面板高度由主进程按它们算再 `setContentBounds`，两边各写一份就会出现"面板比窗口矮一截、底部被切"。
这正是会话行当年的结构（`.row { height: 28px }` 与 sidecar 的 `rowHeight` 各写一份），
动作排顺手把它消掉。CSS 里连一行 `grid-auto-rows: 30px` 都不留 —— 由单测钉住。

### 8. 再点同一个按钮 = 停止

高亮当前动作（暖色描边，与行内「确认」同一套语义色）。**渲染层不记"我点过哪个"** ——
`BarView.actions[].active` 由主进程的真相给出，否则面板收起再打开就会显示错的高亮。
动作清单不变时渲染层**只改高亮不重建 DOM**：重建会把光标下（或正按下）的按钮换成一个新元素，
可能吞掉一次点击。

### 9. 清单解析**不硬编码**（换宠物包要能跑）

- 写错的状态名 ⇒ **丢弃 + 告警**，不让宠物卡在一个不存在的动作上；
- `list` 省略或为空 ⇒ 按**行号顺序**回落为全部状态，文字回落为状态 id
  （面板不能出现"一个按钮都没有"）；
- 清单里**多出来的状态**（有渲染参数但没进 `list`）不自动补进来 —— **清单是权威**。

## 实测（2026-09-22）

### 离线单测：313 → **361 项**（新增第 ⑰ 节 48 项）

`node tools/status-arbiter.test.mjs` 全绿。第 ⑰ 节用**真实宠物包**（`loadPack`）做断言，覆盖：
清单解析与容错、朝向由 `role` 推导、循环动作 = `dwellMs`、一次性动作 < `dwellMs` 且 ≥ 自身片长、
到点必须显式 `play: null`、位移方向/距离区间/夹取、贴边降级为原地演、
以及三条结构性不变量（面板高度算式含动作排、白名单镜像含 `play-action`、
**`play-action` 处理器里不出现 `arbiter.`**）。

### 真机探针：`spikes/m2-control/run.mjs control` —— **PASS**

新增用例 ⑫b 端到端验了四件事（判据取**渲染层日志** `[pet][renderer] 动画覆盖：…`、
**面板 DOM 高亮**与**窗口 x**，不是只看主进程的记账）：

| 判据 | 实测值 |
|---|---|
| 面板无会话时高度 | **132**（= 30 + 2×30 + 42，四段算式成立） |
| 面板 2 条会话时高度 | **188**（= 30 + 2×28 + 2×30 + 42） |
| 动作按钮 9 个，文字/状态与 sidecar 一一对应 | ✅ 完全一致 |
| 点「过生日」→ 主进程在演 + 面板高亮 + **渲染层确实切过去** | ✅ `activeState=running` / `highlightOn=true` / `rendererSwitched=true` |
| 6 秒后自动交回仲裁器 | ✅ `stillPlaying=false`、`[pet][manual] 结束`、`→ 交回仲裁器` |
| 点「左走」→ 窗口 x 真的减小，且落在声明的 180–300px 内 | ✅ 620 → 377，走了 **243px** |
| 再点同一个按钮 = 停止（toggle 那条路径） | ✅ `已停止=true` 且高亮清掉 |
| 把玩期间面板高度不变 | ✅ 132 → 132 → 132 |

（`--no-behavior` 下也通过 —— 手动把玩**不依赖**自主行为层的开关，这是刻意的：
探针与排查常用这个开关，手动把玩若被它一起关掉，排查时就没法用手动动作做对照。）

### 本轮抓到并修掉的缺陷：**收尾被自己的守卫挡掉了**

第一版先把进行态写成 `manualPlay = mp.play`（结束那一 tick 它已经是 `null`），再调记账函数，
而后者开头是 `if (!manualPlay) return;` ⇒ **整个收尾直接返回**，`refreshBar()` 从未执行。

- **用户看到的症状**：动作演完了，面板上那个按钮**一直亮着**（要到下一次状态推送才被清掉）。
- **怎么发现的**：核对探针报告时看到 `releasedToArbiter: true` 但 `endLogged: false` ——
  两条本该同生同灭的日志只来了一条。**这是"读报告"而不是"看判定"发现的**：
  `verdict` 当时是 **PASS**，因为我的断言只查了"点下去有没有开始演"，没查"演完了面板还说不说它在演"。
- **修法**：顺序改成"**先落地这一 tick 的命令 → 再交给收尾函数去清状态**"，
  这样收尾时 `manualPlay` 仍非空，函数能读到 `state/targetX` 做记账。
- **同时补的断言**（`endLogged` / `highlightCleared` / `已停止` 三条），
  并且**把缺陷临时打回 `dist` 跑了一次探针确认它会红** —— 断言不是真空的。

> 这一条与 ADR 035 的"**进程消失 ≠ 退出干净**"是**同一个形状**：
> 拿一个"代替指标"顶替了用户真正看到的那个量。已把它升级为 `AGENTS.md` 的第三条通用纪律。


## 负面结论 / 如实记录的代价

1. **面板变高了**：空闲时 72 → 132 DIP（无会话），2 条会话时 128 → 188 DIP。
   这是"常驻动作排"的直接代价。用户选了常驻（而不是折叠在「动作」按钮里），
   理由是"右键唤出即可直接点，少一次点击"。
2. **手动走路时面板会跟着移动** —— 面板锚在宠物身上（ADR 016 的位置算式），宠物走它就走。
   观感上像"面板跟着飘过来"。**未取得用户观感数据**（机制上确定会发生，好不好看只能实测）。
3. **手动把玩会盖住 agent 状态最多 6 秒**。`needs-input` 那种求助会被推迟几秒才显示。
   用户明确接受（"我不管现在的 agent 状态是什么"），且时长有界 ⇒ 风险很小，但不是零。
4. **一次性动作的收尾是"计时"而不是"播完回调"**：渲染层没有上报"一次动作播完了"。
   与行为层的微动作用同一套 `clipMs` 计时，误差最多一帧 —— 但**这是推断，不是实测**：
   没有验证过"计时结束与最后一帧之间是否总差一帧"。要验证得让渲染层回报播放完成，
   那一层契约现在不存在，不值得为 250ms 的余量去加。
5. **`动画覆盖` 这条通道现在有两个来源**（行为层 / 手动把玩）。渲染层日志前缀因此从
   `行为层：` 改成 `动画覆盖：`，来源由主进程侧 `[pet][behavior]` 与 `[pet][manual]` 区分。
   改前缀时全仓查过：**没有任何探针在 grep 那个字符串**（探针都用 `__petDebug.behaviorState()`）。
6. **探针自身也栽了一次**：第一版 ⑫b 里声明了 `const tail`，与第 ④ 节的 `tail` 重名 ⇒
   整个探针脚本 `SyntaxError`，electron 进程**秒退且不写日志**，而 `run.mjs` 只看到
   "报告未生成"。**这正是本项目那条老纪律的又一次复现：只看"进程消失/报告没出"不够，
   必须把 stderr 拿出来看**（步骤：先 `node --check` 探针脚本，再看 electron 的 stderr）。
