# 014 · 悬浮控制条：本项目第一个可聚焦窗口

- **状态**：已接受
- **日期**：2026-09-16
- **决策人**：用户 + agent（范围 D1–D5 由用户拍板，五项全按推荐执行）
- **影响**：`src/host/control-bar.ts`（新增）、`src/kernel/bar-policy.ts`（新增）、
  `src/renderer/control-bar.{html,ts}`（新增）、`src/main/preload-bar.ts`（新增）、
  `src/main/index.ts`、`src/host/pet-menu.ts`、`src/kernel/status.ts`（+`viewSessions()`）、
  `src/shared/ipc.ts`、`desktop-pet.json`、`package.json`、`tools/copy-assets.mjs`、
  `tools/status-arbiter.test.mjs`
- **设计文档**：`docs/design/m2-control-bar.md`（用户确认 D1–D5 后才动手）
- **修订**：ADR 012 第 5 条（快捷键语义）

## 背景

M2 前三步让状态**可读**了（气泡），但用户能做的只有"看"。控制条是第一个**可操作**的交互面。

开工前必须先回答一个问题：**快捷输入框的内容要发去哪？** 规格里输入框的每个去处
（铅笔=开新对话、`@` 上下文、`$` 技能、"显示控制条并聚焦 Quick Chat"、窗口 B 的线程列表）
**全在 agent 通道上**，而 agent 通道属 M3。所以本轮范围（用户拍板 D1=A）：
**做控制条 + 状态仪表盘 + 快捷动作，不渲染自由文本输入框。**

## 决策

### 1. 控制条 = 状态仪表盘 + 快捷动作；输入框的位置与契约**冻结**而不是砍掉

本轮交付"它是个窗口"这件事本身：悬浮、可聚焦、贴宠物下方、悬停出现、快捷键唤出。
输入框不渲染，但**位置与通道形状已经定死** —— M3 落地时它长在同一位置（面板高度从
"顶栏+行+动作排"多长出一段输入区，仍走同一套 `setContentBounds` 重算），
命令仍走同一个 `barCommand` 通道，只多一个成员 `agent-send`。窗口层不用改。

为什么不做"本地命令通道"这条替代路线：它不推进任何一条验收基线（M2 的退出判据是对照
规格基线表逐条过），却会在**同一个输入框**里与 M3 的对话语义打架 —— 用户不会先读 ADR
再决定敲什么，他会直接提问然后收到"未知命令"。那是"M2 ③ 定下的不做假输入框"的另一种形态。

### 2. 本项目第一个 `focusable: true` 窗口，双路径显示

现有两层窗口（宠物 / 气泡）全是 `focusable: false`，**焦点行为是零经验区**，所以本模块的
每条取舍都由 `spikes/m2-control` 的真实探针支撑：

| 唤出方式 | 显示调用 | 抢焦点 | 理由 |
|---|---|---|---|
| 悬停出现 | `showInactive()` | **否** | 悬停是"垂手可得"，不是"要交互"。用户可能正在 IDE 里打字，鼠标划过宠物不能打断他 |
| 快捷键 | `show()` + 渲聚焦 | **是** | 用户明确按了键，就是要用键盘操作它 |
| 菜单里的"控制条" | `showInactive()` | 否 | 菜单已经拿到了交互，面板只是展示态 |

**实测佐证**（`probe-key-path.js`）：悬停唤出后 `isFocused()=false` 且注入的按键收不到；
快捷键唤出后 `isFocused()=true` 且按键收得到。

### 3. 唯一不适用 ADR 008 逐像素纪律的窗口

宠物层与气泡层要做显式 alpha 判定，是因为**窗口矩形远大于可视内容**（134×146 的框里只有
一个精灵）。控制条是**填满窗口的矩形面板**，窗口矩形 ≈ 可视矩形 ⇒
"矩形窗口吃掉自己矩形的点击"是正常窗口语义。

代价：**本轮不做圆角**。圆角会留下 4 个透明三角（约 1% 面积）去吃掉下层应用的点击 ——
在这个项目里那是需要显式接受的纵容，不值得为观感付。要做圆角得先解决"透明区不吃点击"，
那是 ADR 008 的地盘，另开一轮。

### 4. 显示策略做成**纯函数状态机**，并引入一个 `armed` 位

`src/kernel/bar-policy.ts`（纯 TS、无 Electron、时钟注入），与 `bubble-policy.ts` 同一套路。
理由也一样：这条策略里最容易错的规则**肉眼看不出对错**。

两条必须钉住的规则：

1. **快捷键收起后不能被悬停弹回来** —— 光标还停在宠物上，下一个 tick 就会把它叫回来，
   表现为"快捷键根本关不掉控制条"。靠 `toggleSuppressMs` 抑制窗口挡住。
2. **宠物全屏让位回来后不能自动重现** —— 否则全屏退出瞬间会冒出一个面板。

**只清空计时实现不了这两条**：它们发生时"由非悬停路径引起的隐藏"已经发生，而光标往往
**还停在原地**，下一个 tick 的 `hover(true)` 就会被当成"光标刚刚进入"。所以引入
`BarState.armed`：**置真的唯一时机是 `hover(false)`**（光标真的离开过一次）。
这是整套规则里唯一无法从"当前光标在哪"推导出来的信息，因此必须显式存 ——
设计稿里没写这个位，是实现时补上的（单测里有 5 条断言专门钉它）。

另一个同类的坑（写实现时差点犯）：**到点收起不能顺手撤销 `armed`**。
`hideAt` 只由 `hover(false)` / `focus(false)` 设置，此时光标早已不在宠物上，
而 `hover(false)` 只在 over 真正翻转的那一次发出 —— 在 tick 里撤销 armed 就再也没有
事件能把它解开，表现为**悬停唤出永久失效**，屏幕上只看起来"面板不再自动出现"。

### 5. 快捷键语义修订：`Win+Alt+P` 改为"唤出/收起控制条"

规格 §3.4 写的是「Windows 默认 `Win+Alt+P`：显示控制条并聚焦 Quick Chat」，
而 ADR 012 把它定成了"切换宠物显示/隐藏"。本轮按规格对齐：

| | 改前（ADR 012） | 改后（本轮） |
|---|---|---|
| `Win+Alt+P` | 切换宠物显示/隐藏 | **唤出 / 收起控制条** |
| 宠物当前隐藏 | （无关） | **先恢复宠物，再唤出**（面板锚定宠物，不能悬在半空；也避免"按了没反应"） |
| 隐藏宠物的入口 | 快捷键 + 托盘单击 + 右键菜单 | **托盘单击 + 右键菜单 + 面板里的"隐藏宠物"** |

不减能力，只换入口。归一化与四级降级链（ADR 012 的负面结论 1）继续生效。
菜单里那行文案同步改成 `快捷键：Super+Alt+P（唤出控制条）` —— 菜单不跟着改就是在说谎。

### 6. 动作走**白名单命令 id**，渲染层拿不到动作表

渲染层只能发 `BarCommandId`（7 个），主进程查表执行、未知 id 一律忽略并记日志，
`ack-session` 的 `arg` 还会再校验"会话真的存在"。好处：安全边界干净（传不了任意参数），
且 M3 加输入框时协议形状不变。

D4 的取舍：动作排放**隐藏宠物 / − / 缩放值 / + / ↺ / ⋯**，
**不放"退出"** —— 避免误点；"⋯"弹的是与托盘/右键**同一份**原生菜单，所以退出仍在一步之内。

### 7. 状态层新增只读视图 `viewSessions()`

仪表盘需要"这条会话是否已被确认"。`SessionView` 把 `status`（原始）与 `acknowledged`
**分开暴露**，由 UI 决定呈现成"需要输入（已确认）"，而不是在内核里把已确认的
needs-input 降级成 idle —— 那会让界面说谎，也会让"ack 不改原始状态"这条单测失去着力点。
视图里顺带做一次过期过滤（不删记录、无副作用）。

## 负面结论（本轮踩到的坑，都是实测）

1. **ADR 009 在键盘路径上不复现**（设计文档 §3.3 特意留的两个分支，答案是第二个的反面）。
   实测：`hide()` → `show()` 往返之后，键盘事件**照常投递**（注入按键仍被渲染层收到）。
   ⇒ **控制条不需要 reload**。ADR 009 那个坑是**鼠标按钮事件**的路由问题（Windows 侧），
   键盘走的是"焦点 → 消息队列"，另一条路径。
   这条同时把设计文档 §12 留的"M3 加输入框后 reload 会清空用户输入"的风险降到最低 ——
   本轮不存在 reload。
2. **`skipTaskbar: true` 不会给窗口加 `WS_EX_TOOLWINDOW`**（第五例"推断出来的平台行为被
   实测推翻"）。探针读回扩展样式 `0x108`（`WS_EX_TOPMOST | WS_EX_WINDOWEDGE`），没有 `0x80`。
   原因大概是 `skipTaskbar` 走 `ITaskbarList::DeleteTab` 把窗口从**任务栏**摘掉，
   而 Alt+Tab 列表看的是扩展样式位与 owner —— 两条路径不同。
   修法：`host/control-bar.ts` 里用 koffi 显式 `SetWindowLongPtrW(WS_EX_TOOLWINDOW)` +
   `SetWindowPos(SWP_FRAMECHANGED)`，`skipTaskbar` 保留作双保险。修后读回 `0x188` ✓。
   （`spikes/m2-control`、`spikes/m2-menu` 里都有 `skipTaskbar: true` 的窗口，
   说明这条规则对整个项目都成立。）
3. **`win.isVisible()` 不能用来做显示记账**。日志证据：一次快捷键唤出打出了**两条**
   "控制条显示"，第二条写着"不抢焦点"。机制是 `win.show()` 之后**同一 tick 内**
   `isVisible()` 仍可能返回 false，紧跟其后的 `focus` 事件（`show()` 会激活窗口）
   让调用方以为"还没显示"而**再 show 一次** —— 第二次是 `showInactive()`，
   在"快捷键唤出要抢焦点"的路径上正好把刚拿到的焦点又让出去。
   修法：改为由窗口自身的 `show`/`hide` **事件**驱动内部记账。修后只剩一条日志。
4. **测"位置类规则"之前必须先摆位**。第一版 `probe-control.js` 直接量默认位置，
   报出"下间距 -228、水平偏差 39"两条假失败 —— 真相是宠物默认就贴工作区右下角
   （margin 24 DIP），那里**下方只剩 24 DIP**、260 宽的面板在右侧会被夹进工作区，
   位置算式于是（正确地）翻到上方并夹取。量到的是**别的规则**的结果。
   教训与 ADR 013 的"要量渲染结果就量渲染本身"同源：**判据必须只让被测的那条规则生效**。
5. 设计稿的 `controlBar.height: 44` 落地改为**三段式**（`headerHeight` 30 + 行数 ×
   `rowHeight` 28 + `footerHeight` 42）。44 是示意值：面板有固定顶栏与底部动作排，
   两段都不可压缩，用一个数字描述不了。

## 后果

- 用户第一次能**操作**宠物之外的东西：看多会话明细、就地确认待输入、改缩放、隐藏宠物、
  一步到达全部菜单动作。
- 托盘与右键菜单多了一项"控制条"；`Win+Alt+P` 的语义变了（用户需重新适应，已在菜单里写明）。
- M3 的落点已就位：输入框长在同一位置、走同一通道、只加一个命令成员。
- 未做且刻意不做：自由文本输入框、铅笔/语音/铃铛按钮（全依赖 agent 通道）、
  Mini 模式（基线 13，要求面板自有位置记忆 + 长期常驻，与"锚定宠物"冲突）、
  圆角与投影（见 §3）、控制条钉住与位置记忆。
- 遗留（M3 必读）：若将来某次实测发现键盘路径也开始断（例如 Electron 升级后），
  控制条就要在每次显示前 reload 渲染层 —— 那时**必须同时换掉"隐藏即 `hide()`"的做法**
  （或把草稿留在主进程侧），否则会清空用户正在输入的文字。
