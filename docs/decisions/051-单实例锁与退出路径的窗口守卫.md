# ADR 051：单实例锁，以及退出路径上「窗口已死但定时器还活着」的两个成因

- 日期：2026-09-29
- 状态：已采纳
- 相关：ADR 035（定时器生命周期必须与它要碰的对象的生命周期对齐）、
  ADR 042（守卫要守"会在危险发生时变化的东西"）、ADR 009（hide→show 后输入通路失效）、
  ADR 050（构建链静默失真）、`docs/reviews/2026-09-28-全面代码复核.md`（P0-6）

## 背景

两件事在同一轮里撞到了一起。

### 一、审计 P0-6：全仓无单实例锁

`src/main/index.ts` 每次启动都用 `writeFileSync` **截断** `~/.desktop-pet/pet.log`，
而那条横幅的用途恰恰是"排查时第一眼知道对方跑的是哪一版"（ADR 041）。

⇒ 多实例场景下：**只有最后一个实例的日志留存**，这个排查能力直接归零；
另外两个仲裁器会同时读写同一份 `status.json`，而 `fs.watch` 在 Windows 上对高频写入本就漏事件。

### 二、重跑污染证据时抓到的第四个退出崩溃

为了修审计 P0-1（三份"内含 `Object has been destroyed` 却报 PASS"的入库证据），
本轮重跑了 `spikes/m3-ready-exit`。新证据里出现了：

```
[probe] 判定：PASS
[uncaught] TypeError: Object has been destroyed
    at Timeout.tickBehaviorLayer [as _onTimeout] (dist/main/index.js:1036:43)
```

**功能全对、退出路径崩了一次** —— 而且这条崩溃**不是因为重跑才产生的**，
它一直在那儿，只是旧证据被污染成了 `PASS`，没人看得见。

## 决定

### 一、单实例锁（P0-6）

```ts
if (PET_ALLOW_MULTI) { /* 跳过锁，打一条 warn */ }
else if (!app.requestSingleInstanceLock()) { app.quit(); }
```

**位置在文件最顶端**（`whenReady` 之前）：第二个实例要在建窗口、写日志、碰状态文件**之前**退出。

`second-instance` 的处理是"**把已有宠物叫出来**"，而不是什么都不做 ——
用户又双击了一次图标，合理期望是"它出来了"。分两种情况（**不能都用 `show()`**）：

- 宠物**隐藏**中 ⇒ 走 `resumePet()`（含渲染层重载，否则会留下"看着正常但点不动"的窗口，ADR 009）；
- 宠物**可见** ⇒ **什么都不做**（重载会让它闪一下并把当前动作重播成 idle）。

### 二、探针逃生开关

单实例锁会**挡住探针**：`spikes/*/run*.mjs` 需要独立起实例做对照，而它们**不带**自己的
`--user-data-dir` ⇒ 会互相挡死。

⇒ 加 `--multi-instance` / `PET_ALLOW_MULTI=1`（13 个探针脚本统一在 spawn 的 env 里带上）。
名字刻意写成"我知道我在做什么"，而不是一个看起来无害的 flag。

> **加锁时必须问一句：谁会被这把锁挡住？** 这一问是本条里唯一容易漏的地方 ——
> 锁本身只有 5 行，被它悄悄毁掉的判据却有 13 个文件。

### 三、退出路径的两道守卫（新抓到的崩溃）

`tickBehaviorLayer`（33ms）在窗口销毁后仍被调用。**两个独立成因，必须两道都堵**：

| # | 成因 | 修法 |
|---|---|---|
| ① | 停表挂在窗口的 **`hide`** 事件上，而**窗口销毁不触发 `hide`**、只触发 `closed` | 补 `overlay.browserWindow.on('closed', stopTimers)` |
| ② | 即便 `clearInterval` 执行了，**已经在定时器队列里排期的那一次回调仍会跑** | 回调开头 `if (overlay.browserWindow.isDestroyed()) return;` |

**为什么守卫放在回调里而不是调用点**：ADR 042 的结论是"判据要下沉到资源自己身上"，
而这里的资源判据正是 `isDestroyed()` —— 它**会在危险发生时变**
（反面教材是 `if (!bar) return`：`bar` 是模块级变量，`destroy()` 之后仍非空，守卫恒为假）。

### 四、一个自己踩到并当场被探针抓到的坑（照实记）

单实例锁的第一版把 `app.whenReady()` 写进了 `else` 分支里：

```ts
if (PET_ALLOW_MULTI) { console.warn('跳过锁'); }
else if (!app.requestSingleInstanceLock()) { app.quit(); }
else { app.whenReady().then(boot); }        // ← 错：跳过锁的那条路径没有装配
```

⇒ 走 `PET_ALLOW_MULTI` 时**根本没注册启动逻辑**，宠物窗口从未创建，
探针报 `[probe] 失败：Error: 未等到桌宠窗口`。

**这个错误在屏幕上表现为"宠物不见了"，而日志里只有一条"已跳过单实例锁"的正常警告。**
抓到它的是探针，不是眼睛。⇒ 装配必须放在锁的分支**之外**。

## 判据

- 主单测 **457 → 481 项全绿**（含新增：窗口 `closed` 停表的结构性断言、
  `tickBehaviorLayer` 内 `isDestroyed()` 守卫的结构性断言）。
- `spikes/m3-ready-exit` 重跑：**零 `[uncaught]`**、判定 `PASS`。
- 全部 Electron 探针重跑通过（见 ADR 052 的清单），退出路径均无未捕获异常。
- 单实例锁的行为**尚未做真实窗口实测**（需要"双击两次"这种人工动作）——
  **本轮只验证了"跳过锁时应用正常启动"与"锁的代码路径存在"**，如实记在这里。

## 可复用结论

1. **定时器要两道防线**：事件（`closed`）提前止损 + 回调自证（`isDestroyed()`）。
   只做前者会漏"已排期的那一次"，只做后者会让无谓的 tick 一直跑。
2. **加任何"全局互斥"机制时，先数一遍谁会撞上它** —— 锁、单例、独占文件皆同。
3. **重跑被污染的旧证据不是走过场**：它把一条隐藏了至少一周的退出崩溃翻了出来。
   "证据在把崩溃说成通过"这件事的代价，不是那次崩溃，而是**所有基于它的结论**。
