## 风险摘要

本项目**没有 Critical 级缺陷**，也无安全漏洞（无网络入口、无凭据、无 `eval`、无 `shell: true`）。架构纪律（内核不 import Electron、状态层单一真值、投毒点白名单）执行得比多数商业项目更严格，注释里区分「实测」与「推断」的做法尤其值得保留。

真正需要处理的是**两条 Major**，它们的共同特征是「用户能看见、但单看任何一处代码都像是对的」：

1. **每次启动都无条件全量重建**（`启动桌宠.bat:12`），实测占用启动时间的 **93%（29,941ms / 共约 32s）**。这是用户报告的「启动耗时数秒」的唯一根因，且**与应用代码无关** —— `boot()` 自身只花 322ms。
2. **双通道同时盯同一个 agent 时，用户确认会被反复撤销**（`kernel/status.ts:268`）。本轮已修（迟滞窗口），但**根治手段是让两条通道互斥**，而这个约束目前只写在文档里，代码里没有任何机制强制它。

另有三条 Minor 与五条 Nit，其中 `readyTimeoutMs` 的 60 秒与「公告时效」语义在 ADR 021 里立得住，但**与 `sessionStaleMs`（15min）的相互作用尚未有探针覆盖**，属于已识别但未验证的区域。

审查收尾时在 `dist/` 里另发现一条 Minor（[m-4]）：三个 preload 源码被 `tsc` 与 `esbuild` 各编译一次、产出两个文件名，
其中 tsc 那份（如 `dist/main/preload-bar.js`）**全仓无任何引用、永不被加载**，但它会随源码更新 ——
一个会让"我只跑了 tsc，应该没问题"变得更难察觉的诱饵文件。

## 关键问题

### [M-1] 启动时无条件全量重建，占启动耗时 93% — 🟠 Major

- **位置**：`启动桌宠.bat:12`（`call npm.cmd run build`）、`:19`（`call npm.cmd start`）
- **问题**：

  每次双击启动都跑一遍完整构建链（`tsc` + 6 次 `esbuild` + `copy-assets`）。实测分段耗时：

  | 阶段 | 耗时 | 占比 |
  |---|---|---|
  | `npm run build`（无条件全量） | **29,941 ms** | **93%** |
  | `npm start` 的 npm 引导开销 | 1,232 ms | 4% |
  | Electron → 窗口可见 | 871 ms | 3% |
  | **用户感知合计** | **≈ 32 s** | 100% |

  关键反证：`boot()` 内部只花 **322 ms**（283ms app ready → 605ms boot 返回），其中 `loadPack` + 创建 4 个窗口 + 注册托盘/快捷键全部在内。**应用代码不是瓶颈**，瓶颈是「每次启动都重建 + npm 引导」。

  触发条件：任何一次双击 `启动桌宠.bat`。后果：用户误以为程序在卡死（32 秒无任何界面反馈）。

  补充证据：`tools/run-build.cjs` 已把各步拆分计时（tsc 3.3s + 6×esbuild ~1.4s + copy-assets 0.6s ≈ 5.3s 为**有效构建**），说明 29.9 秒里有约 **24.6 秒是 npm 自身的解析/加载开销**（每次 `npm run` 都要重新解析 `package.json`、加载 npm 的整个模块图）。

- **修复建议**（两步，解耦、可分别验证）：

  **① 构建改为「按需」**：把 `.bat` 里的无条件 `npm run build` 换成产物新鲜度检查。

  ```bat
  rem 只在缺产物或源码更新时构建
  set NEED=0
  if not exist "dist\main\index.js" set NEED=1
  if not exist "dist\renderer\index.html" set NEED=1
  if not exist "dist\renderer\control-bar.html" set NEED=1
  if "%NEED%"=="0" (
    for /f %%F in ('dir /b /s src\*.ts src\*.html 2^>nul') do (
      if "%%~tF" GTR "%BUILD_STAMP%" set NEED=1
    )
  )
  ```

  更省事的等价做法：让 `tools/run-build.cjs` 支持 `--if-stale`（比对 `src/**` 最新 mtime 与 `dist/.build-stamp`），`启动桌宠.bat` 只调它。

  **② 去掉 `npm start` 的引导开销**：直接执行 Electron 可执行文件，不经 npm。

  ```bat
  rem 用 node 直接拉起 electron 的主入口，省掉 1.2 秒 npm 引导
  call "node_modules\.bin\electron.cmd" dist\main\index.js %*
  ```

  **③ 反馈前移（观感层，可选但推荐）**：构建若仍需 1–2 秒，在 `启动桌宠.bat` 开头打一行 `echo 正在启动淘淘…`，避免「双击后毫无反应」的错觉。

  **预期收益**：稳态启动从 ≈32 s 降到 **≈2 s 以内**（构建 0s + 引导 ~0.2s + Electron ~0.87s），提升约 16 倍。**此项改动需用户确认后进行** —— 它改变的是「改完代码直接双击就能生效」这一既有便利，取舍要由用户拍板。

### [M-2] 双通道同时盯同一 agent 时，用户确认被反复撤销 — 🟠 Major（本轮已修，但约束未强制）

- **位置**：`src/kernel/status.ts:268-280`（`ingest()` 的复位条件）、`src/source/status-file.ts:202`（心跳分支）
- **问题**：

  用户报告的「单击宠物后状态又自己回来了」根因不在 `ack()`，而在**两条通道交替写入**：

  - hook 通道写 `running`；文件通道（上游每 15–60 秒刷新 `ts`，`status-file.ts:202` 把它翻译成一条新事件）写 `needs-input`。
  - 状态在两者之间来回跳，而 `ingest()` 的原判据是「非 needs-input → needs-input 就清确认位」—— **每一次跳回来都清一次**，于是用户点完之后十几秒宠物又把手举起来。

  生产证据：`~/.desktop-pet/events.jsonl` 357 条里绝大多数是同一会话的 `needs-input`、`origin: "file"`、间隔 15–60 秒、持续数小时。这正是 ADR 020 明令互斥的组合。

  修复与验证（**本轮已完成**）：

  - 引入 `reAskMinIntervalMs`（默认 60s，`desktop-pet.json → statusTimeouts.reAskMinIntervalMs` 可配），把「确认」锚定在**求助的实例**上而不是状态字符串上；窗口内的重报视为同一次求助的续报，不动确认位。
  - 关键细节：**离开 `needs-input` 不清除 `needsInputSince`** —— 双通道交替正是靠这一点被挡住。
  - 取证探针 `spikes/m3-ready-ack/probe-ack-revival.mjs`：情形 2 的复活次数 **修复前 3 → 修复后 0**；全文件 **13/13 通过**（含反向用例 2b「迟滞窗口外的新求助仍应重新举手」，防误杀）。

  **残留风险（本条仍列为 Major 的理由）**：迟滞窗口是**症状级**修补，它把误报压到 60 秒一次，但**双通道本身仍然并存**。若上游重报节奏变化（例如某 agent 变成每 90 秒刷新一次），误报会以 90 秒周期回来。**根治需要机制级互斥**，而 ADR 020 的「一个 agent 只由一条通道负责」目前**只有文档约束，代码里没有任何检查**。

- **修复建议**：

  **① 机制级互斥**：在 `createStatusFileSource` 的 `diff()` 里加一条过滤 —— 若同一 `sessionId` 在最近 `dedupeWindowMs`（建议 90s）内收到过**非 file 来源**的事件，则文件源放弃该会话并记一行日志。

  ```ts
  // status.ts:逐出「已由 hook 通道负责」的会话，避免双通道交替
  private readonly ownerChannel = new Map<string, { origin: string; at: number }>();
  // ingest() 内：e.origin !== 'file' 时记 ownerChannel
  // status-file 侧：readOnce 后过滤掉 ownerChannel 里属于 hook 的 id
  ```

  **② 至少加一条运行期告警**（成本极低、收益明确）：`ingest()` 里若检测到同一 `sessionId` 在 10 秒内来自**两个不同 `origin`**，`console.warn` 一次并去重（同类告警 60 秒内只报一次）。用户拿到日志就能定位是哪个 agent 配重了 hook。

  **③ 补一条探针**：`spikes/m3-status-sources/` 下加「双通道同时指向同一 agent」的用例，断言 `console.warn` 出现过、且确认位不被撤销。今天这条路径**没有任何自动化覆盖**。

### [M-3] `needsAck` 谓词在两处各写一份，已失配一次 — 🟠 Major（本轮已修，建议补测试）

- **位置**：`src/renderer/control-bar.ts:87`（渲染层）与 `src/kernel/status.ts:316`（内核 `ack()` 的 `want()`）
- **问题**：

  两处都在回答同一个问题 ——「什么算『在等用户处理』」：

  ```ts
  // kernel/status.ts:316
  const want = (s: SessionRecord): boolean => s.status === 'needs-input' || s.status === 'ready';

  // renderer/control-bar.ts:87（修复后）
  function needsAck(s): boolean {
    if (s.acknowledged || s.expired) return false;
    return s.status === 'needs-input' || s.status === 'ready';
  }
  ```

  `control-bar.ts` 的旧版本只认 `needs-input`，于是 `ready` 在面板上**既没有「确认」按钮、行也不可点** —— 用户看到状态一直挂着却没有任何手段清掉它。这正是用户报告第二条的直接成因，属于「两处各写一份判断条件」的典型失配。

  本轮已修正谓词，但**失配的结构性原因没消除**：明天再加一个可确认状态（例如 `blocked` 的「我知道出错了」），两处又会各改一次。

- **修复建议**：

  **① 把谓词下沉到内核并导出**（一处真相，两处引用）：

  ```ts
  // kernel/status.ts
  export const ACKABLE: readonly PetStatus[] = ['needs-input', 'ready'];
  export function isAckable(s: Pick<SessionView, 'status' | 'acknowledged' | 'expired'>): boolean {
    if (s.acknowledged || s.expired) return false;
    return (ACKABLE as readonly string[]).includes(s.status);
  }
  ```

  渲染层改为 `import { isAckable } from '../kernel/status'`（`kernel` 不依赖 Electron，渲染层引用它是允许的 —— 现有 `renderer.ts` 已经这么引 `kernel/player`）。

  **② 补断言**：`tools/status-arbiter.test.mjs` 加一组「`isAckable` 对五种状态 × acknowledged × expired 的组合表」，把这张真值表钉死。今天这个谓词**没有任何单元测试**。

## 一般问题

### [m-4] 三个 preload 被两条工具链编译成两个文件名，其中 tsc 那份是永不加载的诱饵 — 🟡 Minor

- **位置**：`tsconfig.json`（`"include": ["src/**/*.ts"]` + `"outDir": "dist"`）与 `package.json:11-12`（三条 esbuild）
- **问题**：

  `src/main/` 下的三个 preload 源码（`preload.ts` / `preload-bar.ts` / `preload-bubble.ts`）
  被**两条工具链各编译一次，产出两个不同文件名**：

  | 源码 | tsc 产物（`outDir` 直接映射） | esbuild 产物（**实际加载**） | 加载点 |
  |---|---|---|---|
  | `src/main/preload-bar.ts` | `dist/main/preload-bar.js`（877 B） | `dist/main/bar-preload.js`（2,564 B） | `main/index.ts:515` |
  | `src/main/preload-bubble.ts` | `dist/main/preload-bubble.js`（566 B） | `dist/main/bubble-preload.js`（261 B） | `main/index.ts:434` |

  全仓搜索确认：**`preload-bar.js` / `preload-bubble.js` 这两个名字没有任何代码引用**（唯一命中的是
  `package.json` 的输入路径与 `tools/run-build.cjs` 里的源文件名）。它们是纯正的死产物。

  **危害不在磁盘浪费，而在于它制造了一个"看起来改动已生效"的诱饵**：改了 `src/main/preload-bar.ts`
  之后只跑 `tsc`（例如 `npm run build:main` 或 watch 模式），你会看到 `dist/main/preload-bar.js` 的时间戳变了、
  内容也对了，于是以为改动落地 —— 但真正被加载的 `bar-preload.js` 纹丝未动。

  这正是 AGENTS.md 已记录的那条教训（"改 renderer/preload 只跑 `tsc` 不够，必须跑完整 `npm run build`"）
  的一个**更隐蔽的实例**：上次它是以"探针拿到 0 采样点"的形式暴露的，这次多了一层 ——
  有一个会同步更新的同名近似文件，把这条纪律的违反变得更加难以察觉。

- **修复建议**（三选一，推荐①）：

  **① 把 preload 源码排除出 tsc**（最干净，一行）：

  ```jsonc
  // tsconfig.json
  "include": ["src/**/*.ts"],
  "exclude": ["src/main/preload.ts", "src/main/preload-bar.ts", "src/main/preload-bubble.ts"]
  ```

  preload 由 esbuild 单独打包，本来就不该让 `tsc` 再产出一份。副作用：`npm run watch`（`tsc --watch`）
  不再监视它们 —— 但 preload 改动本来就仍需重跑完整 `build`，语义反而更诚实。

  **② 统一命名**：把 esbuild 的 `--outfile` 改成与 tsc 一致的 `dist/main/preload-bar.js`，
  让两条链写同一个文件。风险是构建顺序敏感（`build:main` 先跑，随后 esbuild 覆盖），且 `--external:electron`
  的 bundle 与原 tsc 产物语义不同，容易混淆。**不如①。**

  **③ 至少加一条自检**：在 `tools/run-build.cjs` 末尾断言四个 preload 产物的 mtime 均新于对应源文件，
  并对"存在但无人加载"的 `preload-bar.js` / `preload-bubble.js` 打一行 warn。

### [m-1] `boot()` 单函数 949 行 — 🟡 Minor

- **位置**：`src/main/index.ts:84-1032`
- **问题**：脚本扫描测得 `boot()` 长度 **949 行**（粗筛，含嵌套函数）；文件整体 1043 行。它同时承担：读宠物包、算缩放、创建 4 个窗口（宠物/气泡/控制条/tray）、注册快捷键、装配状态源与仲裁器、装配行为层、挂 4 个定时器、注册全部 IPC、启动全屏监听。
- **潜在后果**：不可独立测试；阅读者需要在 949 行里靠注释导航；`bar` / `bubble` / `barState` 等 `let` 变量的 TDZ 风险需要靠「把所有异步启动放到最后」这条**结构性纪律**维持（代码注释已明确记录这一点，属于已知隐患的自觉管理）。
- **修复建议**：**不建议为拆分而拆分** —— 当前是「装配」性质，拆成 `assembleStatusLayer()` / `assembleBehaviorLayer()` / `assembleWindows()` 三个内层函数即可，不改变执行顺序，也不引入状态传递。优先做的是**把三块定时器注册收进一个 `startTimers()`**，让「什么在跑」一眼可数（现在是 `setInterval` 散落 4 处：813 / 821 / 937 / `fullscreen.ts:178`）。

### [m-2] `readyTimeoutMs`（60s）与 `sessionStaleMs`（15min）的相互作用无探针覆盖 — 🟡 Minor

- **位置**：`src/kernel/status.ts:121`、`:142`、`effectiveStatus()`:570
- **问题**：`ready` 有两条独立的到点规则 —— 通报时效 60s（`readySince`）与会话静默 15min（`rec.ts`）。二者用**不同的时间源**：前者是 `readySince`（只在真正变成 ready 那一次记），后者是 `rec.ts`（每次心跳刷新）。代码注释已解释为什么不能复用（否则机制在自己要防的场景下失效），逻辑正确。
  但**没有探针覆盖这条边界**：若某会话持续报 `ready` 心跳超过 15 分钟，`pruneStale()` 会先把它删掉，`effectiveStatus` 就再也读不到 —— 此时 `viewSessions()` 里那一行会直接消失（因为 `pruneStale` 删了记录），而 `control-bar.ts` 的「（已过期）」分支实际是给「记录还在但已降级」准备的。**「记录消失」与「记录还在但已过期」在面板上是两种不同表现，后者有分支、前者没有。**
- **修复建议**：`spikes/m3-ready-ack/` 加一条用例：`ready` 心跳持续 16 分钟后，断言 `viewSessions()` 为空且主状态为 `idle`（而不是抛错或留下残行）。若期望「仍在面板上显示为已过期」，则需把 `pruneStale` 对 `ready` 的宽限期调大于 `readyTimeoutMs`（例如 2×），否则「已过期」标签其实是永远不会出现的死分支。

### [m-3] 光标轮询在宠物隐藏时仍以 16ms 空转 — 🟡 Minor

- **位置**：`src/main/index.ts:923-937`
- **问题**：`pollPointer()` 每 16ms 执行一次。宠物不可见时它在 `tickBar()` 之后立刻 `return`（`!win.isVisible()`），但**定时器本身不停止** —— 全天候 62.5 次/秒的 JS 回调。同时 `setInterval(tickBehaviorLayer, 33)` 也常驻。
  这是「桌宠长期后台运行」场景下唯一持续消耗 CPU 的部分。实测未量化（`spikes/m3-startup` 只量到启动），但按 Electron 常规开销估算，两个空转定时器约 0.5–1.5% 单核占用。
- **修复建议**：宠物隐藏 / 全屏让位时暂停这两个定时器，恢复时重启（`overlay.show()` 的调用点已经集中在 `resumePet()` 与 `boot()` 的 `ready-to-show`，挂接点现成）。

```ts
let pointerTimer: NodeJS.Timeout | null = null;
function startPolling(): void { pointerTimer ??= setInterval(pollPointer, 16); }
function stopPolling(): void { if (pointerTimer) { clearInterval(pointerTimer); pointerTimer = null; } }
```

**注意**：`tickBar()` 挂在这个轮询上，隐藏期间若控制条仍需「到点收起」，停之前要确认 `bar` 也不可见（`hideBar()` 已经把两者绑在一起，条件成立）。

## 优化建议（Nit）

- **[N-1] `badgeCount` 的语义在注释与实现间有轻微错位**（`kernel/status.ts:377-381`）：注释写「除主状态之外、仍在要求注意的会话数」，实现过滤的是 `effectiveStatus !== 'idle'` —— 后者包含 `running`（不在「要求注意」之列）。若这是有意的（角标 = 还有别的会话活着），建议改注释；若无意，过滤条件应改为 `isAckable` 或明确的「注意类状态」集合。**当前 `running` 会话也会计入角标**，用户可能看到「另有 1 条会话」而那条其实在安分地跑。
- **[N-2] `estimateBubbleWidth` 用 14/8 px 硬编码字符宽**（`host/bubble-layer.ts:58-71`）：CJK 全角 14px、半角 8px 是经验值，与气泡层的实际字体（`bubble.html`）无绑定关系。ADR 013 已明确「要量渲染结果就量渲染本身」，这里的估算是同一纪律的例外 —— 因为气泡宽度必须在主进程算出（`setContentBounds`），属于 `setContentBounds` 约束下的妥协。建议在注释里点明「这是必要妥协，非疏忽」，避免后人误以为可以「优化成精确测量」。
- **[N-3] `STATUS_TEXT` 与 `BarView.statusLabels` 是同一份数据的两处声明**：`main/index.ts:39` 定义常量，`shared/ipc.ts:175` 声明类型并整份下发。后者注释已说明「状态文案只有一处真相」，实现也确实是下发同一对象 —— 但类型层面 `Record<PetStatus, string>` 与 `STATUS_TEXT` 没有 `satisfies` 关联，将来给 `PetStatus` 加成员时两处都要改。建议 `const STATUS_TEXT = {...} satisfies Record<PetStatus, string>`。
- **[N-4] 探针目录缺 README**：`spikes/m3-startup/` 与 `spikes/m3-ready-ack/` 本轮新建，无 README（其余 `spikes/*` 都有）。按工程既有惯例补上「这个探针验什么、怎么跑、判据是什么」三节。
- **[N-5] `probe-ack-revival.mjs` 的时钟推进纪律值得写成探针通则**：本轮调试中，情形 2b 曾因「两次 `ingest` 之间不推进时钟」而量到限流窗格（500ms）而非被测的迟滞窗口 —— 与 M2 ④ 第一版探针「没先把宠物挪离右下角」是**同一类判据不纯**。建议在 `spikes/` 顶层 README 里写成通则：**探针的两次输入之间必须显式推进时钟/改变前置状态，否则量到的是别的机制。**

## 架构评估

- **模块边界**：**清晰且被执行**。`kernel/`（纯 TS、无 Electron 依赖、时钟与随机数可注入）｜`host/`（窗口与系统能力）｜`source/`（外部世界 → 事件）｜`renderer/`（哑渲染）四层划分在代码里是真的，不是文档里的说法 —— `kernel/behavior.ts`（636 行）把漫游/微动作/打盹的全部规则收进纯函数，主进程只做「攒输入 → 调 tick → 落命令」，这是本项目最值得保留的一处设计。
- **依赖方向**：**单向，无环**。`renderer → kernel`（`player`/`status` 的纯类型与逻辑）、`main → kernel + host + source + shared`、`host → shared`。`kernel` 无出边（除 `node:fs` 用于读精灵图尺寸，`kernel/image-size.ts` —— 这处是为避免引入图像库而做的取舍，可接受）。
- **状态单一真值**：**执行得好**。`arbiter.state` 是唯一来源，托盘 / 气泡 / 控制条 / 菜单四处全部现读、各自不持有副本（`petMenuView()` / `barView()` / `refreshBubble()` 都从 `arbiter` 取）。`SessionView` 刻意「原始 status 与 acknowledged/expired 分开暴露」，让 UI 能如实显示「这条在等，但你已经确认过」—— 这是把「内核不为 UI 做决定」这条纪律落到类型上的例子。
- **主要架构风险**：
  1. **`boot()` 是 949 行的装配脚本**，其中「异步子系统必须最后启动」这条顺序约束目前靠注释维持（TDZ 隐患）。今天不崩是因为 boot 全程同步、异步事件插不进来 —— 任何人在中间加一个 `await` 就会踩爆。
  2. **双通道互斥只有文档约束**（M-2），这是当前最可能以「无报错、只是行为不对」形式复发的架构缺口。
  3. **`ack` 语义的耦合面在扩大**：`needs-input`（求助）与 `ready`（通报）语义不同，但共用一个 `ack()` 与一个 `acknowledged` 集合，靠 `effectiveStatus` 的两条降级分支区分。第三个「可确认状态」出现时应考虑把 `acknowledged` 拆成按状态的 map，否则降级分支会以组合数增长。

## 五个维度小结

| 维度 | 结论 |
|---|---|
| **正确性** | 未发现 Critical。本轮修掉一个真实的 Major（双通道撤销确认）。剩余风险集中在 `ready` / `stale` 的时间边界（m-2，无探针覆盖）。错误处理普遍是「失败只降级」（托盘/气泡/控制条创建失败都不致命），且都有 `console.error`，不是静默吞掉。 |
| **安全性** | 未发现问题。无网络入口、无凭据、无 `eval`/`new Function`（扫描 0 处）、无 `shell: true`（仅探针里用 `execSync('taskkill')`，且目标是自己 spawn 的 PID）。投毒点（`status.json`、`pet.json`）执行了白名单取值、文本限长 120、解析失败保留上次好值、绝不清零。`contextIsolation: true` 三个窗口全部开启。控制条命令走**白名单查表**，渲染层传不了任意参数 —— 这是本项目最漂亮的一处安全边界设计。 |
| **性能** | 启动路径有严重问题（M-1，93% 耗时在无条件全量构建），但**应用代码本身不是瓶颈**（`boot()` 322ms）。运行期有两处常态化定时器空转（m-3，16ms + 33ms）。无 O(n²)、无 N+1、无无界缓存（`sessions` / `acknowledged` / `readySince` / `needsInputSince` 四个 Map 全部有 `pruneStale` 清理）。 |
| **可维护性** | 注释质量**显著高于常规项目**，且区分「实测结论」与「推断」、记录被推翻的判断（如「这是本项目第五次推断出来的平台行为被实测推翻」）。主要异味是超长函数（`boot()` 949 行）与「两处各写一份判断条件」（M-3）。魔法数字扫描报 752 处，但绝大多数是探针里的时钟推进与测试值 —— 生产代码的时间常量全部集中在 `DEFAULTS` 与 `desktop-pet.json`，**不构成问题**。 |
| **架构** | 分层清晰、依赖单向无环、状态单一真值被执行。两条结构性隐患：`boot()` 的 TDZ 顺序约束（靠注释维持）、双通道互斥（靠文档维持）。 |

## 建议的处理顺序

1. **[M-1] 启动优化** —— 影响最大（32s → 2s），改动最小（一个 `.bat`）。**等用户拍板**：它会让「改完代码双击即生效」变成「需要先构建」。
2. **[M-2] ② 双通道运行期告警** —— 成本约 10 行，立刻能在日志里抓到配重 hook 的 agent。
3. **[M-3] ① 谓词下沉内核 + ② 补真值表测试** —— 消除已失配一次的结构性原因。
4. **[m-2] `ready`/`stale` 边界探针** —— 补上今天无覆盖的区域，顺带判断「（已过期）」是否为死分支。
5. **[m-3] 隐藏时暂停定时器** —— 桌宠长期后台运行，收益虽小但是纯赚。
6. **[m-1] / Nit** —— 排期处理。
