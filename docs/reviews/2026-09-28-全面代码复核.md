## 风险摘要

本项目**没有 Critical 级缺陷**，架构纪律（内核不 import Electron、状态层单一真值、投毒点白名单）执行得比多数商业项目严格，ADR 045 甚至专门把"版本号只有一个真源"写成了可验收的规则。45 条 ADR 编号连续无孤儿、`AGENTS.md` 路由表约 25 条路径全部存在、配置字段与代码引用零缺失——**这些是逐条核过的，不是印象。**

真正的问题不是"代码写得对不对"，而是三处**系统性**缺陷：

1. **判据的产物无法自证新鲜。** 六份入库的探针证据文件内容是 09-18 的、mtime 是 09-22 的，里面明写 `[uncaught] TypeError: Object has been destroyed` 却报 `PASS`；同时 1885 行的行为测试跑在 `dist/` 上，而**没有任何守卫保证 `dist/` 是本轮构建的**。`AGENTS.md` 纪律 3(b) 推荐的 mtime 验证法，在这批文件上会给出"新鲜"的错误结论。**这是本项目最需要优先处理的一类问题**——不是因为它最严重，而是因为它让其余所有判据的结论都失去依据。

2. **构建/打包链缺事务性与新鲜度守卫。** `make-portable.mjs` 零个 `try` 块，且只检查 `dist/main/index.js` 存在、不与 `src/` 比新旧。结果是：能产出"版本号 1.0.2、代码是 1.0.1、且属性页 / zip 名 / 日志横幅 / 托盘菜单**四处全都自洽地显示 1.0.2**"的包；rcedit 失败还会留下"有 exe 但 `ProductName` 仍是 Electron"的目录，开机自启的注册表值名直接错。另外 `build` 链完全不检查 preload 类型，`npm run watch` 会用 CommonJS 覆盖 renderer 的 IIFE 产物。

3. **文档与发布状态存在多份互相矛盾的"当前事实"。** 同一件已删除的事（`Win+Alt+P` 全局快捷键）在五份文档里有五种状态；`docs/acceptance.md` 六处写 `1.0.0` 而实际是 `1.0.1`，照单验收必然假判红；`1.0.1` 的源码从未提交推送、从未打过任何 tag —— **ADR 045 自己定义的失败模式原样发生了**。

另有一条**运行期**问题值得单独点名：**全仓无单实例锁**，而 `src/main/index.ts:112` 每次启动用 `writeFileSync` 截断同一份 `pet.log`。多实例场景下"看日志确认对方跑的是哪一版"这个能力直接归零，且两个仲裁器会同时写同一个 `status.json`。

## 1. P0 —— 会导致错误发布物、假判据或对外交付事故（12 条）

### [P0-1] 六份入库的探针证据早于它自己的判据，且内含未捕获异常却报 PASS

- **位置**：`spikes/m2-menu/run-tray.out:64-70`（已入库），判据在 `spikes/m2-menu/run-tray.mjs:36-47`
- **证据**：该 `.out` 文件内容为

  ```
  [uncaught] TypeError: Object has been destroyed
      at Timeout.tickBehaviorLayer [as _onTimeout] (...\dist\main\index.js:668:43)
  ✅ 退出用例通过：pid=202748 已消失
  探针判定：PASS
  ```

  而当前 `run-tray.mjs:36-47` 有专门抓这件事的检查（`crashesInLog`）：

  ```js
  const crashesInLog = logText.split('\n').filter((l) => l.includes('[uncaught]'));
  console.log(alive ? `❌ …` : crashesInLog.length ? `❌ 进程是退了，但**退出途中崩了 ${crashesInLog.length} 次**` : …);
  ```

  以这份 `.out` 的内容，脚本必然输出 ❌。但文件里是 ✅。

  | 项 | 值 |
  |---|---|
  | `run-tray.out` 最后一次提交 | `3ab727d` **09-18 00:31** |
  | `run-tray.mjs` 引入 `crashesInLog` 的提交 | `cf0b270` **09-22 11:26**（ADR 035） |
  | 磁盘 mtime | **2026-09-22 22:33:51** |
  | `git diff --quiet HEAD -- run-tray.out` | 一致（内容 = 09-18 版本） |

  即**内容是 09-18 的，mtime 是 09-22 22:33 的**；该秒数同时出现在 `m2-control/run.out`、`m2-hittest/run-fs.out`、`m2-hotkey/run.out`、`m3-behavior/run.out` 上——是一次批量 checkout 留下的统一 mtime，不是重跑产物。
- **问题**：这是 `AGENTS.md` 纪律 3(b) 点名的第三类事故（"读到的日志其实是上一轮留下的旧文件"）**原样复发**，而且**打的是纪律 3(b) 自己推荐的验证手段**。任何 agent 按 `AGENTS.md` 路由表跑完 `run-tray.mjs` 后回看这份入库证据，都会得到"退出路径已验证干净"的错误结论——**而文件自己写着崩了一次。**
- **同类污染至少 6 个入库文件**：`m2-menu/run-tray.out:67`、`m2-control/run.out:118`、`m2-hittest/run-hit.out:79`、`m2-hittest/run.log:68`、`m2-status/status-e2e.log:43`、`m3-ready-exit/ready-exit.log:28`。其中 **`m2-control` 是 `AGENTS.md` 路由表里"手动把玩"的必跑判据**。
- **修复**：
  1. 立即重跑这 6 个并提交真实输出（结果无论是 ❌ 还是修复后的 ✅，都比现在有价值）；
  2. **长期做法**：`run*.mjs` 写 `.out` 的同时写入一行 `// ran-at: <ISO 时间戳> + git rev-parse HEAD`，让"证据属于哪一次"进入**文件内容**而不是文件系统元数据——mtime 会被 checkout 改，git hash 不会。

### [P0-2] `build` 链完全不检查 preload 类型

- **位置**：`package.json:9`（`build`）、`package.json:10`（`build:main` = `tsc -p tsconfig.json`）、`tsconfig.json:22-23`（exclude 三个 preload）、`tsconfig.preload.json:12`（include 它们）、`tools/run-build.cjs:29,46-49`
- **问题**：`tsconfig.json` 把 `preload.ts` / `preload-bar.ts` / `preload-bubble.ts` 排除（注释里解释了原因：tsc 那份是全仓无引用、永不加载的诱饵文件），类型检查职责就落在 `tsconfig.preload.json` 上。而**两条构建入口都不跑它**：`npm run build` 只调 `build:main` 后直接进 esbuild；`run-build.cjs` 同样。`npm run typecheck` 确实包含它，但**无任何 `prebuild` 钩子**（`grep pretest\|prebuild` 零命中），常规 build 路径永不触发。
- **影响**：preload 是渲染层与主进程之间**唯一**的那道门。`contextBridge.exposeInMainWorld` 的键名或通道名拼错，构建期无任何提示，照样产出"成功"的 `dist/main/preload.js` 并打进发行包，只在用户点开控制条时表现为"按钮没反应"。这与 `tsconfig.json:17-21` 注释里"类型检查没有因此丢掉"的自我声明**直接矛盾**。
- **修复**：把 preload 类型检查变成构建的硬前置：

  ```json
  "prebuild": "npm run typecheck:preload",
  "build": "npm run build:main && npm run build:preload && …"
  ```

  `run-build.cjs` 对应地在 `:29` 后加一步 `run('tsc (preload typecheck)', NODE, [tscJs, '-p', 'tsconfig.preload.json'])`，并让结果参与最终退出码。

### [P0-3] `npm run watch` 会用 CommonJS 覆盖 renderer 的 IIFE 产物，且不重编 preload

- **位置**：`package.json:17`（`"watch": "tsc -p tsconfig.json --watch"`）
- **问题**：`tsconfig.json:7-8` 的 `outDir: dist` / `rootDir: src` + `include: ["src/**/*.ts"]` 意味着 tsc 会把 `src/renderer/*.ts` 也编成 `module: commonjs` 的 `dist/renderer/*.js`。`build` 里 `build:main` 先跑、随后 `build:renderer` 用 esbuild 覆盖回来，所以 `build` 结束时是对的。但 **`watch` 只有 tsc，没有任何东西覆盖回去**。同时 preload 被 `tsconfig.json` 排除，watch 期间 `dist/main/preload.js` 纹丝不动。
- **证据**（系统临时目录探针，`--outDir dist_probe`）：

  ```
  dist_probe/renderer/renderer.js:
    "use strict";
    Object.defineProperty(exports, "__esModule", { value: true });
  ```

- **影响**：跑一次 `npm run watch`，`dist/renderer/renderer.js` 变成 CommonJS，浏览器里执行时 `require` / `exports` 未定义 → 宠物窗口白屏或直接抛错。**反向更隐蔽**：preload 改动不生效，但开发者以为 watch 在跑。**同一问题的变体**：单独跑 `npm run build:main` 也会把 renderer 打成 CommonJS，直到下一次 `build:renderer` 才恢复。
- **修复**：`watch` 不应复用会 emit 的主配置。最小改法：

  ```json
  "watch": "tsc -p tsconfig.json --noEmit --watch & esbuild src/main/preload.ts … --watch"
  ```

  更稳的做法是给 `run-build.cjs` 加 `--watch` 模式，让它成为**唯一构建入口**（同时解决 P1-5）。

### [P0-4] 打包不校验 `dist/` 新鲜度 → 可发布"新版本号 + 旧代码"

- **位置**：`tools/make-portable.mjs:74`
- **问题**：唯一的构建态检查是 `if (!existsSync(join(ROOT, 'dist', 'main', 'index.js'))) die('dist/ 没构建好…')`——**只判断文件存在，不判断是否比 `src/` 新**。`grep "mtime\|stale\|newer" tools/make-portable.mjs` 零命中。全链路没有 `dist` 清理（`package.json:9` 的 build 无 clean，`run-build.cjs` 也没有）。
- **影响**：改完 `src/` 直接 `npm run make:portable`，脚本会拿**上一次的 `dist/`** 配上**新的 `package.json` 版本号**，打出一个"1.0.2 版实际装着 1.0.1 代码"的包。这正是 `make-portable.mjs:28-31` 注释里自己警惕的"同一个数字写两遍就会不一致"的极端形态 —— 而且这种包在属性页、zip 名、日志横幅、托盘菜单**四处全都自洽地显示 1.0.2，没有任何一处会露馅**。
- **修复**：构建侧写一份带内容指纹的产物元数据，打包时比对。

  ```js
  // copy-assets.mjs 末尾追加：dist/build-info.json = { srcHash: <src/** 内容的 sha256>, version }
  // make-portable.mjs:74 之后：读它并与当前 src/ 的 hash 比对，不一致 → die('dist/ 与 src/ 不同步')
  ```

  轻量替代：比较 `src/` 下最新 mtime 与 `dist/main/index.js` mtime，dist 更旧即 `die`。
- **相关（同源根因）**：`dist/host/hit-probe.js` 是**孤儿产物**（`src/host/hit-probe.ts` 已不存在），tsc 不清 `outDir` ⇒ 源文件删除或重命名后旧产物永久残留，且被 `make-portable.mjs:92-95` 整体复制进发行包。**根因与本条相同：构建既没有"清理"也没有"校验"环节。**

### [P0-5] 打包非事务性：失败留下"看起来成功"的半成品

- **位置**：`tools/make-portable.mjs:83`（`rmSync(OUT, {recursive:true, force:true})`）、`:87`（拷 368MB 运行时）、`:105`（`renameSync` 改名 exe）、`:136`（rcedit 失败 `die`）、`:140`（才写 README.txt）、`:192`（删旧 zip）、`:201`（写最终 zip）
- **问题**：整个脚本**零个 `try` 块**（`grep -c "try {" tools/make-portable.mjs` → `0`），且全程直接写最终路径。
- **影响**（两个具体后果）：
  1. `:136` rcedit 失败时，`OUT` 里已经有一个叫 `desktop-pet.exe` 的文件（`:105` 改名已完成），但**版本资源还是 Electron 原版的** ⇒ `ProductName` 仍是 `Electron` ⇒ 开机自启的注册表值名会是 `electron.app.Electron` —— **恰好是 `make-portable.mjs:107-112` 用整整一段注释说明要避开的坑**。这个目录有 exe、能双击、看不出异常，但自启名字是错的。
  2. `:192` 先删旧 zip、`:201` 直写最终路径。中途抛错（磁盘满、被杀、P2-10 的条目数溢出）会留下一个**截断的 zip 占着最终文件名**。
- **修复**：输出到 staging 目录，全成功后再原子替换。

  ```js
  const STAGE = join(ROOT, 'dist-win', `.staging-${process.pid}`);
  // …所有写操作指向 STAGE…
  // 最后：rmSync(OUT, {recursive:true, force:true}); renameSync(STAGE, OUT);
  // 顶层 try/catch/finally：catch 里 die(…)，finally 里 rmSync(STAGE, …)
  ```

  zip 同理：写 `zipPath + '.tmp'`，校验通过后 `renameSync` 到 `zipPath`。

### [P0-6] 无单实例锁，重复启动产生多实例并互相截断日志

- **位置**：全仓 `grep -rn "SingleInstance\|second-instance\|already running" src/ tools/` → **零命中**；`启动桌宠.bat:19` 也没有任何"已在运行"检查；核心在 `src/main/index.ts:112`（`writeFileSync(LOG_PATH, …)`，**覆盖写**）
- **问题**：没有 `app.requestSingleInstanceLock()` / `second-instance` 处理。
- **影响**：
  - **双击两次（或自启 + 手动）⇒ 两个进程、两只宠物窗口、两个托盘图标。**
  - 更实质的损害是日志：`index.ts:112` 每次启动 `writeFileSync` **截断**同一个 `pet.log`，所以 N 个实例只有最后一个的日志留存，前面全部丢失。而 `index.ts:108-110` 的注释明确说这个横幅的用途是"排查时第一眼就知道对方跑的是哪一版" —— **多实例场景下这个排查能力直接归零**。
  - 叠加效应：两个实例的仲裁器会同时读写同一个 `~/.desktop-pet/status.json`；`fs.watch` 在 Windows 上对高频写入本就漏事件，双写会放大抖动。
- **修复**：`src/main/index.ts` 早期（`app.whenReady()` 之前）：

  ```ts
  if (!app.requestSingleInstanceLock()) app.quit();
  else app.on('second-instance', () => { /* 聚焦/显示已有宠物 */ });
  ```

- **需人工确认**：实际双击两次的确切表现（是否伴随 `status.json` 的 `EBUSY`、是否互相取消对方的手动动作覆盖）。当前 `pet.log` 首行只有一条横幅，佐证目前是单实例运行，尚无多实例残留证据。

### [P1-1] zip 完整性校验只查 4 字节魔数，且失败无清理

### [P1-3] `check-timers` 守的是书写格式，不是句柄归属

- **位置**：`tools/check-timers.mjs:63-64`（计数）、`:68`（唯一的违规规则 `if (/^setInterval\s*\(/.test(line))`）、`:64`（dispose 工厂只认 `/\bstart\w*Watch\s*\(/`）
- **问题**（用构造样本喂入 `checkTimers()` 实测）：

  | 样本 | 报告 |
  |---|---|
  | `window.setInterval(...)` | 零违规（**漏**） |
  | `init(); setInterval(...)` | 零违规（**漏**） |
  | `setTimeout(...)` | 零违规（**完全不覆盖 `setTimeout`**） |
  | `const t = setInterval(…)`（`t` 从未登记进任何 disposer） | 零违规（**这恰是 ADR 035 原始 bug 最易复发的形态**） |
  | `const t =\n  setInterval(...)` | 误报 |

  规则是"`setInterval` 出现在行首（trim 后）才算句柄丢失"，于是**跨行赋值、同行前置其它语句、成员调用全部漏判**。而反过来，`const t = setInterval(…)` 只要赋值了就放行——**哪怕 `t` 从此再没被登记进任何 disposer 列表**。`src/` 内 4 处 `setInterval`（`index.ts:1127/1153/1154`、`control-bar.ts:241`）全为 `const`/`timers.x` 赋值形式，**说明现有规则在当前代码上恒不触发**。另有 2 处 `setTimeout`（`index.ts:1322`、`status-file.ts:238`）。dispose 工厂只按 `start*Watch` 命名识别，`watchStatus(...)`/`createPoller(...)` 这类返回 disposer 的调用全部漏判。
- **影响**：守卫通过 ≠ 定时器可回收。`package.json:25` 的 `check:timers` 不在任何 CI 位置（无 `test`/`verify` 脚本），实际是需要人记得手动跑的命令。**ADR 035 那类"退出时 Object has been destroyed"的回归可以完全绕过它。**
- **修复**：正则匹配换 AST 匹配。最小可行方案是把规则从"行首正则"改为"在**语句顶层**（`^` 或 `;` 之后）出现且左侧不是赋值/实参"，把 `setTimeout` 纳入，去掉 `start*Watch` 的命名假设（改为匹配"调用结果被登记进某个 disposer 数组"这一数据流事实）。长期方案：`ts-morph` 或 TypeScript compiler API 遍历 `CallExpression` 父节点。
- **客观评价**：这条守卫**方向是对的**——它守的确实是"会在危险发生时变化的东西"，与 ADR 042 的反面教材 `if (!bar) return` 相对；`check-timers.mjs:66-69` 的注释（"统计扫过的调用点总数，否则 0 处会被读成没检查"）也说明作者想到了这个坑。**问题只在覆盖面，不在立意。**
