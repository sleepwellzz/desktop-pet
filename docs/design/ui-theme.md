# 设计：UI 主题系统与布局改造

> 状态：**方案（未实现）**。
> 用户 2026-09-29 的方向：「当前的 UI 仍带有编程数码风格……应该更符合宠物主题，更可爱、颜色更配套。
> 不必急于删除，可以先做简单美化（例如暗黑模式）；另外可以做白色浅色主题，或与狗的颜色相搭配的 UI。
> 现有的 UI 布局相当不现代，风格也不统一，必须进行大幅度的改造。」
>
> 本文回答"怎么做才不至于改一半又推翻"，并给出**分阶段落地路径**与**每条阶段的判据**。

---

## 0. 先纠正一个前提：现在**没有**暗黑模式

现在的控制条是**一处硬编码的深色**（`src/renderer/control-bar.html` 的 `<style>` 里写死
`background: #1b1f27`、`color: #e8ecf2`，色值散落在 12 处），不是一个**可切换的主题**。

⇒ 「实现暗黑模式」这件事的真实内容是：**先有主题机制**，然后"深色"才是它的一种取值。
如果直接照着现状再写一份浅色样式表，就会得到两份互相不知道对方存在的 CSS ——
**那正是"风格不统一"的成因，而不是解法。**

---

## 1. 现状盘点（具体到代码，不是印象）

| 位置 | 现状 | 问题 |
|---|---|---|
| `control-bar.html` | 12 处裸色值写在 `<style>` 里 | 无法换色；两套主题要复制整份 CSS |
| `bubble.html` | 独立的一份样式 | 与面板**各写各的**语义色 ⇒ 同一种状态在气泡和面板上是两个不同的颜色 |
| 语义色 | `#e2863c` 暖橙（需要输入/已确认）、`#e0584f` 红（受阻）、`#4c9be8` 蓝（运行中）、`#4cb782` 绿（就绪） | 色值重复出现在多处，改一次要全仓搜 |
| 布局 | 行 28px、直角、1px 分隔线、11–12px 字号 | 密度高、层次弱 —— 典型"开发者工具面板"观感 |
| 尺寸来源 | 高度算式**四段**（`desktop-pet.json → controlBar`） | 改行高必须同步改配置，否则面板比窗口矮一截 |

### ⚠️ 三条不能碰的硬约束（美化最容易撞在这里）

1. **控制条窗口不能做圆角，也不能加投影。** ADR 014 明确：它是本项目唯一"窗口矩形 ≈ 可视矩形"的窗口
   （代价就是不做圆角）—— 圆角会在四个角留下透明三角，**吃掉下层应用的点击**。
   ⇒ 可爱化只能靠**配色、层次、内容留白与内部元素形状**（按钮圆角没问题），不能靠面板外轮廓。
2. **高度必须与主进程的算式严格对齐**（`headerHeight + 行数×rowHeight + 动作排×actionRowHeight + footerHeight`）。
   ⇒ 改布局 = 改 `desktop-pet.json` 的数值，**不是**改 CSS 里的 `height`。
   （ADR 038 已经为此把动作排的两个参数改成**随视图下发**，本次沿用同一做法。）
3. **CSP 是 `default-src 'none'`**：没有远程字体、没有远程图片。
   ⇒ 想用可爱字体只能**随包分发字体文件**（增加体积，需权衡），或者靠系统字体 + 字重层次。

## 2. 目标架构：主题令牌化

### 2.1 一层令牌，三个消费者

```
desktop-pet.json → theme                        （宠物包声明自己的配色，可选）
        ↓  parseTheme()（纯函数，可单测）
   ThemeTokens { bg, panel, text, dim, accent, ok, warn, danger, ... }
        ↓  随视图下发（与 BarView 同一条路，渲染层不写死）
control-bar.html / bubble.html / renderer 只消费 var(--pet-*)
```

**为什么必须走"随包下发"而不是渲染层自己读配置**：渲染层读不到宠物包（它只有 preload 给的窄接口）。
而 ADR 038 已经为动作排建立了这个模式（`actionColumns` / `actionRowHeight` 随 `BarView` 下发），
本次沿用 —— **同一个问题不引入第二种解法**。

### 2.2 CSS 侧的形态（每个渲染层一份 `<style>`，色值全部走变量）

```css
:root {
  --pet-bg: #1b1f27;
  --pet-text: #e8ecf2;
  --pet-dim: #7d8794;
  --pet-accent: #e2863c;
  /* … */
}
html, body { background: var(--pet-bg); color: var(--pet-text); }
```

渲染层在 `init` 时把这些变量写进 `document.documentElement.style`。
⇒ **换主题 = 改一组变量，不改一行结构**。

## 3. 三套主题的色板建议

用户点名要的三种：**浅色（可爱）**、**深色（改良版）**、**与宠物毛色搭配**。

### 3.1 浅色（默认候选）

宠物主题的浅色不该是纯白（刺眼且冷），用**暖白 + 暖灰**：

| 令牌 | 值 | 用途 |
|---|---|---|
| `--pet-bg` | `#fdf8f4` | 面板底（暖白，像奶油） |
| `--pet-panel` | `#ffffff` | 悬浮/选中块 |
| `--pet-line` | `#efe3d8` | 分隔线（暖调，比灰线柔和） |
| `--pet-text` | `#4a4038` | 主文字（暖褐灰，不用纯黑） |
| `--pet-dim` | `#9a8b7e` | 次要文字 |
| `--pet-accent` | `#e08a4a` | 主强调（与现有暖橙同族，浅底上要略深） |
| 语义四色 | 同现有色值，饱和度各降一档 | 状态点/描边 |

### 3.2 深色（现状的改良，不是重做）

保留现有色相（用户已看惯），只做三件事：**降低边框对比、提高层次、统一圆角**。
`--pet-bg: #20242e`（比 `#1b1f27` 略抬一档，让面板与桌面有分界）。

### 3.3 宠物配色（"与狗的颜色相搭配"）

**做法**：从图集**采样主色**（不是让用户填）。
`tools/make-tray-icon.py` 已经在读图集并做轮廓处理 —— 扩展成"再算一个主色"很自然，
产出写进宠物包（`desktop-pet.json → theme.accent`），成为**包的一部分**（换宠物 = 换配色）。

约束：采样出的颜色必须做**可读性校验**（对比度），不合格就回落到默认强调色 ——
否则会出现"浅色主题 + 浅黄毛色 = 按钮上的字看不见"，而这种坏掉的方式**没有任何报错**。

## 4. 布局现代化（阶段 3 才做）

用户说"布局相当不现代"，具体可改的方向（**全部受第 1 节三条约束**）：

| 现状 | 建议 | 代价 |
|---|---|---|
| 行高 28px、11px 字 | 行高 32px、12px 字 | 改 `desktop-pet.json` 的 `rowHeight`；面板整体变高 |
| 全靠 1px 分隔线分层 | 改为**块状分组** + 组间留白 | 需要重排 DOM 结构（风险最高的那一项） |
| 按钮一律描边小方块 | 主/次两级：主按钮填充、次按钮无边框 | 纯 CSS |
| 无图标 | 用**内联 SVG**（CSP 允许 data URL 与本地文件） | 每个图标要挑/画 |
| 动作排 9 个等宽小按钮 | 分组（位移 / 情绪 / 状态）或收进二级 | 改 `actions.list` 的结构（**会动到宠物包契约**） |

> ⚠️ **最后一行的代价要单独说**：动作排分组意味着 `desktop-pet.json → actions` 的结构变化。
> 按 ADR 041 的承诺范围，`desktop-pet.json` 的**字段**在兼容承诺内 ⇒ 这是 **MINOR** 级改动，
> 且必须**同时兼容旧结构**（扁平 `list`）。建议推迟到最后做，或者永远不做
> —— 它是"好看"与"契约稳定"之间的取舍，用户应该知道这个权衡存在。

## 5. 分阶段落地（每阶段独立可交付、可回退）

| 阶段 | 内容 | 用户可见变化 | 判据 |
|---|---|---|---|
| **0. 令牌化** | 把散落的色值抽进 `:root` 变量，**外观一模一样** | **无**（用户看不出区别） | 结构性断言：`control-bar.html` / `bubble.html` 的 `<style>` 内**不再出现裸十六进制色值**（`#rrggbb`），只允许出现在 `:root` 块里 |
| **1. 双主题可切** | `prefs.theme: auto\|light\|dark` + 托盘菜单切换 + `parseTheme` 纯函数 | 能选浅色了 | `parseTheme` 单测（含非法值回落）；`prefs` 注入后 `resolveTheme()` 是纯函数；探针量"实际背景色"而不是"配置值" |
| **2. 宠物配色** | 从图集采样主色 → 写进包 → 随视图下发 | 换宠物 = 换配色 | 对比度校验的非真空验证：喂一个低对比色必须被拒 |
| **3. 布局改造** | 行高、分组、层次、图标 | 观感明显变"现代" | 高度算式与实际窗口尺寸一致（已有探针可复用）；`--pet-*` 变量之外无裸色值 |
| **4. 三处统一** | 气泡层与面板共用同一套令牌 | 风格一致 | 同一种业务状态在气泡/面板/托盘悬停上的颜色**来自同一个令牌**（结构性断言） |

**阶段 0 的价值被低估**：它**零视觉风险**，却把后面所有阶段的成本从"改两份 CSS"降到"改一组变量"。
建议**先做它**，而且它不需要用户做任何决策。

## 6. 需要用户拍板的三个问题

1. **默认主题**：浅色还是深色？（建议**跟随系统** `prefs.theme = 'auto'` —— Windows 有系统级浅/深设置，
   渲染层用 `matchMedia('(prefers-color-scheme: dark)')` 读得到，与本项目已有的
   `prefers-reduced-motion` 是同一套机制。）
2. **可爱度**：走"**暖白 + 圆润**"（温和可爱），还是"**高饱和 + 大圆角**"（活泼可爱）？
   前者改动小、与现有语义色兼容；后者要重做语义色板。**建议前者**。
3. **布局改造的时机**：是否接受"面板整体变高一点、动作排可能分组"？
   这会动 `desktop-pet.json` 的字段（MINOR 级）。

## 7. 与既有决策的关系

| 决策 | 关系 |
|---|---|
| ADR 014「控制条不做圆角」 | **不破**：本文第 1 节把它列为硬约束 |
| ADR 038「动作排参数随视图下发」 | **沿用**：主题令牌走同一条路 |
| ADR 041「`desktop-pet.json` 字段在兼容承诺内」 | 阶段 3 若动 `actions` 结构 ⇒ **MINOR** 跳号（ADR 045） |
| ADR 043「尊重系统设置的范围要写清」 | **同源**：`prefers-color-scheme` 与 `prefers-reduced-motion` 一样，
   只在"合理"的范围内尊重 —— 但配色是纯视觉，跟随系统没有副作用 |
| 零网络入口 | **保持**：不引远程字体/图标库，图标用内联 SVG 或随包资源 |
