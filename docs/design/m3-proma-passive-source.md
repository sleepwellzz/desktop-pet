## 1. 已知事实（引用既有实测，不重做调研）

来源：`docs/design/m3-status-ecosystem.md` §2.2 / §2.5（2026-09-18 实测）。

| # | 事实 | 对本设计的约束 |
|---|---|---|
| 1 | Proma **没有可配置的 hook 面**：`app.asar` 里 `PreToolUse` **0**、`hook_event_name` **0**；`SessionStart` 25 处逐条看过上下文，全是编辑器内部变量 | ⇒ Proma **只能走通道 B**；也因此**不会**与通道 A 冲突（互斥规则天然满足） |
| 2 | `~/.proma/agent-sessions.json`（1 MB 索引）：**218 条**会话，字段 `id` / `title` / `createdAt` / **`updatedAt`** / `stoppedByUser` / `archived` / `legacyTranscript` | 索引可读 ⇒ 会话标题免费拿到（`title` 就是人话标题）；**218 条不可能都列**，必须有活动窗口过滤 |
| 3 | `~/.proma/agent-sessions/<uuid>.jsonl`（202 个文件）：Claude Agent SDK 消息流，`type: user\|assistant` + 末尾一条 `type:"result"`（含 `terminal_reason:"completed"`、`_durationMs`） | 候选信号是 **agent 自己的消息流**，性质与 WorkBuddy 那堆应用日志不同 ⇒ **很可能真的能区分"在干活"与"只是活着"** —— 但"很可能"不是结论 |
| 4 | `~/.proma/settings.json` 有 `notificationSounds: {taskComplete, permissionRequest, exitPlanMode, planningReminder}` ⇒ Proma 自己认"要授权"这件事，**但未发现任何对外通知通道** | ⇒ **`needs-input` 不做**（ADR 020 §3.2 已定：不承诺端到端不可验证的东西） |
| 5 | **WorkBuddy 的被动源实测只能给"存在性"**：心跳粒度约 30 秒且与在不在干活无关；`tasks/` `file-history/` 窗口内 0 次变更；`logs/` 是应用级噪声 | ⇒ 同类错误不许在 Proma 上重犯：**先采再写** |
| 6 | node 冷启动 ≈ **377 ms**/次 | 对通道 B 不构成约束（它是宿主进程内的轮询，不是每次 spawn） |

## 2. 通道 B 的形状（适配器）

### 2.1 契约：复用 `StatusSource`，不改内核

```
source/proma-sessions.ts  →  StatusSource { id, start, stop, reset?, describe }
                          →  事件 { sessionId: 'proma:<uuid>', status, title, ts, origin: 'proma' }
```

- **`sessionId` 必须带 `proma:` 前缀**（ADR 020 硬规则）：既避免与 `wb:` 撞车，又让"只想看某一个 agent"
  变成一次按前缀过滤。
- **`origin: 'proma'`**：本轮（ADR 023）新增的双通道运行期告警靠 `origin` 判定；
  带上它，将来万一 Proma 也长出一个 hook 面，"同一个会话被两条通道同时写"会立刻在日志里可见。
- **`reset()` 要实现**（与状态文件源同理）：它是快照型来源，菜单「清空状态会话」要求它忘掉记忆，
  否则"清空"会被 diff 成"每条会话都消失"、各补一条 idle 回来（ADR 016 的教训）。
- **只读**：绝不写 `~/.proma` 下任何文件（判据 5：不污染用户环境）。

### 2.2 读盘策略（1 MB 索引 + 202 个 jsonl，不能每次全量解析）

| 层 | 做法 |
|---|---|
| 索引 | 按 **mtime + size** 判断是否变化；没变就不解析。变了才 `JSON.parse` |
| 会话 jsonl | **只按增量读**：记住上次的字节偏移，用 `readSync(fd, buf, 0, len, offset)` 只解新增的那一段；文件变小（被重建）则从 0 重读 |
| 活动窗口 | 只对 `updatedAt` 落在最近 **X 分钟**且未 `archived` 的会话建状态；X 由采样定（初值 30 分钟） |
| 条数上限 | 最多 N 条（初值 3）参与仲裁，其余靠角标 `+N` 表达 —— 面板不是给 218 条会话用的 |

### 2.3 映射初稿（**每一行都要靠采样校正，不许照抄**）

| 信号 | 宠物状态 | 置信度 | 备注 |
|---|---|---|---|
| jsonl 在最近 Y 秒内有**新增 assistant 行** | `running` | 待定 | 这是"活动性"的唯一候选，采样必须给出它与"真的在干活"的相关性 |
| 末尾是 `type:"result"`（`terminal_reason:"completed"`） | `ready` | 高 | `ready` 已有 60 秒通报时效（ADR 021）⇒ 落点不会永久挂着 |
| `updatedAt` 超出活动窗口 / 会话从索引消失 | `idle` | 高 | 会话消失要补一条 idle 收尾（与状态文件源同款） |
| —— | `needs-input` | **不做** | 无信号源（事实 4）。气泡里永远不会有"Proma 等你授权"，这是**如实记录的能力边界**，不是缺陷 |

## 3. 采样探针（**先跑它，再写适配器**）

`spikes/m3-status-sources/probe-prom-live.mjs`（只读、1Hz、≥150 秒；采样期间**必须真的在 Proma 里干活**，
否则量到的是"空转"而不是"在干活"—— 与 WorkBuddy 那次同一个做法）。

它要回答三个问题，每个问题都给"不通过怎么办"：

| # | 问题 | 判据 | 不通过 |
|---|---|---|---|
| **Q1** | 追加节奏能不能区分"在干活"与"只是活着" | 给出 **running 判对率** 与 **假阳性率** 两个数字（对账方式：采样时段内的 jsonl 追加时刻 × 用户实际发消息的时刻） | 分不出 ⇒ **不写适配器**，如实记一条负面结论（与 WorkBuddy §2.5 同款处置） |
| **Q2** | `type:"result"` 末尾行能不能当 `ready` | 真回合结束时**命中 1 次、误报 0 次** | 误报多 ⇒ 只保留 `running`/`idle` 两态 |
| **Q3** | 活动窗口 X 与条数上限 N 取多少 | 采样尾部：被判为"活动"的会话数 ≤ N | 常数进 `desktop-pet.json → statusSources.proma`，**不写死在代码里** |

对应既有判据：4（被动源对账）/ 5（不污染环境）/ 8（失败要能看出来）。

## 4. 判据 6：换一个能用的时间基准

**问题**：`events.jsonl` 里的 `ts` 是 hook 进程产生 payload 的时刻，宠物侧读到它时可能已经过了
"文件监听 + 去抖 50ms + 轮询兜底" 这一整段。两者实测只差 2ms，那是**同一进程内的间隔**，
不是端到端延迟。

**方案（三小步）**：

1. **主进程加一个收到时刻**：`recordEvent()` 落 `JSON.stringify({ ...e, recvAt: Date.now() })`。
   延迟 = `recvAt - ts`，它覆盖"写状态文件 → 主进程收到"这一段，是**真实且可复现**的数字。
2. **hook 侧那段另算**：`--dump` 已经在落原样 payload 与 `at`；"hook 进程启动 + 执行"的成本 = 事件数 × 377ms
   （事实 6），它与第 1 步的数字相加才是用户实际感知的额外耗时。
3. **判据**：一次典型回合的**额外耗时上界**给一个数字（事件数 × 377ms + 观测到的 recvAt-ts 最大值）。
   上界超过"主观无感"的尺度 ⇒ 砍事件集（`PreToolUse`/`PostToolUse` 已默认不挂）或弃用 A 通道。

> 第 1 步是**宿主侧三行改动**，不碰内核、不改语义，可以单独做；第 2 步需要真实回合。

## 5. 判据 9：主观评估怎么问才不是"我觉得还行"

用户照常用一个真实回合（桌宠开着、hook 装着），事后按下面四问回答，四问**全部**为"否/无感"才算通过：

1. 打字、发送、等回复的过程中，**有没有感觉到额外的停顿**？
2. 回合期间**有没有出现过不认识的窗口/命令行闪一下**？
3. 这个回合**与平时的耗时相比**（主观）：明显变慢 / 略微 / 无感？
4. 宠物**有没有在你没让它动的时候乱动**（假阳性）—— 这是通道 B 的失败模式，不是 A 的。

再加判据 6 的数字上界。**任一条不过 ⇒ 先砍事件集（`PreToolUse`/`PostToolUse`），仍不过 ⇒ 弃用通道 A**，
本轮以"映射层 + 客户端 + 一条明确的负面结论"收尾（ADR 020 的止损设计）。

## 6. 待你拍板的三项

| # | 问题 | 我的建议 | 理由 |
|---|---|---|---|
| **P1** | 接受"Proma 只给 `running`/`ready`/`idle`，**不给** `needs-input`"？ | **接受** | 没有信号源就是没有；编一个出来就是假阳性，而假阳性是最不能接受的失败模式 |
