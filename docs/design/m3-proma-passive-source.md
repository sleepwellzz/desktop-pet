## 一、解冻后唯一需要记住的三条

| # | 事项 | 值 |
|---|---|---|
| 1 | **接口** | 复用 M2 ① 就有的 `StatusSource`，**不需要新增任何接口或内核改动**。通道 B 与通道 A 产出同一种 `StatusEvent`。 |
| 2 | **`sessionId` 前缀** | `proma:<uuid>`（ADR 020：来源前缀是"一个 agent 只由一条通道负责"的落地手段） |
| 3 | **通道标签** | `origin: 'proma'`（ADR 023 起的双通道告警依赖它） |

**暂定映射（未验证，解冻后必须先采样再定）**：`running` ← 近期有 assistant 追加；
`ready` ← 末尾出现 `type:"result"`；到期即 `idle`；**不给 `needs-input`**（没有信号源就是没有）。

## 二、已确认的事实（调研实测，不需要重做）

- **Proma 没有可配置的 hook 面**：`app.asar` 里 `PreToolUse` / `hook_event_name` / `disableAllHooks`
  全为 0；`SessionStart` 的 25 处上下文逐条看过，全是编辑器内部变量，不是 agent hook。
  ⇒ **只能走被动源（通道 B）**，这是它与 WorkBuddy 的根本差别。
- **被动源素材可读**：`~/.proma/agent-sessions.json`（218 条，含 `title` 与 `updatedAt`）、
  `~/.proma/agent-sessions/<uuid>.jsonl`（202 个，末尾有 `type:"result"` + `terminal_reason`）。
- **⚠️ 但"可读"不等于"能反映活动性"** —— 这正是必须先采样的原因。
  WorkBuddy 的被动源就栽在这里：心跳 30 秒粒度且与在不在干活无关，只能给"存在性"。
  **假阳性（看起来在工作其实没有）是最不能接受的失败模式。**

## 三、解冻条件（用户问：何时开展）

按顺序，前一条不满足就不开始：

1. **通道 A 成品化完成**：判据 9（用户跑真实回合不觉得被拖慢）与判据 6（端到端延迟可接受）
   都拿到结论；桌宠在日常使用里稳定跑一段时间无异常。
2. **用户哪天正好要在 Proma 里干活时，提前说一声** —— 不需要专门安排时间。
   采样探针是**只读**的，挂在他真实回合旁边跑约 150 秒即可。
3. **采样只回答一个问题**：Proma 的 jsonl 能不能区分"在跑"与"只是存在"。
   → **能**：才写适配器（默认 `enabled: false`，试用后再开）。
   → **不能**：如实记一条负面结论收尾，**不硬凑适配器**。
