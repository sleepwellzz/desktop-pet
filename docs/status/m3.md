**M3 第二块：状态源生态（2026-09-18，进行中，ADR 020）**：把"链路通"升级成"真能用" ——
让桌宠如实反映**真实 agent** 的活动，不再靠"喂状态"模拟。目标 agent 由用户定为
**WorkBuddy（主力）+ Proma（第二主力，Pi agent 架构）**，不是 Codex。

- **架构是两条通道，不是每个 agent 一套适配器**：
  **A · 事件驱动 hook**（WorkBuddy；且与前缀无关地覆盖 Codex / 将来的 Claude Code ——
  它们**是同一套事件名与 stdin 契约**）｜**B · 被动会话源**（Proma）。
- **新增硬规则：一个 agent 只由一条通道负责，两条通道互斥。** 两个**不同** agent 天然不冲突
  （仲裁器从 M2 ① 起就是多会话形状，`+N` 角标即为此）；
  会打架的是**同一个 agent 被两条通道同时盯**（hook 说 running、被动源说 idle，来回刷且无报错）。
  被动源是"降级来源"，**是切换不是叠加**。
- **`sessionId` 带来源前缀**（`wb:<pid>` / `proma:<uuid>`）+ **标题带来源名**
  （气泡只显示一个标题，两个 agent 同时在跑时必须分得清谁是谁）。
  副产品：用户"只想连某一个 agent"变成**一次按前缀过滤**，不是新机制。
- **闸门实测 = YES**：进程树显示桌面把 agent 跑在内嵌 `cli/bin/codebuddy --serve --session-id …` 上
  （该 uuid 与 `~/.workbuddy/sessions/<pid>.json` 完全一致）；CLI 的
  `DEFAULT_SCOPES = [USER, PROJECT, PROJECT_LOCAL]` 且跑 agent 的进程没带 `--setting-sources`
  ⇒ **工程级 `.codebuddy/settings.local.json` 会被读**。
- **施工顺序被实测推翻一次**：初稿把"先做被动源"当零风险的先赢，采样探针证明
  **WorkBuddy 的被动源只能给"存在性"、给不了"活动性"**（心跳粒度约 30 秒且与在不在干活无关；
  `tasks/`、`file-history/` 窗口内 0 次变更；`logs/` 是应用级噪声）
  ⇒ **通道 A 才是 WorkBuddy 的主路径**，B 降为可选。
- **落地**：`tools/codebuddy-hook-map.mjs`（纯函数映射层）、`tools/pet-hook-cb.mjs`（hook 客户端，
  **退出码恒 0**、`--dump` 取证）、`tools/install-codebuddy-hooks.mjs`（安装器，**默认 dry-run**、
  幂等、可卸载、带备份）、`tools/codebuddy-hook.test.mjs`（**70 项**）、
  `spikes/m3-status-sources/probe-workbuddy-live.mjs`（只读采样探针）。
  工程级 hook 配置**已落盘**（6 个低频事件；`PreToolUse`/`PostToolUse` 不挂 —— 每次 377ms）。
- **判据 2 ✅ 已通过（桌宠运行后拿到宠物侧时间线）**：`ready`(09:56:57.853) ← `Stop`(09:56:57.851)；
  `running`(10:02:42.862) ← `UserPromptSubmit`(10:02:42.860)；序列正确、不卡在 running。
  **`idle_prompt` 在真实环境被正确忽略**（hook 侧有、宠物侧无对应事件）⇒ 上面那个修复确认有效。
- **新发现 · 待用户拍板：`ready` 的落点 `review` 是循环终态、没有出口。**
  `ready` → 挥手 → **落到第 8 行"小厨师姿态"**（对照 `docs/status-reference.png` 确认，
  就是用户看到的"炒菜"），而 `review` 是 `loop: true` ⇒ **agent 干完一次活，宠物就永久炒菜**。
  `Stop` 现在每次回合结束都触发 ⇒ 稳定复现（以前没有真实 hook，所以没暴露）。
  支持"这是缺陷"的论据：**气泡对 `ready` 只显示 6 秒就收起，宠物却还在炒菜** —— 两者不一致。
  **但改成什么是产品决策**（`ready → 挥手 → 落到 review` 本身是 M2 ① 验收过的行为），
  选项 A（推荐：`review` 60 秒后自动回 `idle`）/ B（单击宠物 = 已读，复用 `ack()`）/ C（落点改回 idle，不推荐）
  见 ADR 020。
- **⚠️ 判据 6 的测量陷阱（已实测）**：`~/.desktop-pet/events.jsonl` 里的 `ts` 是**写侧产生时刻**，
  **不是宠物收到的时刻**（实测差 2ms，那只是 hook 进程内"落 payload → 写状态文件"的间隔）。
  **拿它算端到端延迟会严重低估。** 要算真实延迟得另找时间基准（主进程日志或探针加戳）。
- **附带事实**：`default` 会话是 8-16 人工验收的残留（title `manual-acceptance`），
  桌宠启动时短暂报了一次 `running`（10:01:15）、4 秒后变 `idle`；**是噪声不是缺陷**，
  菜单「清空状态会话」可清掉。
- **判据**：新增 **70 项** + 既有 **219 项** ⇒ **289 项全绿**。
- **下一步**：① 等用户拍板 `review` 的出口；② **判据 9（会不会拖慢你正常的活）** 现在桌宠开着，
  可以直接用下一个真实回合评估；③ 判据 6 换时间基准重测；④ 判据 3（`needs-input` 端到端，
  已确认可做）；⑤ Proma 的采样探针 → 适配器。

- **止损**：若判据 9 不过就砍事件集或整个弃用通道 A，本轮以"映射层 + 客户端 + 一条明确的负面结论"收尾。

**M3 第三块：状态↔动作全盘复核（2026-09-18 完成，ADR 021）**：起因是用户报
*"感觉现在宠物状态有点乱"* —— **没有任何 agent 在跑，宠物却一直在炒菜**。
全盘复核九行素材的占用表后，结论是**四条**（`docs/design/m3-state-animation-audit.md` §0）：

- **A · 一条真缺陷（已修）：托底值取错。** `bubble-layer.ts` 的 `show()` 在从未
  `followPet()` 过时，把**气泡窗口自己的矩形**当成宠物矩形
  （`if (!lastPetBounds) lastPetBounds = win.getContentBounds()`），
  而主进程调 `bubble.show(text, badge)` 时**根本没传宠物位置** ⇒ 启动后第一次推气泡
  必然走这条兜底，气泡出现在屏幕正中。**与 ADR 017 那条"没有 `ts` 不等于刚刚"是同一类
  错误：兜底值取了一个"看起来像但不等于"的东西。** 修法：宠物矩形显式传进 `show()`；
  **拿不到就选择"不显示"，而不是显示在错的地方**。实测改前 `798,446`（屏幕正中）→ 改后
  `1561,809`（贴宠物正上方）。
- **B · `ready` 没有出口（已修）** —— 这就是"没 agent 在跑却一直在炒菜"的真成因。
  `ready` → `waving` → 落点 `review`（**第 8 行小厨师姿态**，`loop: true`）⇒
  干完一次活就**永久炒菜**；此前只能等 15 分钟静默兜底。
  **⚠️ 这里推翻了任务书初稿的一个推断**：初稿说"落点每 6 秒被反复重走"，
  用真实仲裁器复跑证明**不成立**（稳定输入下 `rev` 不动、渲染层收敛不动）。
  修法：`ready` 加**通报时效**（`statusTimeouts.readyMs`，默认 **60 秒**）到点退场回 `idle`；
  `ack()` 扩展为也能消解 `ready`（单击宠物 = 已读）。**注意不能复用 `SessionRecord.ts`
  计时** —— `ts` 每次心跳都刷新，拿它计时会让机制在自己要防的场景下失效；
  新增独立的 `readySince` map（单测钉住"心跳不推后时效"）。
- **C · 一处语义挤压（用户拍板，已改）**：第 5 行趴卧同时被 `blocked`（"已受阻"）
  与「打盹」（空闲）两种**相反**含义共用。按用户拍板："打盹可以是日常休闲动画之一，
  但 blocked 时**打盹的样子上应该出现文字提示**" ⇒ **`blocked` 气泡改常驻**
  （`bubble.stickyStatuses` 从 `["needs-input"]` 扩到 `["needs-input", "blocked"]`，
  并把它从 `holdMsByStatus` 的定时表上摘掉）。
- **D · `ready` / `running` 已分离（用户确认自己记混了）**：小厨师姿态（第 8 行）**同时**是
  `ready` 的落点与 `running` 的映射，**这才是"看着像没 agent 在跑却在炒菜"的观感来源** ——
  用户原话"只要你确保 running 和 ready 不一样就行"已满足：`running` = 第 7 行生日（稳定态），
  `ready` = 第 8 行小厨师（**且有 60 秒出口**），两者不同行、不同命运。
  **⚠️ 口径差异（需用户确认）**：用户拍板时写的是"`ready` 落到第 7 行生日"，
  但同一轮又说"确保 running 和 ready 不一样" —— **第 7 行是 `running` 的现行落点**，
  真改过去两者就撞行了。因此实施取**"保持现落点 `review`（第 8 行）+ 叠加 60 秒出口"**，
  这样既不撞 `running`，又消灭"永久炒菜"。**若用户更想要"生日 = 等你验收"的语义，
  改一行 `then` 即可**（`desktop-pet.json` 的 `statusMap.ready.then`），代价是 `ready` 与
  `running` 用同一个动作外观、只靠 60 秒出口区分。
- 另关闭一个疑点：`wb:default` 会话是 8-16 人工验收的残留
  （`origin=file, title=manual-acceptance`，39 小时跨度 114 条），**不是缺陷**。

**判据（全跑，全绿）**：单测 **219 → 255 项**（新增 ⑨b 段"ready 的通报时效"约 36 项）；
hook 单测 **70 项**；新增真实窗口探针 `spikes/m3-ready-exit/run.mjs`（**PASS**：
`0.1–0.5s` 第 3 行 → `0.6–4.2s` 第 8 行 → `4.3s→` 第 0 行，用 `--ready-ms=4000` 压时效）；
`m2-status/run-status-e2e`、`m2-menu/run-tray`、`m2-control/run`、`m3-behavior/run`（不带
`--no-behavior`）全 PASS。**`m2-hotkey` 的气泡定位/跟随用例 ✅**（位置从 798,446 → 1561,809）；
其**快捷键用例 FAIL 是既有环境问题** —— 已用 `git stash` 对照实验证明（未改动版本同样 FAIL；
本机 `Win+Alt+P` 不可用，日志显示降级为 `Control+Alt+P`），与本轮改动无关。



- **可以离开原位，但不超过几百像素**：有任务在跑（running / needs-input / blocked / ready）时，
  宠物每 **60–180 秒**沿地平线走 **60–300px**，方向朝**工作区中心**那一侧
  （默认蹲在右下角 ⇒ 观感就是"往左走几步"）；
- **锚点约束是结构性的**：目标由"进入任务状态时的位置"算，不由当前位置算 ——
  按当前位置累加会越踱越远，让"不超过几百像素"在几分钟后悄悄失效且无任何报错；
- **不作"忙碌动作"**：早先记的"运行中看起来像在忙"这条**待办作废**（用户不认这个动机），
  名字也不再使用；
- **不跨屏（锁定范围）**：只在宠物所在显示器的工作区内活动 ⇒ 拖到哪块屏就在哪块屏活动。
  用户明确暂不考虑多屏；
- **有任务时不计打盹**（`idleSinceAt` 恒为 null）；抑制条件与「减少动态效果」同空闲模式。

**M3 第一块：行为层（2026-09-17）**：宠物从"站在角落里循环待机"变成"**没人用它时像个活物**"。

- **只在主状态 = `idle` 时做大动作**：有任务在跑（running / needs-input / blocked / ready）时只踱小步
  （2026-09-18 由 ADR 019 修订，此前是"原地不动"）；
- **自主漫游**：每 25–90 秒沿地平线走 80–320px（速度 96px/s @默认缩放，按缩放线性换算，
  保证放大缩小后"每秒几个身位"的观感一致）；目标点**夹进工作区**，贴边就换方向；
- **微动作**：每 40–150 秒挑一个候选（挥手 / 跳跃）播一次；
- **打盹**：空闲满 5 分钟落 `failed`（复用趴卧帧），**单击或拖动即醒**、重新计时；
- **四条抑制**：拖动中 / 宠物被隐藏 / 全屏让位 / 控制条打开 → 一步都不动；
  系统「减少动态效果」下不漫游不做微动作（打盹这种静态姿态仍然允许）。

分层沿用既有架构：规则 = 纯函数（`kernel/behavior.ts`，时钟与随机数可注入）｜接线 = `main/index.ts`｜
渲染 = 哑渲染层（接住 `CH.behavior` 覆盖，覆盖期间不收敛回主状态）。

判据：单测 **138 → 191 项**（新增 ⑭ 段 22 项）；新增真实窗口探针 `spikes/m3-behavior/run.mjs`
7 条全过（真的在走 / 只沿地平线走 / 不越界 / **位移行号与方向一致 8/8** / 抓住不动且松手恢复 /
控制条开着不动 / running 期间不动 / 打盹画第 5 行且单击能醒）。
**两条只有实测才发现的坑**：① 打盹计时若被漫游重置，"每 25–90 秒走一次"会让它**永远睡不着**
（屏幕上只表现为"它就是不打盹"）；② 自主行走会让既有的**位置类断言集体变脆** ——
7 个回归探针因此统一加了 `--no-behavior` 接缝。

**M2 ④ 交互模型重做（用户拍板，ADR 016）**：**悬停唤出整条路径删除** —— 桌宠常驻角落、光标是
"顺便"掠过的（拖窗口、去任务栏、切应用都会经过），任何自动弹出都必然产生"我没叫它它自己冒出来"
的体验，延迟只降频不改性质；而且左键单击要播动作，"停在它身上"不该带第二个含义。
现在唤出只有三条**显式**路径：**右键宠物** / `Win+Alt+P` / 托盘菜单「控制条」，一律**抢焦点**；
关闭：Esc / × / 再唤出一次 / 点到别处（失焦 200ms）/ 宠物被隐藏。
**两处右键分工**：宠物右键 = 控制条，托盘右键 = 完整菜单（面板的「⋯」也是这份）。
面板的动作排从"只读的 70%"换成**宠物名**（取 `pet.json` 的 `displayName`）。
`kernel/bar-policy.ts` 因此从"七条规则 + `armed`/`suppressUntil` 两个补丁位"缩到**五条规则**。
新增一条机制：**`⋯` 弹原生菜单期间屏蔽"失焦即收"**（原生菜单会夺焦，不屏蔽则面板与菜单一起消失）。

**M2 ④ 缺陷修复（ADR 017）**：① 快照里**没有 `ts`** 的会话此前被内核兜底盖章成"现在"，
于是昨天写的 `running` 在启动后"新鲜" 15 分钟（"一启动就显示某某在运行中"）——
改为用**快照的 mtime** 兜底，且这类条目不参与"ts 变了算心跳"那条分支；
② 菜单「清空状态会话」此前只清了文件：宠物确实松手了，但**面板照旧列两行 idle、
菜单照旧写「（2 条）」** —— 改为**文件 / 适配器记忆 / 仲裁器记录三处一起清**。

**M2 ③ 已完成（2026-09-16）**：状态**可读**了 —— 气泡层（独立窗口，不扩大宠物窗口）显示状态文案，
多会话时带 `+N` 角标；全局快捷键 `Win+Alt+P` 切换宠物显示/隐藏。
实测：快捷键真实击键触发；气泡按策略显示/2 秒收起/常驻（needs-input）；拖动宠物时跟随；
**新增窗口没吃掉任何点击**（命中图误吃 0）。详见 ADR 012。
**人工验收通过**（用户逐项测过快捷键、气泡、角标、跟随），并修掉两项观感缺陷（ADR 013）：
① 文字下缘被裁（`line-height: 1` 使行盒短于字体行高，被省略号必需的 `overflow:hidden` 切掉下缘）；
② 文字没水平居中（flex 默认左对齐，宽度估算多出的余量全落右侧）。
判据做成了**渲染层面**的差分测量（同一帧截两次，关掉 overflow 前后比对墨迹行范围），不依赖字体公式。

**M2 ② 已完成（2026-09-16）**：托盘菜单与宠物右键菜单，两处共用一套模板与一张动作表。
落地项：状态行、隐藏/显示、宠物大小（0.5–1.5）、重置大小、开机自启、退出。
