## 做了什么（按实际执行顺序）

### 一、先修代码，再跑探针（顺序刻意如此）

先做不需要 GUI 的部分：打包事务化、事件日志、定时器守卫、字段白名单、
以及三处零覆盖的判据。原因是**跑一次探针要几分钟**，而代码改完再跑能一次验完。

### 二、探针第一次跑就抓到我自己写的 bug

单实例锁的第一版把 `app.whenReady()` 写进了 `else` 分支 —— 于是"跳过锁"那条路径
**根本没有注册启动逻辑**，宠物窗口从未被创建。探针报：

```
[probe] 失败：Error: 未等到桌宠窗口
```

而日志里只有一条"已跳过单实例锁"的**正常警告**，看不出任何异常。
**这类错误看一眼屏幕只会觉得"宠物没出来"，是探针把范围缩到了 5 行代码里。**

### 三、重跑污染证据 ⇒ 抓出第四个退出崩溃

这是本轮最有价值的发现。修 P0-1 时按纪律重跑 `spikes/m3-ready-exit`，新证据里出现：

```
[probe] 判定：PASS
[uncaught] TypeError: Object has been destroyed
    at Timeout.tickBehaviorLayer [as _onTimeout] (dist/main/index.js:1036:43)
```

**功能全对、退出路径崩了一次。** 两个独立成因：

1. 停表挂在窗口的 `hide` 事件上，而**窗口销毁不触发 `hide`**、只触发 `closed`；
2. **`clearInterval` 之后，已经在定时器队列里排期的那一次回调仍会跑**。

两道都堵：补 `on('closed', stopTimers)` + 回调开头 `isDestroyed()` 守卫。

⇒ 这条崩溃**至少存在了一周**，之所以没人知道，**是因为那三份证据在把"崩溃过"说成"通过"**。
这正是 P0-1 被列为"最该先做"的原因 —— 它的代价不是那次崩溃，而是**所有基于那些证据的结论**。

### 五、顺带修掉三个"判据自身"的缺陷（都不在审计清单里）

1. **`stripComments` 会吞掉几百行代码。** 单测的结构性检查用它去注释，
   而它是跨行匹配块注释的 —— 本工程注释里会写出「`dist/` 紧跟两个星号」，
   那正好是一个块注释开始符。后果：改 `make-portable.mjs` 后 **9 条打包断言全部失败**，
   而根因是**被断言的那段代码本身被剥掉了**。这类失效**不报错**，只是安静地找不到字符串。
2. **`run-status-e2e` 用 `spawnSync` 调 hook** ⇒ 本沙箱里进程根本没起来，
   六个步骤全判 `hook 调用失败：null` ⇒ **整条判据 FAIL，而它要测的东西从未被触发**。
   改异步 `spawn` 后 6/6。
3. **两套状态探针的断言与 ADR 024 之后的设计不同步**：它们仍期望"过期的会话留在面板视图里、
   只是标了 expired"，而 ADR 024 改的正是"过期项**同时从输出与视图退场**"。
   更新断言的同时把原意图换成更强的判据（**上游改口 running 时必须能回来**）。
