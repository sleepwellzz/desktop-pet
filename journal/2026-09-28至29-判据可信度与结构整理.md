# 2026-09-28 夜 · 判据可信度与结构整理

## 为什么做这一轮

用户问了两件事：

1. 「我们在这种软件开发过程中需要具备哪些技能？GitHub 上关于 AI Vibe Coding 有很多推荐的技能或
   工程过程的约束，我不太懂。我在想模型能力的边界是否适合一个稳定的开发过程，
   是否需要引入这些技能来实现更好的迭代。」
2. 「我观察到我们现在的仓库、代码以及文件的排布，从外行人的角度来看显得有些杂乱无章，
   缺乏结构化的感觉。」

用户批准了三个方向：① 修判据可信度 ② 结构整理 ③ 补交接承接性。

## 核实先于动手：项目的约束已经比 GitHub 规范更严

动手前先数了一遍现状，发现**用户的前提需要修正**：

| 维度 | 现状 |
|---|---|
| 已决策记录 | `docs/decisions/` 46 条 ADR + INDEX 路由表 |
| 分主题硬约束 | `docs/constraints/` 6 份，AGENTS.md 按"改什么 → 读哪份 + 跑哪些判据"路由 |
| 过程记录 | `journal/` 33 篇按日 |
| 平台行为验证 | `spikes/` 17 个探针目录、118 个入库文件 |
| 状态管理 | PLAN.md 含状态表 + 挂起清单 + 变更路由 |

对照 GitHub 上"vibe coding 工程规范"的典型内容（规则文件、阶段门禁、小 diff 纪律、TDD、CLAUDE.md），
**这些全都已有，且是被真实事故打出来的**：

- 平台行为一律用探针实测，不要推断 —— 已有**六次**推断被实测推翻
- 位置类参数必须显式传入 —— ADR 021
- **"发生了"不等于"表现对了"，且"有证据"不等于"证据属于这一次"** —— ADR 035 / ADR 038 / 09-22 那次
- **"写了一个守卫"不等于"守住了"** —— ADR 042

⇒ **结论：不引入任何外部规范包。** 理由不是"不需要"，而是**会变坏**：
审计（`docs/reviews/2026-09-28-全面代码复核.md`）已查出同一件已删除的事在**五份文档里有五种状态**，
`docs/acceptance.md` 六处写 `1.0.0` 而实际是 `1.0.1`。
**再叠一层通用规则，只会让"文档说的"与"实际跑的"差距更大。**
缺的不是新纪律，是**让现有判据可信**。

## ① 判据可信度（ADR 047）—— 主单测 446 → 452 项

### 三个 P0 其实是同一件事：判据报"通过"不需要真的验过

| 编号 | 病 | 本轮处置 |
|---|---|---|
| P0-10 | 1885 行行为测试跑在 `dist/` 上，而**无任何守卫保证 `dist/` 是本轮构建的** | 构建戳 + ⓪ 节硬失败 |
| P0-9 | 删功能时调试钩子被静默删掉，探针不是报红而是"跑不出证据" | 静态守卫 + ⓪b 节硬失败 |
| P0-1 | 六份入库证据内含 `[uncaught] TypeError` 却报 `PASS` | 扫出来、列清单、建常态检查 |

### 构建戳：为什么是内容哈希而不是 mtime

新增 `tools/stamp-build.mjs`：构建成功后把 `src/`（`.ts/.tsx/.js/.json/.html/.css`）
全量内容的 SHA-256 前 16 位写进 `dist/.build-stamp.json`；
`tools/status-arbiter.test.mjs` ⓪ 节不一致就 `process.exit(2)`。

**不用 mtime 的理由**：mtime 在本项目**已经骗过人一次** —— P0-1 那批证据内容是 09-18 的、
mtime 是 09-22 的，"比 src 新"成立而"是这次跑的"不成立。
而 `AGENTS.md` 纪律 3(b) 问的正是后者：`git checkout`、文件复制、`touch` 都会重写 mtime，
**它回答不了那个问题**。哈希只认内容。

### 三处关键的取舍

1. **硬失败而不是记一条断言**：此刻后面 450 项**全都跑在旧 dist 上**，
   它们"全绿"这件事本身已经没有意义了。一条 `FAIL` 混在 450 项里会被滑过去。
2. **戳只在全部编译成功后写**：提前写戳等于给一次失败的构建发通行证。
3. **不做"测试前自动构建"**（更彻底但被否）：那会掩盖"你到底测了什么"，
   且是 P0-2/P0-4 那类漏洞的温床（人会为了跑通测试而跳过构建检查）。

### 探针钩子静态守卫：能便宜发现的，不要留到贵的那一步

新增 `tools/check-probe-hooks.mjs`：**不启动 Electron**，
抽出 `src/main/index.ts` 里 `__petDebug` 桥的键名，与全部 `spikes/*/probe*.js`
的 `dbg.<name>(` 调用逐一核对。接进 ⓪b 节，硬失败。

**核心判断**：钩子被删这件事**不需要启动 Electron 就能发现**。
只放在独立脚本里 = 需要人记得跑；接进主测试 = 每次跑测试都会撞上它。

**它当场抓出了一处审计漏掉的**：`spikes/m2-control/probe-key-path.js:97` 也命中 `dbg.hotkey()`。
去注释后确认那是**一条正确维护过的注释**（"（原日志里的 `快捷键=${dbg.hotkey()}` 已随全局快捷键一并删除，ADR 032。）"），
该处在 ADR 032 时已被正确清理。
⇒ **判据把注释当代码，它的失败就会变成噪音，而噪音是让人忽略判据的头号原因**（ADR 044 §2 同款纪律）。
所以匹配前必须去注释。

### 证据不许被失败的判据销毁

`spikes/m2-hotkey/run.mjs` 改为：经 `PROBE_LOG`/`PROBE_REPORT` 环境变量
把探针输出指到临时文件，**确认真的拿到新报告后才 `rename` 覆盖**；
中途抛错则旧证据原样保留 + 打印说明 + 退出码 1。

⚠️ **必须同时改探针侧**（`probe-bubble-hotkey.js` 顶部读这两个环境变量）。
只改驱动侧会出现"探针把正式那份截断重写、rename 又拿临时那份盖回去"，
判据失败时**仍然**会毁掉旧证据 —— **这正是"改了但没改全"的形状，本轮实际踩过一次才改成现在这样。**

### 删掉失效用例

`probe-bubble-hotkey.js` 移除"注入真实击键验快捷键"用例（ADR 032 之后钩子已不存在），
连带清掉不再被使用的 `keybd_event` / `VK_LWIN` / `VK_MENU` / `VK_P` 声明。
控制条键盘与焦点行为由 `spikes/m2-control/probe-key-path.js` 负责，**不搬回气泡探针**。

## ② 入库证据的归属：spikes/ 文件数不减少（ADR 048）

用户的"杂乱"感受里有一项是 `spikes/` 下 118 个入库文件。**核实结论与直觉相反**：

| 类别 | 数量 | 被引用？ |
|---|---|---|
| 探针源码 | 66 | 是 |
| 组件截图 | 8 | 是 |
| **判据产物** | 42 | **是** |

逐个查了 42 份产物被谁引用（排除"被 run.mjs 写"这种自引用）：
**ADR 008 / 014 / 023 / 035 / 038 / 039 逐一点名了具体文件**，
`docs/constraints/window.md` 也直接读 `m2-hittest/fs-verify.json`。

⇒ **"把可重跑产物出库"不是清理，是切断决策链。**
`fs-verify.json` 一删，ADR 023 的"实测过了"就变成一句没人能复核的话。

**真正的噪声源是 9 份 `.out`**：逐个查过，**没有任何脚本写它们** ——
是 `node xxx.mjs > run.out` 这种手工重定向的产物。
危害不只是 diff 噪音：重定向把 stdout 与 stderr 混在一起，
于是 `[uncaught] TypeError` 后面紧跟一句 `全部探针 PASS` —— **一份自相矛盾的证据**，
而它就此入库并被 ADR 引用。

新增 `tools/check-evidence.mjs` 静态扫这类自相矛盾，扫出 **3 份 error**（P0-1 说的是 6 份；
本口径把"含异常但未声称通过"的单列为 warn，只把自相矛盾的算 error）：
`m2-control/run.out`、`m2-menu/run-tray.out`、`m3-ready-exit/ready-exit.log`
—— 全是 `Object has been destroyed` 之后仍报 PASS，**正是 ADR 035 修掉的那个崩溃**。

### 一条值得单独记住的取舍：⓪c 刻意不阻断

这三份**只能靠重跑探针修**，而重跑要启动 Electron（本轮用户已决定不跑）。
若做成硬失败，主测试就会**长期亮红** —— 而 PLAN §4 #16 记的正是
"偶发失败如何被磨成待观察、最后不再当作已通过"这个过程。
**长期亮红 ⇒ 判据被忽略 ⇒ 判据彻底失效，这比少一条检查更坏。**

⇒ 判别标准写进纪律：**能立即修的才做成阻断闸门（⓪ 与 ⓪b），
历史遗留的只做成提醒（⓪c）。** 前者防"此刻正在发生的错误判断"，
后者防"已入库的历史污染"，性质不同。

## ⚠️ 如实记录：一次操作失误

为检查 `spikes/m2-hotkey/run.mjs` 的语法，用了 `node -e "import('./spikes/m2-hotkey/run.mjs')"`。
**它不是纯导入** —— 顶层就 `spawn` 了 `electron.exe`，**探针真的跑起来了**。
而审计报告明确写着这类操作"需用户确认能否在这台机器上跑"。

已 `taskkill` 清理，无残留进程。副作用：三份 `m2-hotkey` 证据被改写。
**原内容是 ADR 032 之前的 `FAIL` 残留**（`accelerator: "Control+Alt+P"`），
新内容是 `PASS`、日志零 `[uncaught]`、已不含失效的 `hotkey` 段 ⇒ **信息上更准确**。
已向用户报告，用户确认**保留**。

**但它不是一次经批准的验证，这一点必须留在记录里。**

**教训**：验证一个驱动脚本能否正确解析，**不能靠 `import` 它** ——
`run.mjs` 顶层就有副作用。**用 `node --check`。**

### 为什么不直接改 README（这一步的推理）

README 改起来只是一句话，但**它写什么取决于能不能给出一个真链接**。
当时核实到的现状是：**确实没有下载入口** —— 仓库无 Release（`No releases published`）、
`dist-win/` 被 gitignore。而用户明确说过不要往公开仓库丢大二进制。
⇒ 所以我当时写的是“目前没有公开发布的预编译包”—— 那是**如实陈述**，不是偷懒。

现在用户要发布，我不能把那句改成“有下载”却**不给出任何入口** ——
那会比原来更坏：**访客看到一个“有”的声明，却找不到在哪拿**。
⇒ 先问用户选哪种分发方式，用户选了「建 GitHub Release」。

### 公开附件必须体检（这是 ADR 048 思路在分发侧的延伸）

上传前把 zip 独立解压，逐项扫本机路径 / 用户名 / 邮箱：

- 唯一命中：`LICENSES.chromium.html`。
  **没有就此放过** —— 先查清命中的是什么，再用 **SHA-256 与
  `node_modules/electron/dist/` 下那份逐字节比对** ⇒ **完全相同，是 Electron 官方包原件、
  未被改动** ⇒ 不是泄露，而是超长行导致的显示截断。
  **“命中了”与“真的泄露了”是两件事**，后者才需要前者的两倍证据。
- 另扫：`resources/app/` 内部（我方代码）**零命中**；文件名扫无 `lingw`/`Possesions`；
  **无 `pet.log`、无 `.jsonl`**（避免把运行时日志传上去）。

### 一件必须核实的事：`gh release create` 会不会改写 tag

`gh release create v1.0.1 --target main` **有可能**新建或移动 `v1.0.1` tag ——
而 ADR 045 明写「**已发出去的版本号不能回收**」。

⇒ 事后用 API 查：远端 `v1.0.1` **仍指向 `49d82e5`**，未被改动。**好在没动。**
但这条得记下来：**下次用 `gh release create` 时，务必拿一个明确的 commit 而不是 `main`**，

⇒ 我先去验证了「重打包出来的东西到底是不是同一个」，再打包：

用 `Expand-Archive` **独立解压新旧两个 zip** 做**全量 SHA-256 比对**：

| | 旧包（09-23） | 新包（09-29） |
|---|---|---|
| 文件数 | 236 | **237** |
| zip 大小 | 164,397,015 | **164,397,284**（+269 字节） |

差异逐项查明，共 4 处 + 1 个新增，**全部是构建期元数据**：

2. `resources/app/package.json` —— 本轮加的 `build` 尾巴与两个新 script

4. 新增 `resources/app/dist/.build-stamp.json` —— 本轮构建戴

**关键一条**：`resources/app/dist/main/index.js` 的 SHA-256 两包**完全相同**
（`abedc20b45897ecac91897c081df28efc698fb16`）⇒ **运行时行为逐字节一致**。

⇒ **本次属「同物」，不违反 ADR 045 那条禁令。** 这也是为什么值得把核验过程写下来：
**"同名"本身不构成问题，"同名且运行起来不一样"才构成问题。**

**但也正因如此，不跳号这个选择的收益其实是 0** —— 没人真的需要这个新包，
它的唯一作用是**避免为纯工具改动虚构一次版本跳跃**。这一点我如实跟用户说了。

### `v1.0.1` tag 为什么没重打

ADR 045 要求"每次交付给当前 HEAD 打 `v<版本号>` 的 tag"。但 `v1.0.1` 已存在于本地与 GitHub、
指向 `49d82e5`，而 **Git 不允许同名 tag 指向另一个 commit**。
而 ADR 045 同时写着「**已发出去的版本号不能回收**」⇒ 重打属于回收行为。
用户确认：**保持不动**。
