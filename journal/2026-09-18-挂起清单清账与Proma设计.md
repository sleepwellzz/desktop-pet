## A · 双通道运行期告警（清单 #2 的告警版）

此前 ADR 020 的"一个 agent 只由一条通道负责"只是文档里的一句话，**违反时没有任何输出**。
本轮让它第一次可观测：

1. **通道打标**：hook 客户端 `tools/pet-hook-cb.mjs` 写入条目时带 `origin: 'hook'`；
   文件适配器 `src/source/status-file.ts` 的 `Entry` 增 `origin?`，两处 `send()` 都发 `e.origin ?? 'file'`。
   `origin` 走投毒点纪律：**限长 32、白名单 `[A-Za-z0-9_-]+`、不合法就丢**（不原样透传）。
2. **检测**：`StatusArbiter` 按 `sessionId` 记 `lastOrigin`，`ingest()` 里判
   **同一会话 10 秒内换通道** ⇒ 打一条 `⚠️ 双通道冲突` 日志；通道对排序后做冷却键，**60 秒内只报一次**。
3. **清账**：`clearSessions()` 与 `pruneStale()` 一并清掉记忆，避免陈旧记录造成误报。

**刻意不做逐出。** 同一会话被两条通道同时盯时该留谁，是产品决策（留哪条取决于用户对"哪个来源更可信"
的判断），不是实现细节；本轮只把"发生了"这件事送到日志里，机制级收口留给另一轮带设计的改动。

## B · `isAckable` 下沉内核

ADR 022 里 `ready` 消不掉的**成因一**是"渲染层与内核各写一份'什么算待确认'"。
上层早就改对了（`needsAck` 补上 `ready`），但**结构性根因还在**：两处仍然是两个字符串比较。

- `kernel/status.ts` 导出 `isAckable({ status, acknowledged?, expired? })`；
- `renderer/control-bar.ts` 删掉本地 `needsAck`，直接 `import { isAckable } from '../kernel/status'`；
- 内核 `ack()` 的 `want()` 改为调用同一个谓词 —— **三处判据收敛成一个函数**。

测试补了三层，其中第三层是关键：

- 20 组真值表（五种状态 × 已确认 × 已过期）+ "恰好 2 组为真"的计数断言；
- 五种状态下 `ack()` 的记账与谓词**逐一对齐**（防止只改一处再次失配）；
- **源码级断言**：读 `control-bar.ts` 的源文件，断言它 import 了内核谓词、且不再出现
  `s.status === 'needs-input'`。

第三条是本轮最有价值的一笔：**"结构性"要靠源码级断言钉住，不能靠"我记得改了"。**

## C · `ready`/`stale` 时间边界探针

新增 `spikes/m3-ready-ack/probe-ready-stale-boundary.mjs`（离线、秒级，**18/18**），四个场景：

| 场景 | 结果 |
|---|---|
| `ready` 59 秒 | 仍是 `ready`（用户还来得及看见） |
| `ready` 61 秒 | 退场回 `idle`，且 `expired = true` |
| 每 15 秒重报 `ready`、持续 16 分钟 | **主状态已回 idle，但面板那一行仍在，且带「（已过期）」** |
| 心跳停止满 15 分钟 | `pruneStale` 才把它扫掉 |
| `running` 14:59 / 15:01 | 静默兜底边界正确 |

**顺带推翻交接文档的一处推断。** `docs/HANDOFF-2026-09-18.md` 推测"重报 16 分钟后 `viewSessions()`
会空" —— 实测**不会**：`pruneStale` 的判据是"最后一次心跳的年龄"，而重报本身就是在刷新心跳，
**只要上游还在报，这一行就永远不消失**。

这已经不只是"探针补全覆盖"了：**「（已过期）」在生产的重报节奏下会长期挂在面板上**（而生产的
`origin: "file"` 条目确实每 15–60 秒重报一次）。三选一留给用户在 PLAN.md §4.5 #14 拍板：
保持现状 / 过期即从面板隐藏 / 过期即视为会话结束。

## D · preload 诱饵文件

`tsconfig.json` 排除三个 preload；另建 `tsconfig.preload.json`（`extends` 主配置、`noEmit: true`、
只 include 三个 preload）。`package.json` 的 `typecheck` 改为跑两份配置。

**一个坑**：`extends` 会**继承 `exclude`**，主配置里那句排除会把 include 完全抵消 ⇒ `TS18003
No inputs were found`。必须在子配置里显式写 `"exclude": []`（已加注释说明原因）。

`dist/main/preload-bar.js`、`preload-bubble.js` 这两个**永不被加载但会随源码同步更新**的诱饵
从此不再产出 —— 少了"产物时间戳变了就以为生效了"的假象来源。类型检查一份没丢。

## E · 隐藏时暂停定时器

`main/index.ts` 把 33ms 行为 tick 与 16ms 光标轮询收进 `timers` 记账，由 `show`/`hide` 事件
驱动 `startTimers()` / `stopTimers()`（幂等），`quit()` 与 `app.on('will-quit')` 也停。

**250ms 的仲裁器 tick 故意保留** —— 隐藏期间托盘状态、气泡、面板仍要更新；停掉它会让"宠物藏起来时
状态面板冻结"。

新增 `spikes/m3-hidden-timers/`（驱动 + 渲染层探针）：可见时 ≈17 ticks/800ms；隐藏后
**0 ticks/1000ms** 且 `timersRunning = false`；恢复后回升 ⇒ **PASS**。

连带修掉一处：退出时定时器晚于窗口销毁 ⇒ 日志里 `Object has been destroyed`。现在 `quit()` 第一件事
就是 `stopTimers()`。

## F · Proma 被动源（**只出设计，未写代码**）

`docs/design/m3-proma-passive-source.md`。要点：

- **契约复用 `StatusSource`**，`sessionId` 前缀 `proma:`、`origin: 'proma'`；
  增量读 jsonl（按字节偏移，mtime/size 双守卫）；活动窗口 X 与条数上限 N 由采样定，不拍脑袋；
- **映射草案**：running ← 近期有 assistant 追加；ready ← 末尾出现 `type:"result"`；到期即 idle；
  **不给 `needs-input`** —— 没有信号源就是没有，编一个就是假阳性；
- **判据 6 的修法**：主进程 `recordEvent()` 加 `recvAt: Date.now()`，延迟 = `recvAt - ts`
  （现状只有写侧的 `ts`，拿它算端到端会严重低估，ADR 020 已实测）；
- **判据 9** 是四道主观题 + 一个数值上限，只能由用户在真实回合里回答；
- **止损**：采样若显示 Proma 也只能给"存在性"（与 WorkBuddy 同款），**不接**，如实记负面结论。

三项待拍板：P1 接受"Proma 不给 `needs-input`"；P2 采样只给存在性则不接；P3 适配器默认 `enabled: false`。
**另需用户配合一件事**：采样期间要在 Proma 里真的干一次活（≥150 秒），否则采样探针的 Q1 无解。

## 想清楚的两件事

**一、可观测性先于处置。** 双通道冲突这件事，机制级逐出需要产品设计（留哪条通道、是否要用户介入），
但"它正在发生"这件事**不需要任何决策**就能送到日志里。先把可见性做掉，处置那一步才有真实的
触发频率数据可依 —— 否则设计文档里连"这事多久发生一次"都只能猜。同理，"只告警不逐出"必须写进
ADR，免得下一轮有人看到告警却找不到处置，误以为这是没做完。

**二、文档里的推测也是推测。** 交接文档推测"重报 16 分钟后面板会清空"，写它的时候是认真的，
但它没被实测过；C 的探针一跑就被推翻，而且推翻的方式很具体 —— `pruneStale` 判的是心跳年龄，
**重报就是在刷新心跳**。这与本项目"平台行为一律实测"那条纪律同源，但这次栽在**自己的文档**上：
**不是只有平台行为需要实测，自己的推断同样需要。**

### 一、#14 判定为 bug，已修（ADR 024）

用户答复："看不懂你说什么，反正如果你觉得是 bug，就修复。先制定计划，然后完成修复即可。"

**判定为 bug 的三条依据**（而不是"三种可选的产品风格"）：
1. ADR 021 的"出口"原则**只落地了一半** —— 60 秒时效改了仲裁输出，没改面板视图；
2. 留下的这一行 `isAckable=false` ⇒ **不给按钮 ⇒ 用户没有任何手段消掉它**；
3. 而"等 15 分钟静默兜底"在生产里**永远不会发生**（重报刷新 `ts`）。

否决的另两个选项：**删记录**会造成周期性复活（重报时 `readySince` 重设 ⇒ 每 60 秒炒一次菜）；
**给过期行加按钮**是让用户去确认一条已经结束的通报，语义上是撒谎。

修法一行：视图过滤（`!(status==='ready' && effectiveStatus!=='ready')`）。范围窄、不删记录。

**连带发现（值得单独记）**：`ack()` 对 `ready` 是把 `readySince` 拨回"已过 60 秒"，
所以修复后"确认一条 ready"的表现从"行还在、标已读"变成**行直接消失**。这是对的，
但**两处断言的观测方式必须跟着改**（单测 ⑯、`probe-ack-revival` 情形 3）—— 改完才绿。

**判据**：单测 294 → **304**；边界探针 18 → **27/27**；ack-revival 13 → **14/14**；
stale-sessions 22/22；真实窗口 `m3-ready-exit` **PASS**（4.3s 行号 8→0）、`m2-control` **PASS**；
hook 70 项；typecheck 0 错。

**教训**：**一条规则跨层生效时，每一层都要有判据。** ADR 021 那轮的探针测的是渲染层画的行号，
它 PASS 是对的；面板那一半没人测，于是出口只走了一半而不自知。

### 五、判据 6 落地 + 挂起 #8/#9 清账（ADR 026）

**判据 6 的时间基准**：`recordEvent()` 加 `recvAt`，端到端延迟 = `recvAt - ts`。

`--since=` / `--budget=`；**无 recvAt 的旧记录单列计数不参与统计** —— 否则"测不出来"会被误报成
"延迟很低"）与 `spikes/m3-latency/run.mjs`（启动桌宠 + pet-hook 喂状态 + 回读判定的真实验证，PASS）。

**顺手清掉两笔小账**：#8 `badgeCount` 注释（实现是对的，注释说窄了 —— 它不限于"要求注意"两类，
running/blocked/ready 都算）；#9 `STATUS_TEXT` 从 `Record<...>` 注解改成 `satisfies Record<...>`

否决"后到者胜"（那正是来回刷的机制）与"先到者锁定"（启动时往往先读到快照，会把被动源永久锁死）。
选 **hook（事件驱动）优先于被动源** —— 与 ADR 020"被动源是降级来源"完全一致，
且实践中 hook 的信息一定比被动源准。带**锁过期**作为安全底线（hook 挂了不会让宠物永久失明）。

**#12 HTTP 状态源 → 降级为"不做"**（两条通道已够，没有 agent 需要第三种；接口留着）。
**#13 打包那轮 → 保留，不是"前期可忽略"**：它挂在"被误判为流氓软件"这个高风险项下，
触发条件 = 开始打包。

### 七、无控制台启动 + 日志落盘（ADR 028）

用户："必须挂着命令窗口，一旦关闭宠物就退出。这不符合宠物软件驻留后台的形式吧？"

**根因是启动方式，不是宠物不支持后台**（实测不是推断）：
`electron.exe` 是 **GUI 子系统** —— 不隐藏窗口直接 spawn，`conhost.exe` 数量 **14 → 14 不变**。
旧脚本的黑窗口来自 `npm start → node.exe`（console 子系统），**而它正是宠物的父进程**
⇒ 关窗即退出。**推论：开机自启天然无控制台**（注册表里写的是 electron.exe 不是 node）。

做法：新增 `启动桌宠-后台.bat`（先可见构建，再 `start "" electron.exe .`，窗口 3 秒后自关），
**不需要 PowerShell**（原打算用 `Start-Process -WindowStyle Hidden`，实测证明多余）；
日志落盘 `~/.desktop-pet/pet.log`（包装 console 三件套，**每次启动截断**；
渲染层 console 本来就转发到主进程，一并进文件）。保留原 bat 给开发/排查用。

**我自己踩的坑**：第一版 exit=1，日志里 `'控制台' 不是内部或外部命令` —— 我在 `.bat` 注释里
写了中文，cmd 按 GBK 解析成了命令。**这正是本项目自己的硬约束**，而我在知道它的情况下违反了，
因为"只是加几行注释"看着不像改代码。已把"改 .bat 必须脚本校验非 ASCII 字节数 == 0"写进构建约束。

**没验的部分（如实标注）**："关掉所有窗口后宠物是否长期驻留"我这边验不了 —— 自动化环境在命令
结束时清理整个进程树（脚本退出后 electron.exe 归零）。用户从资源管理器双击不受此影响，已请他验证。

### 八、接续（2026-09-21）：修 bat + 双通道逐出（ADR 029 / 030）

**用户反馈**：① 用了后台启动的 bat，**关掉窗口后宠物仍然消失**；② 授权我做双通道逐出；
③ 问我"这轮先跑判据 9 还是先做 #2"。

#### 1. 无控制台启动的修正（ADR 029）—— 推翻我自己上一份 ADR

**结论**：`start "" electron.exe` 不行，改回 `powershell Start-Process`。

**实测**（空壳 Electron，三方式各起 3 个进程，用 explorer 启动 bat 模拟双击，再 `taskkill` 不带 /F 关窗）：

| 方式 | 关窗后 |
|---|---|
| `start ""`（ADR 028 的写法） | ✗ **全部被带走** —— 完整复现用户现象 |
| `Start-Process`（我的第一版） | ✓ 3/3 存活 |
| node `DETACHED_PROCESS` | ✓ 3/3 存活 |

**我错在判据不纯（第三次）**：ADR 028 里我测的是"启动 electron 时 conhost 数量不变" ⇒
推断"它没有控制台 ⇒ 关窗不影响它"。但要证明的命题是"**它有没有附加到 cmd 已有的那个控制台**"
—— 不新建控制台，完全可以附加。**我拿一个支持不了结论的数字下了结论。**

中间还有一次：想用 `AttachConsole(pid)` 做精确判据，结果它对每个进程都失败（**忘了先 `FreeConsole()`**），
差点得出"三种方式都没控制台"。**判据工具自己没校准，会稳定地给错误答案。**

最后收口靠"直接测命题本身"（关窗后存活与否）。已把这条写进 `constraints/build-probe.md`。

#### 2. 双通道逐出（ADR 030）

规则：**按通道优先级，不按到达顺序** —— hook 高于被动源；低优先级上报被丢弃；
`holdMs` 10 分钟释放作安全底线；无 `origin` 的人工喂状态永远放行。
配置 `desktop-pet.json → statusTimeouts.dominance`。

**实施时踩到并修正的一点**：最初把逐出放在 `ingest` 最前 ⇒ 单测 ⑮ 的
"冷却过后再次冲突会重新告警"立刻变红（期望 2 实际 1）。根因：**逐出生效后低优先级事件
根本走不到告警逻辑** ⇒ "有两条通道在盯同一个会话"这件事再也不报警，而那正是用户要知道的。
改成 **告警（诊断）在前、逐出（处置）在后**，两者独立。

**判据**：单测 294 → **319**（⑮c 新增 15 条）、`probe-ack-revival` **14/14**、
`probe-ready-stale-boundary` **27/27**、`probe-stale-sessions` **22/22**、hook **70 项**、
typecheck / build 0 错。
**真实窗口回归待补**（`m3-ready-exit`、`m3-latency`）—— 它们要启停桌宠，与用户正在测的实例冲突。
