# 2026-09-18 · 用户报告缺陷修复 + 工程级审查

## 本轮起点

用户对上一轮（M3 第三块）的修复质量认可，提两件具体的事 + 一个功能要求 + 一次工程级审查：

1. **启动耗时明显增长，已达到数秒**；
2. **agent 干完后 `ready` 的炒菜动画一直保持**，点击或确认都不回待机；悬浮条里仍写"就绪但结果待确认"；
3. **要求在悬浮条加一个「已确认」按钮**，用来消掉这类状态、让宠物回默认；
4. **用审查 skill 做一次完整的工程级代码审查与复盘**。

## 做了三件事

### 一、启动耗时：定量归因，发现瓶颈完全不在应用代码

先写计时器再说话 —— 新增 `--trace-boot` 接缝（生产零开销）与 `spikes/m3-startup/` 两个脚本
（`run.mjs` 走 Electron 打戳，`run-cost.cjs` 分三段量）。三次取样一致：

| 阶段 | 耗时 | 占比 |
|---|---|---|
| `npm run build`（无条件全量） | **29,941 ms** | **93%** |
| `npm start` 的 npm 引导 | 1,232 ms | 4% |
| Electron → 窗口可见 | 871 ms | 3% |

`boot()` 内部只花 **322ms**。再拆构建链（`tools/run-build.cjs`）：有效构建只有 ≈5.3s
（tsc 3.3s + 6×esbuild 1.4s + copy-assets 0.6s）—— **差的 24.6 秒全是 npm 自身的解析/加载开销**。

这一步的价值在于**把"数秒"从感觉变成了三个数字**，而且立刻排除掉了一整类可能的怀疑对象
（Electron 启动慢？宠物包解析慢？窗口多？—— 全都不是）。

优化方案写了三步（构建改按需 / 去掉 npm 引导 / 加启动反馈），**没有直接改**：
它换来的是"改完代码双击即生效"这个便利，属取舍而非纯改进，等用户拍板。

### 二、`ready` 消不掉：查出两个独立成因（这是本轮最费工的一步）

第一反应是去查 `ack()`，但先用探针把内核本身排除掉：
`probe-ready-ack.mjs`（手写简化 statusMap）11/11、`probe-real-config.mjs`（真实配置）5/5 ——
**内核逻辑是对的**。既然内核没错，问题就在别处。两个方向查下去，各中一个：

**成因一（渲染层）**：`control-bar.ts` 的 `needsAck` 只认 `needs-input`，而内核 `ack()` 的 `want()`
早就同时覆盖 `ready`。于是 `ready` 在面板上**连按钮都没有、行都不可点**。
——同一判断在两处各写一份，已经失配。

**成因二（内核，更隐蔽）**：写了 `probe-ack-revival.mjs` 去复刻"用户报告的真实失败序列"，
情形 2（双通道交替）复刻成功：**修复前 revivals=3**。机制是 hook 写 `running`、文件源每 15–60 秒
重报 `needs-input`，状态来回跳、每次跳回来清一次确认位。生产证据在 `events.jsonl` 里躺着 ——
357 条绝大多数是同一会话的 `needs-input`、`origin: "file"`、间隔 15–60 秒。

修法是把"确认"锚定在**求助的实例**上（新增 `reAskMinIntervalMs` 迟滞窗口），
并**刻意不清** `needsInputSince` —— 双通道交替正是靠这一点挡住的。修复后 revivals=0。

调试中出现一次我自己的判据不纯：情形 2b 首版在同一次钟值上连发两条 `ingest`，
量到的是 500ms 限流窗格而不是被测的迟滞窗口，导致"迟滞窗口外应重新举手"假失败。
把时钟推进拆开（各给 1 秒）后 13/13。**这与 M2 ④ 第一版探针"没先把宠物挪离右下角"是同一类错误**，
已写进审查报告当通则。

### 三、「已确认」按钮

`ack-all` 命令，走 `arbiter.ack()` 不带参 —— **与"单击宠物"是同一条内核路径**，
所以不需要新机制，也不会再多一处"什么算待确认"的判断。

### 四、工程级审查

`docs/reviews/2026-09-18-工程级审查.md`，五维度 + 四级分级。
**无 Critical、无安全漏洞**，总评 7.5/10。三条 Major 的第一条就是启动全量构建；
第二条是"双通道互斥只有文档约束"—— 也就是我刚修的那个问题的**机制级缺口仍在**，
不该因为症状消失了就当它过去了。

## 想清楚的一件事

**症状一样不等于成因一样。** `ready` 消不掉这一个症状，背后一个是渲染层的谓词漏项、
一个是内核的记账粒度错误，层次完全不同。如果只修了一个就收工，用户下次还会报同一个现象 ——
而"我明明修过了"会让下一轮排查更难。所以本轮坚持把两个成因都定位到能写探针复刻的程度。

另一件事：**修完不删机制级缺口。** 迟滞窗口是症状级修补，ADR 020 的"一个 agent 只由一条通道负责"
仍然只是文档里的一句话。已在 ADR 022 与审查报告里明确标出复发条件（上游重报节奏一变就回来），
并给出三步收口方案。
