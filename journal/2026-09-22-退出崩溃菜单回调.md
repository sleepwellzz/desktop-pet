# 2026-09-22 · 退出路径的 `Object has been destroyed`（ADR 042）

> 用户原话：「这一版很好，但出现了右键托盘按退出按键时候，A JavaScript error occurred in the main process
> Uncaught Exception: TypeError: Object has been destroyed at callback(E:\ ...\dist-win\desktop-pet\
> resources\ app\ dist\ main\ in...:55)」

## 一、定位：从"被截断的堆栈"里只捞出了两个字

他给的路径行号**对不上源码**：那一版 `dist\main\index.js` 的第 55 行是
`function resolveStatusFile()`，不是任何回调。截断的部分（`in...`）恰好吃掉了行号。

真正能用的只有函数名 —— **`callback`**。

于是对整个编译产物穷举了一遍：

```
$ grep callback dist/**/*.js
dist/main/index.js:779   callback: () => {        ← 只有这一处
```

⇒ `at callback` 只能是它：`'popup-menu'()` 里那条 `menu.popup({ window, callback })`。
面板上的「⋯」按钮弹出的正是**同一份**含「退出」的原生菜单（托盘右键与面板「⋯」共用一套模板、
同一个 `actions.quit()`），所以用户说"右键托盘"与实际走的面板「⋯」是同一份菜单。

**这是本轮最有用的一个方法**：堆栈被截断时，**用函数名的出现次数去反推定义点**。

## 二、根因：写了一个守卫，但守的是错的对象

```ts
callback: () => {
  barMenuOpen = false;
  if (!bar) return;                                  // ← 守的是"包装对象非空"
  const focused = bar.browserWindow.isFocused();      // ← 窗口销毁后这里抛
  ...
}
```

`bar` 是模块级 `let`，**`destroy()` 之后它仍然非空**（`quit()` 也从不把它置回 `null`）
⇒ 这个守卫在真正危险的状态下**恒为假**，等于没守卫。

于是单独实测了"销毁之后能调什么"：

| 调用 | 结果 |
|---|---|
| 销毁后 `win.isFocused()` | **抛 `TypeError: Object has been destroyed`** |
| 销毁后 `win.isDestroyed()` | `true`，不抛 |
| 销毁后 `win.destroy()`（二次） | 不抛（幂等） |

用户看到的那句话，正好对上第一行。

## 三、诚实交代：我没能复现它

五种方式，全部失败：

| 方式 | 结果 |
|---|---|
| 合成点击「⋯」→ `quit()` | 不崩（合成点击下菜单没停留） |
| **真实鼠标**点击「⋯」→ `quit()` | 不崩 |
| `tray.popUpContextMenu()` → `quit()` | 不崩 |
| 拦截 `Menu.prototype.popup` 抓真实 menu → 销毁窗口 → `closePopup()` | 回调在 `destroy()` **途中**就被调用了，那时 `isFocused()` 还没坏 |
| 直接调 `quit()`（两条入口） | 不崩 |

⇒ 时序是竞态的（菜单关闭时机 vs `bar.destroy()`），**与 ADR 035 那个退出崩溃同一形状**。

照 ADR 035 §7 的规矩办：**别把"没复现"说成"不存在"，也别把"测过了"说成"证明过了"。**
机制是实测的、代码路径是唯一的、用户看到的就是这一条 ⇒ 修，但按"最坏情况"修，
并且**判据不赌时序**。

## 四、修复与判据

- 守卫改成 `if (!bar || bar.browserWindow.isDestroyed()) return;`
- **顺手堵掉同类第二处**：销毁后的 `Tray` 调 `setToolTip`/`setContextMenu` 会抛
  （实测 `Error: Tray is destroyed`），而"退出后迟到的状态推送"会经 `refreshMenu()` 打到它
  （`void statusSource?.stop()` 是异步的，随后才 `tray.destroy()`）。
  判据**下沉到资源自己身上**（`createTray` 内的 `dead` 标志，`destroy()` 先置位再销毁），
  **不放在调用点** —— 调用点会新增，资源只有一个。
- 加 `setupCrashLog()`：未捕获异常的**完整堆栈**落 `pet.log`。就是为了下次不用再反推。
  **只记录，不吞异常。**
- 判据（`spikes/m2-control` 用例 ⑭）：搭一个只做观测的 `Menu.prototype.popup` 补丁，
  抓住 Electron 真正会调的那个函数，**面板存活时调一次（基线）+ `bar.destroy()` 之后调一次**。
  结果 `抓到 1 个｜面板存活时 ok=true｜面板已销毁时 ok=true`。
- **确认不是真空的**：把修复从 `dist` 里撤掉再跑 ⇒
  `面板已销毁时 ok=false｜TypeError: Object has been destroyed` —— 红的正是用户那句话。
- 单测 408 → **413 项**（新增 ⑲ 节结构钉子；并在注释里写明**它只是 lint**，真判据是探针 ⑭）。

## 五、一条可复用的自检

本项目**第二次栽在同一句话上**：ADR 035 是"定时器越过了窗口"，这次是"**守卫守错了对象**"。

⇒ 落笔前问自己：**"我守的这个东西，会在危险发生时变吗？"**
`!bar` 不会变（销毁后仍非空），所以它守不住；`isDestroyed()` 会变，所以它守得住。
