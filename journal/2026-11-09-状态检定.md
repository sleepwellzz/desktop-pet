## 二、发现的唯一实质缺陷：交接入口过期了

`docs/HANDOFF-2026-09-29.md` 里「五、下一步」写着
**「收口剩下 3 条 P0 …… 都还没动手」** —— 而那 3 条**已经被做完并发布了 `v1.0.2`**。

**为什么发生**：09-29 下半段那个会话做得很完整 ——
写了 journal（`2026-09-29-收口P0与全部判据.md`）、更新了 PLAN §3/§4/§7、新增了 ADR 051/052、
发了 Release、还新建了 `docs/constraints/release.md` —— **唯独没有更新交接文件**。
我核对过：`git log --follow -- docs/HANDOFF-2026-09-29.md` 只有我那次提交，
文件 mtime 变新只是 checkout 的效果。

⇒ 后果：新 agent 若按交接文件开头那句"读它然后按『五、下一步』继续"走，
**会去做已经完成的事**。而 `PLAN.md` 是准的（§3 明写"12 条 P0 已全部结项"），
所以危害可控 —— 但两份入口文件互相矛盾这件事本身就是问题。

**处置**（不用 `git revert`，旧交接只增不改）：
在交接文件顶部加**补记**，写清它描述的是上半段、下半段做了什么、**以 PLAN 为准**；
把过期的「五、下一步」折进 `<details>` 保留追溯，另写真实的遗留清单；
并把「Release 附件已过期」那节改为已解决（附本轮 sha256 核对表）。
PLAN §0 也加了提示：**状态以 PLAN 为准，不要只读交接**。

## 四点五、一个容易误判的坑：GitHub API 有缓存

本次 `git push` 报成功且本地 `origin/main` 已更新，但 **GitHub API 立即查仍是旧提交**。
这个现象与本项目已记录的那个坑（"`git push` 报成功但 ref 不落盘"）**长得一模一样**。

**实际是 API 缓存**，约 12 秒后自行刷新。用三种方法交叉验证才敢下结论：

| 方法 | 结果 |
|---|---|
| GitHub API `/commits/main` | 首次 `accbdf7` ⇒ **12 秒后** `cc6756c` |
| API `/commits/cc6756c`（直接问该提交在不在） | `200` |
| `git ls-remote origin main` | `cc6756c` = 本地 HEAD |

⇒ **纪律要再具体一点**：
- "不信本地 git 自述、走 API 核实"这条仍然对，但**API 自己也有一段静默期**；
- **首次不一致时不要立即判失败，也不要重推**（重推对已落盘的提交无害，但容易误判）；
- 最可靠的旁证是 **`git ls-remote`**：它直查远端 ref、不经本地 ref 缓存。
  ⇒ **推送后的核实首选 `git ls-remote`**，API 只当第二个信源。

## 五、一条流程教训

**"做完了"与"交接说做完了"是两件事。**
这一轮的记录链路其实做得很好（ADR + journal + PLAN + changelog 四处都更新了），
但**入口文件**（交接）漏了 —— 而入口恰好是下一个 agent 最先读的那一份。

⇒ 可复用的做法：**收工时先问"下一个 agent 第一眼会读哪个文件"，再更新它。**
`AGENTS.md` 的收工协议列了 PLAN / ADR / journal / commit 四件，
**没有把"更新交接文件"写进去** —— 这可能是它被漏掉的直接原因（值得补进协议）。
