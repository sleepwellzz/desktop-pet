# 2026-09-18 · M3 第三块：状态↔动作全盘复核（ADR 021）

起因是用户的一句话：

> "我感觉现在宠物状态有点乱，就在我打字的这个过程之中，并没有任何 agent 在跑，
> 但是它依然是小厨师在炒菜的这个动画状态。"

## 开工：先确认解读，不猜

用户的原始诉求里有一句关键的自我更正：他先说"小厨师应该是 running"，随后又撤回，
承认自己记混了，最终只要求 **"只要你确保 running 和 ready 不一样就行"**，并要"审慎检查有没有冲突"。

因此本轮**没有**按用户最初的解读去把 `running` 改挂第 8 行 —— 那会把 `ready` 挤出小厨师，
却同时让 `running` 和 `ready` 的区分变成"只靠有没有出口"。实际证据是：

- `running` 的现行落点 = **第 7 行生日姿态**（2026-09-16 拍板的"保持第 7 行"）；
- `ready` 的落点 = `waving` → `then: review` = **第 8 行小厨师姿态**。

两者本来就不同行。用户看到的"炒菜"是 `ready` 的落点，不是 `running` 的落点 ——
所以真正要修的是 **`ready` 没有出口**，不是 `running` 的映射。

## 九行素材占用总表（审计基线）

复核的第一步是把九个行号"谁在用"全摊开，避免只盯着用户报的那一条：

| 行 | 画面 | 当前占用 |
|---|---|---|
| 0 | 待机 | `idle` |
| 1 / 2 | 位移姿态 | 行为层漫游与踱步（**刻意不留给业务状态**） |
| 3 | 拜一下 | 左键单击 + `needs-input` 的入口动画 |
| 4 | — | 跳跃（微动作候选） |
| 5 | 趴卧 | `blocked`（受阻）+ 行为层「打盹」—— **两种相反含义共用** |
| 6 | — | `failed` |
| 7 | 生日姿态 | **`running`** |
| 8 | 小厨师姿态 | **`ready` 的落点 `review`** |

摊开之后冒出两个问题，都不在用户报的那一条里：**第 5 行语义挤压** 与 **`ready` 无出口**。

## 复核过程中的自我更正（两处）

### 1. 初稿的机制推断被复跑推翻

任务书初稿写的是"`ready` 的落点被反复重走"（`ready → waving → review` 每 6 秒重走一次）。
用真实仲裁器连续复跑三组后证明**不成立**：

- 稳定输入下 `rev` 不动；
- 渲染层收敛后不动。

真机制更简单也更糟：**`ready` 完全没有任何出口**，只能等 15 分钟的会话静默兜底。
所以"永久炒菜"不是因为被反复触发，而是因为**根本没人把它收回去**。

**教训**：把"看起来像的症状"当成机制写进设计稿，会导出一条错误的修法
（"打断重走"），而真修法是"给它一个出口"。

### 2. 初稿的事件流证据也是错的

初稿引用 `wb:de8d4bad-…` 的 55 条事件当作"反复触发"的证据。
逐条看过后：**50 条是 `needs-input`，`ready` 只有 1 条**。
那条事件流证明的其实是另一件事（`needs-input` 很粘），与 `ready` 无关。

**教训**：引用事件流要给出条数分解，不能只看"有 55 条、看起来很多"。

## 修法（用户拍板：先改再验）

### A · 气泡定位缺陷

`src/host/bubble-layer.ts` 的 `show()` 在从未 `followPet()` 过时执行：

```ts
if (!lastPetBounds) lastPetBounds = win.getContentBounds();
```

**把气泡窗口自己的矩形当成了"宠物矩形"**。而 `src/main/index.ts` 调
`bubble.show(text, badge)` 时**根本没传宠物位置** ⇒ 启动后第一次推气泡必然走这条兜底，
位置由"气泡窗口自己被创建在哪"决定，于是出现在屏幕正中。

这与 ADR 017 那条"没有 `ts` 不等于刚刚"是**同一类错误**：
**兜底值取了一个"看起来像但不等于"的东西。**

修法：`show(text, badge, petBounds)` 显式接收宠物矩形；**拿不到就不显示**，
而不是显示在错的地方。

### B · `ready` 通报时效

- `desktop-pet.json` 新增 `statusTimeouts = { stickyMs: 300000, readyMs: 60000, sessionStaleMs: 900000 }`；
- `kernel/status.ts` 新增 `readyTimeoutMs`（默认 60 秒）与 **独立的 `readySince` map**；
- `ack()` 扩展为也能消解 `ready`（单击宠物 = 已读）。

**不能复用 `SessionRecord.ts` 计时** —— `ts` 每次心跳都刷新，拿它计时会让机制
在自己要防的场景下失效（"干完活后 agent 又发了一次心跳，宠物又得重新等 60 秒"）。
单测用 `expiredAt === 60_000` 钉住"心跳不推后时效"。

### C · 第 5 行语义挤压

用户拍板：

> "打盹可以是宠物日常休闲的动画之一，但它和 blocked 的区别在于 blocked 时
> 打盹的样子上面应该出现文字提示。"

⇒ `bubble.stickyStatuses` 从 `["needs-input"]` 扩到 `["needs-input", "blocked"]`，
并从 `holdMsByStatus` 定时表上摘掉 `blocked`。

## 踩坑（只有实测才发现的）

### 只跑 `tsc` 不够 —— preload 是 esbuild 打包的

`spikes/m3-ready-exit` 首跑 0 个采样点，看起来像探针逻辑坏了。实际日志：

```
[pet][renderer:error] Unable to load preload script ... module not found: ../shared/ipc
```

渲染层根本没初始化。改成跑完整 `npm run build`（7 步 + copy-assets）后 PASS。
**这条已写进 `spikes/m3-ready-exit/README.md`。**

### 单测断言写错，不是测试 bug

⑨b 有一条断言"重报 ready 期间输出没变过"期望 0 实际 1。原因：我每 10 秒重报一次共 10 次，
**第 6 次（t=60s）恰好是到期点**，于是有 1 次**合法**的输出变化。
改为精确断言："10 次心跳里只有一次输出变化（就是到点退场那次）" + "退场发生在第 60 秒"。

**教训**：断言失败时先问"我的期望对不对"，再问"代码对不对"。

## 关闭一个疑点

`wb:default` 会话看起来可疑（114 条、39 小时跨度）。核实后是 8-16 人工验收的残留
（`origin=file, title=manual-acceptance`），**不是缺陷**。已记进任务书 §5。

## 留下的口径差异（需用户确认）

用户在拍板 `ready` 出口时写的是 **"落到第 7 行生日（当'等你验收'）"**，
但**第 7 行是 `running` 的现行落点** —— 真改过去两者会撞行，
与同一轮"确保 running 和 ready 不一样"的要求相矛盾。

实施取的是：**保持第 8 行 `review` + 叠加 60 秒出口**。这样既不撞 `running`，
又消灭"永久炒菜"。

**若用户更看重"生日 = 等你验收"的语义**，改 `desktop-pet.json` 的
`statusMap.ready.then` 一行即可，代价是 `ready` 与 `running` 用同一动作外观、
只靠 60 秒出口区分。这条已写进 §3 D 条与 ADR 021。
