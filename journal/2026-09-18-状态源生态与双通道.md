# 2026-09-18 · M3 第二块：状态源生态（双通道）

接上一轮（同日的"任务中踱步"）。本轮从 §4 第 7 条的两条候选里选了 **⑦-b 状态源生态**。

## 起因

PLAN §8 风险表里唯一还写着"仍待验证"的一条：**"真 agent 的 hook 配起来好不好用"** ——
此前只验证了链路（文件 hook + 人工喂状态），没有真实 agent 跑过。

设计稿初版的目标 agent 是 **Codex**。用户答复 D1 时把目标改成了
**WorkBuddy（主力）+ Proma（第二主力，Pi agent 架构）**，于是重做了调研 —— 结论有实质变化。

## 用户的两条关键输入

1. **"万一两个软件同时运行，会不会冲突或叠加？"** —— 这条直接决定了架构。
2. **"状态变化延迟不能太高"** —— 且用户注意到我提到过"监测不及时"，要我澄清是哪一层。

## 调研：三个决定性的实测发现

### ① WorkBuddy 自带完整的 Claude 系 hook 引擎（初稿完全没料到）

扫内嵌 agent CLI（`resources/app.asar.unpacked/cli/dist/codebuddy.js`，23MB）发现：
14 个事件的字面量数组（含 `PermissionRequest` / `Notification` / `PostToolUseFailure` / `WorktreeCreate`）、
`hook_event_name`×49、`executeHook`×32、`permissionDecision`×56、`disableAllHooks`；
hook 是**真的 spawn 子进程**。配置位置 = `.codebuddy/settings.json`。

### ② 闸门跑通：桌面确实走内嵌 CLI，工程级配置确实生效（YES）

- **进程树**：`WorkBuddy.exe → daemon-app-server-entry.js --stdio → sidecar-entry.js
  → cli/bin/codebuddy --serve --session-id ab2f75f8-…`。该 session-id 与
  `~/.workbuddy/sessions/203516.json` 的 `sessionId` **完全一致**。
- **设置作用域**：CLI 里 `DEFAULT_SCOPES = [USER, PROJECT, PROJECT_LOCAL]`，
  而跑 agent 的进程**没带** `--setting-sources`（只有一条 prewarm 进程带 `--setting-sources user`）。

### ③ Proma 没有 hook 面，但有很好的被动源

`app.asar` 里 `PreToolUse` / `hook_event_name` / `disableAllHooks` 全 0；
`SessionStart` 那 25 处**逐条看过上下文**，全是编辑器内部变量，不是 agent hook。
**但** `~/.proma/agent-sessions.json` 有 218 条会话（含 `title` 与 `updatedAt`），
`agent-sessions/<uuid>.jsonl` 末尾有 `type:"result"` + `terminal_reason:"completed"`。
顺带实证了用户说的 SDK 迁移：`legacyTranscript.sourceRuntime` = **claude 38 / Pi 180**。

## 架构决策（详见 ADR 020）

- **两条通道**：A 事件驱动 hook（WorkBuddy / 将来的 Claude Code / Codex —— **同一套事件名与契约**，
  所以是"1 份映射 + N 个配置路径"，不是 N 份适配器）；B 被动会话源（Proma）。
- **一个 agent 只由一条通道负责，互斥** —— 这是本轮新增的硬规则。两个**不同** agent 天然不冲突
  （仲裁器本来就是多会话形状）；会打架的是**同一个 agent 被两条通道同时盯**（来回刷且无报错）。
- **`sessionId` 带来源前缀**（`wb:` / `proma:`）+ **标题带来源名**。
  副产品：用户"只想连某一个 agent"变成一次按前缀过滤，不是新机制。

## 施工顺序被实测推翻了一次

初稿把"先做通道 B（读文件）"当作零风险的先赢。**采样探针（151s @1Hz）推翻了这个排序** ——
WorkBuddy 的被动源**只能给"存在性"，给不了"活动性"**：

- `sessions/*.json` 心跳 151 秒里**只刷新 5 次 ⇒ 粒度约 30 秒**，且与"在不在干活"无关；
- `tasks/*/N.json`、`file-history/`、`changes-index/`、`plans/` 窗口内 **0 次变更**；
- `projects/` 4 次、`artifact-index/` 2 次（太少）；
- `logs/` 105 次写入，但内容是 `vendor-extract.log`、`weixinpay/*.xlog` 这类**应用级日志** ⇒ 噪声。

⇒ 通道 A 才是 WorkBuddy 的主路径，B 降为可选。

## 一条自我更正

我先前在设计文档里写"`sessions/<pid>.json` 心跳**秒级新鲜**"，**是错的**。
那是**只看了一次文件的当前年龄**（"它现在很新"），而不是**看它的更新频率**（"它多久更新一次"）。
两者完全不同：前者能推出"刚刚有人写过"，推不出"它一直在写"。已更正回文档。

3. **payload 比文档更丰富**：多了 `permission_suggestions`、`permission_mode`、`client`（实测 `"WorkBuddy"`）、

4. **我的一条预测被推翻**：我据进程树里的 `--permission-mode fullAccess` 预测"不弹审批、判据 3 验不了"。

### 真实回合抓到一个我自己的缺陷（已修）

`Notification` 我原本一律映射成 `needs-input`，而实测的 `notification_type` 是 **`idle_prompt`**
（`"CodeBuddy is waiting for your input"` —— "干完了、在等你说话"），它在 `Stop` 之后**约一分钟必然出现**。
两者叠加的结果：**每次干完活宠物都会举手要你确认**，`needs-input` 这个最宝贵的状态会被**贬值**。

修法：加良性类型白名单（目前只有 `idle_prompt`），命中的 `Notification` **不写状态**；
未知类型仍按"要你注意"处理。**这条单测写不出来 —— 我当时根本不知道有 `idle_prompt` 这个取值，
只有跑真实回合才会露出来。** 新增 8 项断言钉住（62 → **70 项**）。

## 第二次验证：判据 2 通过；用户撞到一个产品级缺口

用户装上了桌宠，于是宠物侧终于有了时间线。

### 判据 2 ✅ 通过

| 宠物侧收到 | 状态 | 对应 hook |
|---|---|---|
| 09:56:57.853 | `ready` | `Stop` @09:56:57.851 |
| 10:02:42.862 | `running` | `UserPromptSubmit` @10:02:42.860 |

序列正确（提交 → 结束），没有卡在 `running` 不回。
**而且 `idle_prompt` 在真实环境被正确忽略**：hook 侧 09:57:57.845 有一条
`Notification type=idle_prompt`，宠物侧**完全没有对应事件** ⇒ **上一轮修的那个假阳性确认有效**。

### 用户报告：一启动桌宠就是"炒菜/做饭"，不是默认待机

**诊断（对照 `docs/status-reference.png` 确认，不是凭状态名猜）**：

- `ready`（就绪·未读）→ 动画 `waving`（第 3 行）→ **落点 `review` = 第 8 行**，
  对照图上的原文就是"先挥手拜，再落到小厨师姿态" —— **画的就是穿围裙拿锅铲炒菜的小狗**。
- `review` 在 `desktop-pet.json` 里是 **`loop: true` 的循环态、没有出口**。
- 触发链：我 09:56:57 结束回合 → WorkBuddy 发 `Stop` → 客户端写 `wb:<会话>` = `ready`
  → 用户 10:01 启动桌宠，读到快照里 10 分钟前的 `ready`（未到 15 分钟静默兜底）→ 立即炒菜。

**根因：`ready` 的落点没有出口，而 `Stop` 现在每次回合结束都会触发**
⇒ **agent 干完一次活，宠物就永久炒菜**。
用户以前没遇到过，是因为那时没有真实 hook，`ready` 只来自人工喂状态。

**一条支持"这是缺陷"的现成论据**：气泡对 `ready` 只显示 6 秒
（`bubble.holdMsByStatus.ready = 6000`）**就收起了，宠物却还在炒菜** —— 两者不一致。

**但改成什么是产品决策**（该落点是 M2 ① 验收过的行为，PLAN §1 明确写着"不是回待机"），
所以**没有擅自改**，列为待用户拍板：
**A（推荐）`review` 60 秒后自动回 `idle` ／ B 单击宠物 = 已读（复用 `ack()`）／
C 落点改回 `idle`（与已验收行为冲突，不推荐）**。

### ⚠️ 一个测量陷阱（差点让我推出错误结论）

对账时我先看到 `Stop` 的 hook 落盘 09:56:57.851、宠物侧 `ts` 09:56:57.853 —— **只差 2ms**，
看起来像"端到端延迟极低"。

**但那 2ms 是假的**：`events.jsonl` 里的 `ts` 是**写侧（hook 客户端）产生的时刻**，
不是宠物收到的时刻。所以这 2ms 只是 hook 进程内"落 payload → 写状态文件"的间隔。
**拿它算端到端延迟会严重低估。** 判据 6 要换时间基准（主进程日志，或探针自己加戳）。

### 附带事实

`default` 会话是 8-16 人工验收的残留（title `manual-acceptance`）。
桌宠启动时被读到并短暂报了一次 `running`（10:01:15），4 秒后变 `idle`，之后不再干扰。
它带 `ts`，会正常落进静默兜底 —— **是噪声不是缺陷**，菜单「清空状态会话」可清掉。

### 用户拍板：小厨师 = Agent running（取代 2026-09-16 的旧决定）

原话：*"我认为可以让小厨师的姿态一直保持为 Agent 在 running 的状态。"*

后者顺带修掉"没有 agent 在跑、宠物却还在炒菜"—— 因为那是 `ready` 占着小厨师造成的。

不改用其它行"）。两个子问题（`ready` 落到哪、第 7 行生日归谁）留待全盘复核定稿。

### 真缺陷：气泡出现在屏幕中间（用户报告）

**根因（代码级确证）**：`src/host/bubble-layer.ts` 的 `show()`：

```js
show(text, badge) {
  if (!lastPetBounds) lastPetBounds = win.getContentBounds();   // 第 116 行
```

`show()` 的签名里**没有"宠物在哪"这个参数**，只能靠 `followPet()` 提前喂。
而 `followPet()` 只在**宠物移动/缩放**时被调用；`main/index.ts:420` 调
`bubble.show(text, badge)` 时不传宠物位置。**启动后第一次推气泡必然走这条兜底**，
于是把**气泡窗口自己的矩形**当成了宠物矩形 ⇒ 位置由"气泡窗口被创建在哪"决定 ⇒ 跑到屏幕中央。

**这叫"把未知当成已知"**，与 ADR 017 那条"没有 `ts` 不等于刚刚"是同一类错误 ——
**兜底值取了一个"看起来像但不等于"的东西。**

修法：宠物矩形显式传进 `show()`；**拿不到时选择"不显示"，而不是显示在错的地方**。
"为什么恰好在屏幕正中"待用最小 Electron 探针实测，不写进结论。
