# 2026-09-18 · 任务中踱步落地 + "不跨屏"锁定（ADR 019）

## 这轮从哪来

上一轮（2026-09-17）行为层落地时，ADR 018 刻意留了一个**产品决定**没拍：
"任务进行中，宠物能不能离开原位？"——因为"运行中看起来像在忙"这条早先记的承诺
与"只在 idle 时活动"直接冲突，不该由实现顺手决定。

用户这轮的答复分两段：

1. **"忙碌动作"这个词他不认**（不记得当初为何记它），所以那条待办**作废**。
2. 但位置问题他答得很具体：**可以离开原位，但不超过几百像素（约 300–400px）**；
   往屏幕内侧走几步就行；**频率不能高，只作为点缀与解闷**。
   **多屏暂不考虑** —— 只用主屏，或者"我把宠物拖到哪块屏，它就一直在这块屏活动"。

所以本轮做的是一个**更小、更明确**的行为：任务进行中的低频短距离踱步。

## 做了什么

**A. 行为层加"踱步模式"（`kernel/behavior.ts`）**

`tickBehavior` 的规则 0 从"未启用 / 有任务 → 一起归零"拆成两套模式：

- `status === 'idle'` → 空闲模式（漫游 / 微动作 / 打盹），规则原样；
- `status !== 'idle'` → **踱步模式**（新函数 `tickBusy`）：不漫游、不微动作、不打盹，
  只在中低频上走一小步。

新增相位 `pacing` 与三个状态字段：`busySinceAt`（进入踱步模式的时刻，兼作"需要重新锚定"的信号）、
`anchorX`（踱步锚点）、`nextPaceAt`（下一次踱步的到点时刻）。`rearmBehavior` 改成兼顾两种模式。

**B. 最关键的一条：目标由锚点算，不由当前位置算**

`pickPaceTarget` 用 `anchorX ± distancePx`，不用 `pet.x ± distancePx`。

漫游可以按当前位置累加（它本来就是随机游走），但踱步被明确要求"不超过几百像素"。
按当前位置累加的话，踱十次就漂出几百像素 —— 用户的要求会在几分钟后**悄悄失效**，
而屏幕上只表现为"它怎么跑那么远"，没有任何报错可循。锚点约束把这条要求变成**结构性成立**。

锚点在两处重记：进入任务状态时、以及**每次抑制结束后**。后者正是"拖到哪块屏就在哪块屏活动"
的落地机制 —— 拖动属于抑制，抑制期间 `busySinceAt` 被清成 null，恢复后第一 tick 用新位置重记锚点。

**C. 方向朝工作区中心一侧，不固定朝左**

用户说"往左走几步"，那是在他常见位置（右下角）说的。固定朝左在宠物贴屏幕左边时会**永久失效**
（每次都够不到，目标返回 null）。朝中心在右下角时恰好就是朝左，观感一致且任何位置都不失效。

**D. 参数（`desktop-pet.json → behavior.busyPace`）**

| 参数 | 值 | 依据 |
|---|---|---|
| `everySec` | [60, 180] | 比空闲漫游（25–90 秒）更稀疏 —— 它是点缀，不是主要活动方式 |
| `distancePx` | [60, 300] | 用户说"三四百像素"，取 300 留余量。上限同时就是"最多离开锚点多远" |
| `speedPxPerSec` | 96 | **沿用漫游基线**：位移速度是照着位移行步频校过的，另取一值会有一处滑步 |

有任务时**不计打盹**（`idleSinceAt` 恒为 null）：打盹是"没人理它"的表现，正在干活不该趴下。

**E. "不跨屏"从"本轮范围"升级为**锁定范围**（`edgePolicyScope` 改措辞）

零代码改动：`workArea` 每 tick 用 `getDisplayNearestPoint(宠物中心)` 取，宠物在哪块屏就用哪块屏的
工作区，目标点夹进去；配合锚点重记，"拖到哪块屏就在哪块屏活动"是自然结果。

## 判据（全绿）

**离线单测**（`tools/status-arbiter.test.mjs`，虚拟时钟 + 固定随机种子）：**191 → 219 项**。
新增 ⑥b（踱步）与 ⑥c（不跨屏），三条核心判据：

- **踱几十次之后仍在锚点 200px 以内** ⇒ 无累积漂移（这是本决策的核心风险）；
- **默认节奏（60–180 秒）下 10 秒内一次都不踱** ⇒ 频率确实是点缀级；
- `workArea` 换成"另一块屏"时，目标夹在新工作区内、锚点留在新屏上 ⇒ 不跨屏。

同时改写了 ⑥：`running` 期间不再是"一步不动"，而是"交回业务动画 + 锚在当前 x + 踱步未到点所以不动"。

**真实窗口探针**（`spikes/m3-behavior`，临时宠物包把节奏压到 3–5 秒 / 60–160px）：

```
④ running 期间踱步：在动=true｜锚点=1249（观测期内 1 个锚点）｜离锚点最远 111px（上限 160px）
  ｜相=idle｜画面行号=[7,2,1]（7=running 业务态，1/2=位移行）｜越界采样=0
④b 清空会话后恢复自由漫游=true
```

判定 **PASS**（7 条全过）。

**其余回归**：命中图**误吃 0**（漏吃 2 = 既有边缘基线）｜全屏两轮 OK｜托盘 PASS｜
控制条两探针 PASS｜状态端到端 PASS｜气泡与快捷键 PASS｜陈旧会话哨兵 22/22。

## 本轮踩到的坑

1. **单测第一版两处断言是我写错的，不是产品代码**：
   ① `simulate` 的 x 是局部变量，`walk.x` 不会自动带进下一次调用 —— 忘了传 `startX`，
   于是"锚在当前位置"量到的是初始值 600 而不是 627；
   ② "关掉踱步后仍交回一次"——但初态本来就是干净的（`sentPlay === null`），
   它**正确地**什么都没发。修法是把用例初态设成"带着位移覆盖"，不是放宽断言。
   **教训：断言红了先怀疑自己的用例，但修法必须是"让被测规则真的生效"，不能是"放宽"。**
2. **从踱步模式切回空闲必须显式清相**：`idleSinceAt` 在踱步模式下恒为 null，
   回到空闲正是靠它变回 now 才触发首次排程。若不清 `phase`，宠物会带着 `pacing` 相停在半路
   —— 表现是"停在那儿不动，也不漫游"，同样没有任何报错。已写进 ADR 019 负面结论与设计文档。
3. **`busySinceAt` 一名两用**（"在踱步模式" + "需要重新锚定"）。省了一个字段，
   代价是读代码时要记得"抑制期间它被清成 null 是故意的"。记在 ADR 019 负面结论 3。

## 留给用户验收的一条

踱步期间画的是**位移行**（第 1/2 行），不是业务状态那行。另一条路是"业务动画不动、
只是窗口在挪"，画面上会变成生日姿态在地面上平移——明显更怪。用户原话"动画可以照常播放"
两种读法都通，所以记在 ADR 019 负面结论 1，**验收时看一眼**；改的话是一行。
