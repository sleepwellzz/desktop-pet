## 二、`+1` 角标为什么看不到 —— 不是 bug，是操作方法

角标的语义是"**主状态之外**仍在活动的会话数"（`StatusArbiter.state.badgeCount`，
统计 `sessionId !== primary && effectiveStatus !== 'idle'` 的会话）。
而 `喂状态.bat` 的所有选项都写**同一个会话 `default`** ——
所以"开两个终端、一个按 1 一个按 4"其实喂的是同一个会话，角标恒为 0。

处置：给菜单加 **`8` 第二会话 b=running** 与 **`9` 清掉会话 b**，并把这条语义写进菜单头部。
操作变成：按 `4`（default 需要输入，进入粘滞）→ 按 `8` → 气泡右侧出现 `+1` → 按 `9` 角标消失。

同时给仲裁器单测补了一条**正好就是这个场景**的断言（粘滞期间第二会话出现 → 角标 1、
主状态仍是 needs-input）。单测 81 → **87 项**。

## 三、文字裁切与居中：先取证，再修

### 修的是什么

| 问题 | 根因 | 改法 |
|---|---|---|
| 文字下缘被切 | `line-height: 1`（13px）短于字体自身行高（雅黑 13px ≈ 17px），字形溢出后被省略号必需的 `overflow: hidden` 切掉下缘 | `line-height: 20px` |
| 文字没水平居中 | `#bubble` 是 flex，默认 `flex-start`；气泡宽度是**估算**的，多出的余量全落右侧 | `justify-content: center` + `#text{min-width:0}` |

实测（`spikes/m2-hotkey/`，DPR 1.5，文本「需要输入」+`+1`）：

| 指标 | 修前 | 修后 |
|---|---|---|
| 被裁（上/下） | 0 / **1 物理像素** | **0 / 0** |
| 左右余量 | 0.00 / 3.39px | **1.69 / 1.70px** |
| 探针判定 | FAIL | **PASS** |

### 方法上的坑（比缺陷本身更值得记）

第一版判据用 canvas 的 `fontBoundingBoxAscent/Descent` 当字体度量、按"半行距 + ascent"
反推基线，算出**裁切 0.00px** —— 与真实渲染不符。放大 8 倍的截图上，字的下横画明显被平切。
也就是说：**canvas 字体度量 ≠ Chromium 排版度量**，用 A 引擎的度量预测 B 引擎的像素本身就是错的。

改成**差分截屏**：同一帧截两次（保留 `overflow:hidden` / 注入 CSS 关掉它），
比对"文字墨迹行范围"，差值就是被裁的物理像素数，容差 0。
这个判据与字体、引擎、DPR 都无关。只扫 `#text` 的列带以避开角标白字，另加"墨迹高度 < 字号 0.7 倍即判失败"的兜底。
