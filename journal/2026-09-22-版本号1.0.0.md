# 2026-09-22 · 版本号定为 1.0.0（ADR 041）

> 会话目标（用户原话）：「那我们是不是就给这一次做完了的这个版本加一个版本号码？是不是叫 1.0.0？
> 我不太确定应该怎么编号，我也想了解一下咱们一般怎么给软件进行版本编号」

## 一、先做的事是"查现状"，不是"写代码"

用户以为要从零开始加版本号。先读了一遍打包产物，发现情况是**反过来的**：

| exe 版本资源字段 | 改前 | 判定 |
|---|---|---|
| `FileVersion` | `44.4.0` | ❌ **Electron 自己的版本** |
| `ProductVersion` | `44.4.0` | ❌ 同上 |
| `ProductName` | `desktop-pet` | ✅ ADR 036 改的（决定自启值名） |
| `FileDescription` | `desktop-pet desktop pet` | ✅ |
| `CompanyName` | `GitHub, Inc.` | ❌ Electron 的 |
| `LegalCopyright` | `Copyright (C) 2015 GitHub, Inc.` | ❌ 同上 |
| `OriginalFilename` | `electron.exe` | ❌ 文件已改名，资源里还写着旧的 |

而 `package.json` 里的 `version: 0.1.0` **从来没被任何东西读过** —— 它跟着 `resources/app/`
进了包，但既没人把 `app.getVersion()` 接到任何地方，也没人把它写进 exe。

⇒ 任务被重新定义为：**把一个错的版本号换成对的，并保证它只写一遍**。

## 二、怎么跟用户讲"版本号"

用户问的是"一般怎么编号"，所以先讲清楚（配了两张图：SemVer 三段结构 / 本项目的落点图）：

- **`1.0.0` 的含义是"从这里开始承诺兼容性"，不是"功能做完了"** —— 用工作量衡量版本号在
  SemVer 里没有依据。所以门槛应该这样问：*这个软件现在有没有"不能被下一次更新搞坏的东西"？*
- 本项目有：`prefs.json` / 注册表自启项 / sidecar 字段 / 分发结构 / 图集规格。
  **最有力的证据是"已经为兼容性付过一次真实成本"**（旧自启值名迁移，ADR 035）。
- 反面意见也摆了：若接下来要大改 sidecar 字段名，`0.x` 更诚实；但长期挂 `0.x` 的代价是
  **没有数字空间表达"这一版改坏了兼容性"**。⇒ 取 `1.0.0` + **窄承诺**。
- 顺带交代另外两套：Windows 四段式（`1.0.0.0`，系统要求，与 semver 不冲突）与
  CalVer（日期版，适合固定周期发版，桌宠不适合）。
- 提醒一个命名坑：工程里已有 `spriteVersionNumber`（**图集**版本 V1/V2），别和软件版本混。

## 三、用户拍板（三项）

1. 版本号取 **`1.0.0`**；
2. **顺手清掉 exe 里 Electron 的痕迹**（CompanyName / LegalCopyright / OriginalFilename）；
3. **托盘的悬停提示不要出现版本号**（保持「淘淘 · 空闲」），
   版本号改放**托盘右键菜单里一行只读小字**，理由是他要的只是"自己开发时能知道"。

第 3 条是"用户说不要"的落点 —— 已用单测钉住（`tray.ts` 剥注释后不得出现 `version`），
防止下一个会话觉得"到处显示才完整"而顺手加回悬停提示。

## 四、落地

- `package.json`：`0.1.0` → `1.0.0`（**唯一手写处**）。
- `tools/make-portable.mjs`：从 `package.json` 读版本；新增 `windowsVersion()` 换算；
  rcedit 写 4 个版本字段 + 清 3 个 Electron 残留字段；zip 名带版本；README 带版本。
  **目录名保持不带版本** —— 自启注册表记的是绝对路径，改名会让老用户条目失效。
- `src/main/index.ts`：日志横幅带 `v${app.getVersion()}`；打包态日志行带版本；
  `petMenuView()` 提供 `version: app.getVersion()`。
- `src/host/pet-menu.ts`：`PetMenuView` 加 `version`；菜单最上方加一行只读版本
  （原生菜单不支持字号，`enabled: false` 的置灰就是"小字"的等价物）。

## 五、实测

**rcedit 参数探测**（对一份**副本** exe 跑；用运行中的 exe 作目标会 `Unable to commit changes`
—— 第一次就是这么失败的）：

| 参数 | 结果 |
|---|---|
| `--set-file-version 1.0.0` / `1.0.0.0` | 都接受 |
| `--set-product-version 1.0.0` / `1.0.0.0` | 都接受 |
| `--set-version-string OriginalFilename ...` | 接受（任意键都能写） |

**关键读数**：同时写 4 段数值版与 3 段字符串版后，属性页读出的是 **`1.0.0`（字符串版）**
⇒ **两套都得写**，各有各的读者。semver 的预发布后缀在数值字段里没有位置，显式剥掉。

**打包后/运行后**：

- exe 版本资源全部正确；`ProductName` 仍是 `desktop-pet`（自启值名不许动）；
- 便携版走**双击路径**启动：6 个进程、`isPackaged=true`、横幅 `==== 启动 v1.0.0 … ====`、
  手动把玩 9 个动作、窗口/精灵图/托盘/控制条就绪、**零异常**、收尾 0 残留；
- **开发态**也报 `v1.0.0`（`isPackaged=false｜版本 v1.0.0`）⇒ 两种形态读同一份 `package.json` 证实；
- 单测 **391 → 408 项**全绿。

## 六、这一轮我犯的错（已写进 ADR §9）

**六处 `Edit` 报告成功但文件没变。** 根因是我把多个 Edit **并发**打到同一个文件上
（一条消息里发了 6 个），读-改-写互相覆盖丢了更新。

症状很有欺骗性：工具回的是 "Successfully edited"，而 `tsc` 报的是一个看起来毫不相干的
类型错误（`Property 'version' does not exist`）—— 因为**接口那半边丢了、用它的那半边留下了**。
两轮构建才定位到。

⇒ 纪律：**同一个文件的多处改动必须串行**，且改完 grep 复核。
这与工程里已记的"Edit 偶发报告成功但文件没变"是同一类风险，只是这次成因明确、可避免。

另：删掉了上一轮遗留的不带版本号的旧 zip（154 MB）—— 两个名字并存会让"哪个最新"变模糊。
