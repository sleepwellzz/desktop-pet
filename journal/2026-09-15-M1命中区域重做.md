# 2026-09-15 · M1 命中区域重做（ADR 008）+ 缩放调整

## 这轮要解决的问题（Justin 的人工复验反馈）

1. 穿透区域不稳定：左 100px / 上很准 / 右 400px / 下 700px，**拖动后死区变化很大且越来越大**，每次启动数值都不同；
2. 触发挥手的判定左右偏宽（上下很精细）；
3. 宠物占地大，希望缩到 0.5~0.7 倍面积。

## 做法：先造测量手段，再动手改

上一轮已经吃过"凭推断下结论"的亏（`WindowFromPoint` 那条死路），这次直接搭真实点击探针：
`spikes/m2-hittest/` 里 `require` 真实主进程，再开一个铺满屏幕的近透明靶窗，用 `mouse_event`
注入真实 OS 点击，逐点记录"宠物吃到 / 靶窗收到 / 当前帧 alpha"三个信号，169 个采样点。

探针本身踩了四个坑，都写进 ADR 008 的负面结论了：
GUI 进程 stdout 拿不到（改落盘 + 外层驱动轮询）、koffi 拿 HWND 最稳的路是
`getNativeWindowHandle()` 转数字（`WindowFromPoint` 返回 null）、
`SetCursorPos` 不产生 `WM_MOUSEMOVE`（注入拖动必须用 `mouse_event(MOVE|ABSOLUTE)`）、
探针基准帧必须与被测帧同帧（否则漏吃率被放大 3 倍）。

## 实测结论

**A. 生效命中区域 = 整个窗口矩形，与像素 alpha 无关。**
修复前：窗口矩形内 **90/90 采样点全部被宠物吃掉**（穿透率 0%），矩形外 79/79 全穿透。
与精灵 alpha 比对：应穿透却被吃 43、应命中却穿透 0。
→ M0"逐像素穿透是原生行为"的判断是错的：M0 只验证了窗口**外**的点击能穿透。

**B. 窗口每移动一次长 1 DIP**（148×160 → 149×161 → … → 154×166，物理 221×239 → 230×248）。
`setPosition` 在 150% 缩放下反复做 DIP↔物理取整，误差累积。
修复前"死区 = 窗口矩形"，所以拖得越多死区越大 —— 这正是反馈里那条"越变越大"。

## 改了什么

- `src/host/overlay-window.ts`：起步 `setIgnoreMouseEvents(true, {forward:true})`；
  新增 `setInteractive()`；`useContentSize: true`；拖动改 `setContentBounds`（每次复位内容尺寸）。
- `src/renderer/renderer.ts`：保留整张阈值清理后的精灵像素，新增 `solidAt/hitAt`，
  按**当前帧**做 alpha 命中判定，命中才 `setInteractive(true)`；拖拽期间不释放。
- `src/main/index.ts`：转发 `CH.interactive`；16ms 光标轮询（位置变化才发 `pointerHint`）。
- `src/shared/ipc.ts` / `preload.ts` / `global.d.ts`：新增 `CH.interactive` 与 `CH.pointerHint`。
- `desktop-pet.json`：`render.defaultScale` 1.0 → 0.75。
- `tools/npm-run.mjs`：新增（这个环境 Bash shim 没有 npm，node -e 拼 cmd 转义层数太多，已踩过一次）。

## 复测结果

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 窗口内被吃掉 | 90/90（100%） | 34 点，**全部在精灵轮廓内** |
| 误吃（应穿透却被吃） | 43 | **0** |
| 漏吃（应命中却穿透） | 0 | 2（轮廓最外一行，1px 边界） |
| 拖动后命中图 | 不稳定 | 与拖动前逐点一致 |
| 拖动后窗口尺寸 | 每次 +1 DIP | 稳定 |

缩放：`--screenshot` 自检截图实测宠物 **151×218 物理像素 = 100×146 DIP**，
与"精灵表 134×194 × 0.75 × 1.5"完全吻合，面积比 0.562，落在要求的 0.5~0.7 区间。
