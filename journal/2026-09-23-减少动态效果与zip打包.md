# 2026-09-23 · 减少动态效果不该冻结动画 + 打包压 zip 改用自带实现

## 开局是什么

用户把上一轮打好的 `desktop-pet-1.0.0-win-x64.zip` 发给两位朋友，其中一位（Windows 11 25H2）
回报：

> 他的动作不管是在悬浮条里你点击哪个动作，都是一种静态图片的展示，并没有动起来。
> 左走右走也都是简单的图像平移。然后炒菜呢，就是一个站立不动的图片、贴图。
> 但是我给另一个朋友发他那边就是正常的是可以运动的。

用户的问题是："图片要动起来形成动画，是不是有什么依赖？是不是要什么依赖的系统环境或者库？"

## 我怎么定位的

**先按"用户猜的方向"去否掉它**，这比直接顺着猜要省事：如果是缺运行库/缺 DLL，Electron 根本起不来，
不会是"窗口在动、只有帧不动"。所以去查**帧是怎么推进的**：

`grep requestAnimationFrame / frameIndex / tick` → 全仓只有 `src/renderer/renderer.ts` 在用
`requestAnimationFrame`，且**没有任何兜底**。然后看到第 102 行：

```ts
if (player && !reducedMotion) player.update(dt);
```

往上找 `reducedMotion` 的来源：

```ts
const reducedMotion = window.matchMedia?.('(prefers-reduced-motion: reduce)').matches ?? false;
```

这就是 Windows「设置 → 辅助功能 → 视觉效果 → **动画效果**」。开关打开 ⇒ 帧推进被整个关掉 ⇒
`setState` 换了行、帧永远停在第 0 帧 ⇒ 正好是"一张静态图""站在不动的贴图"。
另外两处也挂着同一个开关：`reconcileStatus()` 直接落到静止落点、左键「拜一下」也不播。

**接着查"这是不是故意的"**：ADR 018 里确实写了要尊重这个设置 —— 但**那段理由只针对行为层
（自主漫游/微动作）**，即"未经请求的动画"。而这个"尊重"被顺手用到了整个渲染层，
连用户**显式点击**的动作也一起吞了。⇒ 这是把范围放大了，不是设计如此。

## 复现（这一步很关键）

这个缺陷**在一台机器上根本看不出来** —— 它需要两台系统设置不同的机器对照。
用 Electron 的 `--force-prefers-reduced-motion` 在本机造出那个条件，新建 `spikes/motion/`：

- 探针采样**渲染层实际画面**（每帧取指纹），而不是问代码"你打算演什么"；
- 结果（**修复前**）：正常机器 `idle` = `ABCCDDEEFFGGHHCCDDEEFFGG`（8 种在循环）、
  手动动作 = `ABCDEFGABCDHEFG…`；强制 reduce 时 **`AABBBBBBBBBBBB…`（变一次后冻死）/
  `AAAAAAAAAAAA…`（一动不动）** —— 与用户报的三种症状完全对上。

这里有个小插曲值得记：我第一版探针只数"有几种不同画面"，得到 2 种（不是 1 种），
**与我的预期不符**。于是改成打印**序列**才看清是"开头变一次然后冻住"。**数个数会骗人，序列不会。**

## 改了什么

- 新增 `src/kernel/motion-policy.ts`（纯函数：`parseMotionPolicy` / `shouldAdvanceFrames` /
  `describeMotionPolicy`）。**判据下沉到内核**才能单测 —— 这个缺陷是"两台机器对照才看得见"的那类。
- 主进程随 init 下发给渲染层；渲染层**不再自己读 `matchMedia` 去决定"要不要推进帧"**
  （但仍要把它**上报**给主进程，因为行为层要靠它决定要不要漫游）。
- sidecar `reducedMotion.strategy` 默认从 `freeze-frame` 改成 **`animate`**，想完全静止的人可改回去。
  顺手清掉一处文档腐化：sidecar 里那个 `strategy` 字段**代码从来没读过**。
- 启动横幅加一行 `减少动态效果：系统开关=…｜策略=…` —— 下次不用两台机器对照就能看出原因。

## 打包时撞上的第二件事（比第一件更值得记）

交付上面这个修复时，`make-portable.mjs --zip` **先炸了，而且炸得没有声音**：

```
tar -a -c -f desktop-pet-1.0.0-win-x64.zip desktop-pet
  → exit 0，脚本打印「zip 完成：…（373 MB）」
  实际产物：一个 tar（头部是 tar 的文件名，不是 PK\x03\x04）
```

`-a`（按后缀自动选格式）没生效。对方拿到的是改名为 `.zip` 的 tar，**双击解不开**；
而日志那一栏"373 MB"**恰好等于未压缩体积** —— 从任何一处都看不出破绽。
**这是这一轮最该记住的一件事：一个"成功"的日志，可以完全没有价值。**

⇒ 新增 `tools/zip-dir.mjs`（纯 Node：`zlib.deflateRawSync` + 手写 ZIP 结构 + CRC-32 +
逐条目流式写盘），`make-portable.mjs` 改 import 调用它，并且**压完回读魔数**：

```js
if (magic !== '504b0304') die('压缩产物不是 ZIP —— 别把它发出去');
```

实测 236 个文件 / 372.6 MB → **156.8 MB / 10.1 秒**。

同批还有第二处同形问题：单测第 ⑳ 节用 `spawnSync` 起 node 跑 `check-timers.mjs`，
本机沙箱间歇 `EBUSY` ⇒ **一条与定时器无关的断言被环境判红**。
改成 `check-timers.mjs` 导出纯函数 `checkTimers()`、单测直接调用（CLI 用法不变）。

## 没做 / 做不到的

- **`make-portable.mjs` 里 `rcedit` 那一步仍是 `spawnSync`**（原生 exe，没有等价 JS 实现）。
  本机沙箱会拒它 ⇒ 本轮是**分步跑完**的（复制 → rcedit → README → zip）。这一处没改：
  **它失败时会报错，不是静默的**，风险等级不同。
- **本沙箱里验证不了便携版"长期驻留"**：`spawn(detached)` 起的进程会被沙箱回收
  （日志写完了但进程查不到），`explorer.exe` 时灵时不灵。能验的只有"它完整启动并初始化完成"；
  **长期驻留仍需用户双击确认**。
- 上一轮记的 **PLAN §4 #16**（`m2-control` 依赖真实鼠标的用例偶发失败）**本轮没碰** ——
  它需要"拖动前置确认到位再继续"的重试，属于另一件事。
