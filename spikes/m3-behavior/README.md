# spikes/m3-behavior · 行为层的真实窗口验证（M3 第一块）

结论已回写到 **ADR 018** 与 `docs/design/m3-behavior.md`。这个目录**建议留着做回归** ——
改了 `kernel/behavior.ts`、`desktop-pet.json → behavior`、或任何窗口移动相关代码都要重跑。

## 怎么跑

```bash
node spikes/m3-behavior/run.mjs          # 约 1.5 分钟；跑之前先 node tools/npm-run.mjs build
```

产出 `behavior.json`（判定与逐段数据）+ `behavior.log`（主进程日志，含 `[probe]` 行）。

## 它验什么（7 条）

| 判据 | 为什么必须用真实窗口 |
|---|---|
| 12 秒内真的在走 | 纯函数只算"命令"，窗口有没有真的移动是另一回事 |
| **只沿地平线走**（y 从不变化） | 位移只改 x，纵向由窗口管理逻辑守着 |
| 不越出工作区 | `setContentBounds` 的取整 + 工作区夹取只有真窗口能验 |
| **位移行号与移动方向一致** | 渲染层画的是不是第 1/2 行、方向对不对，只有画出来才知道 |
| 抓住不放时一步不动、松手恢复 | 需求"绝不与用户的手抢方向盘"，且要看真实指针事件的边沿 |
| 控制条开着时不动 | 面板锚在宠物身上，动了会一起飘 |
| running 期间不动 | 业务状态优先于自主行为 |
| 打盹画到第 5 行、单击能醒 | 睡眠姿态与"被摸一下要醒"是观感，不是逻辑 |

## 为什么用**临时宠物包**

真实参数是"每 25–90 秒走一次、5 分钟后打盹"，照原样验一轮要十几分钟，而且中途任何一步失败都
**看不出是哪条规则的问题**（第一版就是这么误诊的：探针设了 5 秒打盹，观测窗口还没开始宠物就睡着了，
"没在走""拖动没生效""单击没唤醒"全是同一个原因）。

所以探针把 sidecar 复制到临时目录、**只改 `behavior` 段的节奏**（2–3 秒走一次、20 秒打盹），
`pet.json` / `behavior-map.json` / `spritesheet.webp` 原样带过去、**不改任何代码路径**。

## 踩到的坑（复现时注意）

1. **注入点击不能打窗口中心**。命中判定是渲染层按**当前帧**的 alpha 给的（ADR 008），
   而趴卧（第 5 行）这类姿态的精灵贴在单元格底部 —— 窗口中心是透明的 ⇒ 那时窗口处于整窗穿透，
   注入的按下根本到不了渲染层。探针因此先用 `dbg.petInteractive()` **扫出一片网格里真的落在
   精灵上的点**（`findSolid()`），再点它。这是第一版报出两条假失败的直接原因。
2. **打盹阈值别设太短**。设了 5 秒，观测阶段开始时它已经在睡（`sleeping` 相位会挡住漫游）——
   于是"没在动"的根因与漫游无关。现在 20 秒，并且每个阶段前先 `ensureAwake()`。
3. **回归探针要带 `--no-behavior`**（本目录的探针当然不带）。宠物会自己走，位置类断言全都
   变成"读一次窗口位置、再按它算点击坐标" —— 中间走掉了就点空。
4. 采样窗口内可能出现"行号 0/3/4"：那是漫游之间的待机与**微动作**（挥手/跳跃），
   判据只看"位移行号与方向是否一致"，所以只对 `row ∈ {1,2}` 且两端都在位移行上的相邻采样做检查。
