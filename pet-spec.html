结论速览

1. 它不是养成游戏，是状态显示器

Pets 的本质是「Agent 任务状态的视觉化承载层」。官方原话：选择不同的宠物只会改变外观，不会影响 ChatGPT 完成任务的方式。宠物没有任何任务能力，也没有用户可操作的成长系统。

2. 真正的核心资产是一份极简契约

一个宠物包只有两个文件：pet.json + spritesheet.webp。图集尺寸严格固定为 1536×1872，8 列×9 行的 192×208 单元格。整套格式小到可以被第三方在一周内复制出十几个图库站。

3. 生成资产靠技能，不靠内置编辑器

官方没有提供图形化宠物编辑器。创建自定义宠物的路径是：安装 bundled 的 hatch-pet 技能 → 用自然语言描述 → 模型生成 1 张基准图 + 9 条动画行 → 脚本确定性地拼成图集并打包。

4. 状态机只有四态，但优先级是设计重点

Running / Needs input / Ready / Blocked。多对话并存时按「需要输入 > 受阻 > 就绪 > 运行中」仲裁。这是把「多任务焦虑」压回单点视觉信号的关键设计。

对我们的直接影响

如果我们采用与 Codex 完全一致的宠物包契约（1536×1872 / 8×9 / 192×208 / pet.json），将直接获得两件事：一是可复用社区已产出的上千套现成精灵图，二是我们自制的宠物也能被 Codex 客户端直接加载。这是一个成本极低、收益明确的兼容性决策。

1 它到底是什么：先做一次事实核查

「ChatGPT 里面有个宠物系统」这个说法需要先被精确化。真实情况是：Pets 是 ChatGPT / Codex 桌面客户端的一个可选悬浮伴侣功能，于 2026 年 5 月上线，2026 年 9 月扩展了 Quick Chat 能力。它同时存在于桌面端、网页端和 Codex CLI 终端，但三处能力差异很大。

1.1 时间线

  • 2026-05 · 上线ChatGPT 桌面端（macOS / Windows）引入 Pets。8 款内置像素风宠物，/pet 命令与 Settings > Pets 入口，可悬浮于其他应用窗口之上，实时显示 Codex 任务状态。同期上线自定义宠物能力（hatch-pet 技能）。
  • 2026-05 · 社区爆发PetShare、Petdex、codex-pets.net 等第三方图库站在数周内出现，npx codex-pets add <slug> 之类的安装 CLI 随之出现。
  • 2026-09 · 能力扩展加入 Quick Chat：可直接在悬浮宠物下方的输入框打字或语音发起对话，并用 @ 添加上下文、$ 选择技能。Mini 模式（只保留控件、不显示宠物）同期可见。
  • 2026-09 · 多端铺开网页端（Settings > Personalization > Pet）、Codex CLI 终端宠物（/pets）、以及明确不提供宠物的 IDE 扩展。

1.2 官方定位原文

官方事实

「Pets are optional animated companions for following work. Where a pet appears and what it shows depend on the interface you use. Choosing a pet changes its appearance, not how ChatGPT completes tasks.」

这一定位决定了它的全部边界：宠物是只读的状态呈现层，不是 Agent 的一部分，不参与任务执行、不影响工具调用、不改变模型行为。

2 四种承载形态与能力差异

3.2 悬浮控件上能做什么

鼠标移到宠物下方的控件区后，提供三类入口：

  • 铅笔图标 — 发起 Quick Chat。输入请求回车发送；@ 添加上下文，$ 选择技能。
  • 铃铛图标 — 打开活动托盘，跟进所有线程进度；点线程在 ChatGPT 主应用中打开完整对话，点折叠箭头收起。
  • 语音图标 — 语音输入（可用性遵循 ChatGPT Voice 的既有规则）。

3.3 活动托盘与系统通知是两套东西

官方事实

「The activity tray is separate from system notifications.」

这一点在工程上很关键：宠物不接管系统通知渠道，它是一个独立的应用内状态面板。把「Agent 状态可视化」与「操作系统级提醒」解耦，既避免了与通知中心的功能重叠，也让用户可以单独关闭其中一个。

3.5 可访问性：减少动态效果

官方事实

「Pets respect your operating system's reduced motion setting. When reduced motion is enabled, the pet uses a still frame instead of sprite animation.」

落地要点：减少动画时不是停止播放（会停在随机帧），而是固定使用一个静帧。结合图集规范，这个静帧应当是 idle 行的第 0 列。我们的实现里必须显式处理这条分支，否则会出现「宠物卡在 failed 那种趴平帧上」的糟糕体验。

3.6 状态与位置持久化

  • 宠物选择与屏幕位置在应用重启后保留。
  • 自定义宠物创建于桌面端时存储在本机，不会自动同步到网页端。
  • 选中自定义宠物后，它也会出现在 Profile 视图中。

4 状态机与优先级

这是整个系统里最值得逐字照搬的部分。官方只定义了四个状态，但两个细节是设计精华：状态语义与仲裁优先级。

状态官方含义用户视角的潜台词
RunningA chat is actively working.正在干活，别打扰，也别担心
Needs inputA chat needs your approval, answer, or another decision.卡在你这儿了，必须处理
ReadyA chat has completed and has unread activity.出结果了，去看一眼
BlockedA chat failed or encountered a system error.出问题了，需要介入
官方事实 · 优先级

「When more than one chat has activity, the pet prioritizes chats that need input, followed by blocked, ready, and running chats.」

即：Needs input > Blocked > Ready > Running。

把这个顺序翻译成设计语言：优先级排序的依据不是「紧急度」而是「需要用户动作的程度」。Needs input 是唯一一个用户不动作流程就无法推进的状态，因此置顶；Blocked 需要用户判断是否重试；Ready 只需用户确认；Running 完全不需要用户动作，因此垫底。

5 架构反推

OpenAI 从未公开 Pets 的内部实现。下面的分层结构是根据三组硬约束反推出来的：官方对「宠物只改变外观、不影响任务」的定义、四种承载形态并存的事实、以及 1536×1872 单一图集契约的存在。它是一条自洽的解释路径，可作为我们设计的起点。

5.1 关键接口设计

反推出的层间接口都刻意保持极小：

这套切法的直接证据是终端宠物：终端没有窗口、没有活动托盘、没有 /pet 之外的交互，却能展示同样的四态与同一批内置宠物。如果播放层与业务逻辑耦合，终端形态将无法以如此低的成本实现。

7 设计意图解读

理解「为什么这样设计」，比记住「它是怎样」更有迁移价值。以下是对几个关键取舍的解读，均基于公开信息推导。

用宠物替代进度条

Agent 类工具的核心体验问题是「后台执行期间的不确定性」。传统做法是进度条或日志，但它们都需要用户主动切回应用查看。宠物的解法是把状态搬到用户已经盯着的屏幕上，用生物性的动作代替数字。

为什么只有四个状态

状态数受限于「必须能被一眼区分」。九个动画行里真正承担状态语义的只有四个，其余五行是表现层动画。增加状态会直接增加用户的识别成本，而识别的即时性正是这个功能的全部价值。

优先级按「需用户动作」排序

不是按重要性，也不是按时间。这是把「用户注意力」当作唯一稀缺资源来分配的设计，而不是按系统视角的紧急度。

活动托盘与系统通知分离

避免与操作系统通知中心竞争。宠物管「我一直在看着你的任务」，通知中心管「有事发生」。两者渠道不同、打扰强度不同，可以独立关闭。

没有养成与成长系统

没有等级、经验、喂食、亲密度。这些机制会引入「用户必须回来维护宠物」的义务，与「降低焦虑」的初衷相反。宠物不向用户索取任何东西。

没有图形化宠物编辑器

与其做一个复杂的 sprite 编辑器，不如把一个技能交给模型：描述 → 生成基准图 → 生成九行动画 → 脚本拼装。编辑器交给 AI，约束交给脚本。

本报告推断 · 契约为什么这么小

pet.json 只有四个必需字段，图集尺寸被写死成唯一值。这种「极简且刚性」的设计不是偷懒，而是刻意的：一个刚性契约能让社区在没有官方工具的情况下自行生产、验证、分发资产。事实上上线数周内就出现了 PetDex、PetShare、codex-pets.net、hatch-pet.com 等多个第三方图库与安装 CLI，全部基于这一份契约。如果我们希望自研桌宠也能形成生态，压缩资产契约的自由度、换取可验证性，是被验证过的正确取舍。

8 宠物包资产契约

这是本报告中最具直接复用价值的部分。以下内容来自官方文档与 hatch-pet 技能契约，并与多个第三方实现交叉验证一致。

8.1 包结构

${CODEX_HOME:-$HOME/.codex}/pets/<pet-id>/
├── pet.json          # 必需 · 清单
└── spritesheet.webp  # 必需 · 图集（也接受 .png）

Windows 上 ${CODEX_HOME} 默认展开为用户目录下的 .codex，例如 C:\Users\<name>\.codex\pets\<pet-id>\。分发时通常打包为包含这两个文件（位于压缩包根目录）的 ZIP。

8.3 官方网页端上传限制

9.1 播放规则（最容易踩错的一条）

硬性规则

播放从第 0 列开始读取连续的非空帧，末尾的空单元格被忽略。

这意味着帧数不是靠声明，而是靠「哪里开始透明」推断出来的。如果某一行的第 0、1、2 帧有内容、第 3 帧意外为空、第 4–7 帧又有内容，那么实际播放的只有 3 帧，第 4–7 帧永远不会被播放。这类「空洞」是社区自制宠物最常见的失败原因。

12 风格与透明度规范

12.1 Codex Digital Pet Style

这是官方为内置宠物定义的画风。即使你的参考图是写实或高精度插画，也要先简化成这个风格再进入行生成。

维度要求
整体类型像素风邻接的小型吉祥物，紧凑 Q 版比例
轮廓厚实、可读，1–2px 深色描边，可见的阶梯/像素边缘
配色有限色板
上色平涂赛璐珞阴影，无软渐变
面部与四肢表情简单，四肢短小
明确不要精细插画、绘染渲染、动画主视觉、3D 渲染、光泽应用图标质感、写实毛发或材质、软渐变、高精度抗锯齿、复杂微小配饰

12.2 透明背景与色键规则

  • 每一行都要在干净的、纯平面的色键（chroma key）背景上生成，不允许白底、黑底或棋盘格透明示意。
  • 色键颜色记录在 pet_request.json 中，不强制绿幕。
  • 宠物本体、道具、特效、高光、阴影都不得使用与色键相近的颜色，否则去背时会咬掉宠物本身。
  • 行条带切分后每个像素要么属于宠物，要么是能被干净移除的色键背景——不允许杂散像素、断续描边、被裁掉的肢体、跨格姿势。

12.3 特效白名单与黑名单

官方规范 · 允许的特效

必须同时满足五条：状态相关且有助解释动画；物理上贴合/接触/重叠宠物轮廓而非在旁漂浮；位于同一帧槽内不构成独立精灵部件；不透明、硬边、像素风且非色键色；在 192×208 下仍清晰不杂乱。

典型允许项：贴着脸的眼泪、贴着箱子或头部的小股烟、失败/眩晕时压在宠物身上的小星星。

官方规范 · 默认禁止

会被去背/提取破坏的：波浪纹、运动弧线、速度线、动作条、残影、模糊、涂抹。

漂浮类：分离的星星、松散的闪光、浮动标点、浮动图标、坠落的泪滴、分离的烟云、松散尘点。

阴影类：投射阴影、接触阴影、椭圆地面阴影、地面斑块、落点痕、冲击爆、辉光、光晕、光环、柔边透明效果。

非视觉噪音：文字、标签、帧编号、网格线、引导标、对话框、UI、代码。

本报告推断

这份特效黑名单看起来苛刻，但它服务于一个具体的工程目的：让每一帧都能被无歧义地去背和切分。所有「漂浮的、柔边的、半透明的、脱离主体的」元素都会让自动去背产生残留或误删。如果我们的管线也想做自动化资产处理，这条原则必须照搬——把「机器可可靠处理」作为美术约束的第一原则。

13 QA 判定标准

13.1 形象一致性（第一阻断项）

所有行必须与基准图共享同一个：头型、面部、标记、调色板、道具、描边粗细、身体比例、剪影。规范里有一句很重的判语：任何一行如果看起来像「相关的但不同的宠物」，即判失败。

13.2 阻断项清单

  • 任何行改变了物种、体型、脸型、标记、调色板、道具所在侧或整体轮廓。
  • qa/review.json 中存在 error（warn 需要人工目视确认）。
  • 联系表出现：参考图被裁切、重复瓦片、白色格底、非精灵碎片。
  • 出现被禁止的特效：分离特效、色键邻色残影、阴影、辉光、涂抹、尘土、落痕、波纹、速度线、拖影。
  • 形象漂移即使 JSON 校验全部通过，也直接阻断。

13.3 running-left 的镜像判定

镜像可以省下一次图像生成，但只有在确认对称性安全时才允许。判断依据是：宠物是否具备非对称的单侧标记、可读文字、非镜像 Logo、有手性的道具、单侧配饰、固定光向，或方向语义会因翻转而错误。

# 仅在目视确认镜像不会破坏形象一致性后执行
python scripts/derive_running_left_from_running_right.py \
  --run-dir /absolute/path/to/run \
  --confirm-appropriate-mirror \
  --decision-note "说明为什么镜像能保留该宠物的身份特征"

如果不能镜像，就把 running-left 作为一次正常的生成任务，并把 running-right 作为步态参考一起传入。

{
  "state_name": "miner_tired",
  "dims": [0, 0, 45, 50],            // 偏移 X、偏移 Y、帧宽、帧高
  "move": [2, 0],                  // 每帧位移 [x, y] 像素
  "file_name": "miner_idle.gif",
  "transitions_to": [
    { "name": "miner_tired",   "probability": 0.8 },  // 80% 留在当前状态
    { "name": "miner_sleeping", "probability": 0.2 }  // 20% 转入睡眠
  ]
}
{
  "trigger": "click",
  "type": "chatgpt",
  "prompt": "Let's chat.\nMe: %s\nYou:",   // %s 注入用户消息
  "listen_state":   "begin_listening",   // 点击后进入
  "response_state": "begin_talking",    // 开始回复时进入
  "end_state":      "idle"             // 回复结束后进入
}
本报告推断 · 为什么这份设计值得抄

它把「宠物在做什么」抽象成两个正交维度：状态（states）管形象与自动游走，事件（events）管外部触发。Codex Pets 的九行动画本质上可以被理解为九个状态，而它的四个运行时状态是由外部事件驱动的状态切换。两者可以合并成同一套模型：用官方四态做业务状态，用九个动画行做呈现状态，中间加一层带优先级的映射——这正是第 5 节反推出的架构。

15.2 鼠标穿透的正确做法：默认穿透 + 按需收回

关键取舍

整窗 setIgnoreMouseEvents(true) 会让宠物无法被点击；整窗不穿透又会在宠物周围的透明区域挡住用户操作。正确做法是默认穿透，并借助 { forward: true } 把鼠标移动事件转发给渲染进程，由渲染进程判断光标是否落在宠物身上，再动态收回穿透。

win.setIgnoreMouseEvents(true, { forward: true });

ipcMain.on('pet-hover', (event, hovering) => {
  const w = BrowserWindow.fromWebContents(event.sender);
  w.setIgnoreMouseEvents(!hovering, { forward: true });
});
// renderer —— 用 pointer-events 精确控制哪些区域“可交互”

15.3 多显示器与位置持久化的坑

把窗口位置直接存盘会在一种情况下导致「启动后宠物消失」：用户把宠物拖到副显示器后关闭，下次启动时那块显示器已不存在。正确做法是启动时用 screen.getAllDisplays() 取出所有显示器边界，校验保存的坐标是否落在任一显示器的可视区域内，否则回落到主显示器安全区。

function validateSavedPosition(saved, fallbackDisplay) {
  if (!saved) return null;
  const inside = screen.getAllDisplays().some((d) => {
    const b = d.bounds;
    return saved.x >= b.x && saved.x < b.x + b.width
        && saved.y >= b.y && saved.y < b.y + b.height;
  });
  return inside ? saved : null;
}

15.4 状态仲裁器（照搬官方优先级）

const { STATUS_PRIORITY, STATUS_TO_ROW } = require('./pet-spec');

/** sessions: [{ id, status }]，status ∈ needs_input | blocked | ready | running */
function resolveDisplay(sessions, idleAfterMs = 60_000) {
  for (const status of STATUS_PRIORITY) {          // 按官方优先级短路
    const hit = sessions.find((s) => s.status === status);
    if (hit) return { status, row: STATUS_TO_ROW[status], sessionId: hit.id };
  }
  return { status: 'idle', row: STATUS_TO_ROW.idle, sessionId: null };
}
实现建议

加一个「瞬时动画」通道是必要的：waving（被点击）、jumping（任务成功）这类行不属于四态仲裁的结果，而是一次性插播。建议仲裁器输出 { row, loop }，其中插播动画以 loop: false 播放一次后回落到仲裁结果。这样业务状态与表现动画就不会互相污染。

15.5 8×9 图集播放器

const CELL_W = 192, CELL_H = 208;

// 行号 → 帧数。帧数也可由图集自动探测（从第 0 列起连续非空格）
const ROWS = {
  idle: [0, 6], 'running-right': [1, 8], 'running-left': [2, 8],
  waving: [3, 4], jumping: [4, 5], failed: [5, 8],
  waiting: [6, 6], running: [7, 6], review: [8, 6],
};

class AtlasPlayer {
  constructor(image, { fps = 8, reducedMotion = false } = {}) {
    this.img = image; this.fps = fps; this.reducedMotion = reducedMotion;
    this.state = 'idle'; this.frame = 0; this.loop = true;
  }
  play(state, { loop = true, fps } = {}) {
    if (state === this.state && loop === this.loop) return;  // 避免重复状态打断动画
    this.state = state; this.loop = loop; this.frame = 0;
    if (fps) this.fps = fps;
  }
  draw(ctx, dx, dy, scale = 1) {
    const [row, frames] = ROWS[this.state] ?? ROWS.idle;
    // 减少动效时固定使用 idle 第 0 帧，而不是随机停在动画中途
    const col = this.reducedMotion ? 0 : this.frame % frames;
    const r = this.reducedMotion ? ROWS.idle[0] : row;
    ctx.drawImage(this.img, col * CELL_W, r * CELL_H, CELL_W, CELL_H,
                  dx, dy, CELL_W * scale, CELL_H * scale);
  }
}

17 面向我们开发的建议

17.1 四个前置决策

决策 1 · 采用兼容契约

建议：直接使用 Codex 的宠物包格式（1536×1872 / 8×9 / 192×208 / pet.json）。
收益：可加载社区上千套现成精灵图；我们产出的宠物可被 Codex 客户端直接使用，等于免费获得一个分发渠道。
代价：美术上受九行结构与 192×208 尺寸约束；需要为超出九行的新语义（例如「思考中」「等待网络」）设计降级映射。

决策 2 · 壳层与渲染分离

建议：把「宠物外壳（窗口、穿透、定位、托盘）」与「帧播放器（图集解码、状态映射）」拆成两个可独立替换的模块，接口只传 {row, frameCount, loop} 与一张带 alpha 的位图。
理由：这是官方能同时支持悬浮窗、网页内联和终端三种形态的唯一解释路径。我们即使短期内只做一个形态，也应该保留这条边界。

决策 3 · 状态模型两层化

建议：业务状态沿用官方的四态（Running / Needs input / Ready / Blocked）与其优先级，另加一层「插播动画」通道处理 waving / jumping 这类一次性表现。
理由：四态已被验证是「可被一眼区分」的上限；而业务事件与表现动画混在同一层会让仲裁逻辑迅速失控。

决策 4 · 资产管线照搬 hatch-pet 模式

建议：不自建图形化精灵图编辑器。改为「模型生成 + 脚本组装 + 双层验收」，并配备本报告附带的模板生成器与校验器。
理由：编辑器是长期投入且难以覆盖长尾创意；技能化路径能把创意成本转嫁给模型，同时用刚性契约保证产物可用。

17.4 里程碑建议

  • M0 · 壳层可行性验证把透明、置顶、穿透、拖拽、位置持久化、多显示器回落跑通。这一阶段不放任何资产，只验证「宠物能不能稳定地待在桌面上且不干扰操作」。这是风险最高、最该先做的一步。
  • M1 · 契约与播放器固化 pet.json 与图集规格，实现图集播放器，用本报告附带的 examples/demo-pet 与模板图打通「加载 → 校验 → 播放」链路。
  • M2 · 状态接入接入我们自己的任务/会话事件源，实现仲裁器与插播通道，把四态跑通。此阶段即可验收「宠物是否真的降低了查看任务的切换成本」——这是这个功能唯一的核心指标。
  • M3 · 资产管线照搬 hatch-pet 模式搭生产管线：任务清单落盘、生成、切帧、校验、联系表、预览视频、打包。目标是「一句描述产出一个可安装宠物包」。
  • M4 · 交互与记忆在宠物上叠加快捷输入、托盘、语音等交互；如需要「记得你」的长期记忆，参照 N.E.K.O 把记忆做成独立服务，不要塞进渲染进程。
